# Pair agents with SANE’s actual browser

**Yes, entirely local control of the exact visible session is feasible—but SANE’s current browser pane is an HTML iframe inside the browser hosting SANE, not a native webview or an app-owned Chromium instance.** The smallest approach is to attach an authorized controller to that hosting Chromium browser, select the existing SANE page, and operate its existing preview frame. Sharing cookies, reopening its URL, or launching another browser does not preserve the same live page. Existing “Browser Pair” is explicitly passive metadata, and the available Chrome DevTools MCP is not automatically connected to that frame. For a robust embedded product without replacing SANE’s web-app shell, prefer an app-owned local Chromium session whose exact target supplies both the streamed view and automation. Native Chromium embedding offers better interaction fidelity at substantially greater integration cost; Browserbase supplies a useful hosted UX reference, not an established all-local solution. ([Current iframe implementation, browser-view.tsx:176–183](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176-L183); [Pair contract:1–9](file:///Users/beto/sane/packages/sane-app/shared/browser-pair-contract.ts#L1-L9))

## The live session belongs to SANE’s hosting browser

SANE App is a Bun-served React browser application, optionally installed as a PWA. Its supported installation flows include Safari Add to Dock; installation does not create a native browser-control service. Therefore the decisive first question is **which browser and device host the current SANE window**, not which hypothetical native engine SANE embeds. That runtime fact was not inspected. Detailed WKWebView/Tauri attachment research is conditional background, not the explanation of today’s implementation. ([package.json:5–46](file:///Users/beto/sane/packages/sane-app/package.json#L5-L46); [README.md:173–183](file:///Users/beto/sane/packages/sane-app/README.md#L173-L183))

SANE’s tabs are `{id,url}` UI records, not native tabs or CDP page targets. `BrowserFrame` renders an iframe beneath `#browser-panel-<tab.id>`; persisted state records URLs, IDs, and display preferences, not browser profiles or live execution state. Hidden frames remain mounted within the browser view, but reload/URL changes replace the iframe, and workspace changes remount the keyed browser view. An integration must track the actual frame and its lifecycle rather than treating a saved URL as session identity. ([browser-tabs.ts:1–60](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L1-L60); [browser-view.tsx:133–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L133-L181); [app.tsx:408–409](file:///Users/beto/sane/packages/sane-app/frontend/app.tsx#L408-L409))

**Same live page is stronger than same cookies/profile.** Another tab with matching authentication still has its own DOM, JavaScript heap, session storage, history, connections, and unsaved application state. A top-level external tab also need not inherit the iframe’s partitioned storage behavior. Neither profile reuse nor storage-state import fulfills exact-session control. Browser Pair does not bridge this gap: its contract says “A link grants no browser or execution capabilities,” and the API explicitly avoids fetching tab URLs or dispatching agent actions. ([Playwright authentication reuse](https://playwright.dev/docs/auth#session-storage); [Pair contract:1–9](file:///Users/beto/sane/packages/sane-app/shared/browser-pair-contract.ts#L1-L9); [bridge.ts:3566–3596](file:///Users/beto/sane/packages/sane-app/src/bridge.ts#L3566-L3596))

Embedding remains a separate constraint. Sites can reject framing through CSP `frame-ancestors` or X-Frame-Options; third-party storage restrictions and HTTPS/mixed-content rules also remain. SANE already warns about these limitations. Privileged automation does not make an otherwise blocked iframe usable. ([SANE limitations, browser-view.tsx:123–127](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L123-L127); [HTML embedding rules](https://html.spec.whatwg.org/multipage/iframe-embed-object.html))

## CDP can reach the exact frame, but MCP presence proves no pairing

Chrome DevTools MCP is an automation interface to a Chrome instance, not an embedded browser surface. Its documented `--browser-url` and `--ws-endpoint` attach modes can connect to an existing browser; browser-use exposes `cdp_url`, and Playwright exposes `connectOverCDP`. **Attaching to the host’s existing SANE target and existing preview frame preserves that live session**, provided the controller does not reload or replace it. Attaching to another Chrome instance—even one with the same URL—is different. ([Chrome DevTools MCP configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md); [browser-use settings](https://docs.browser-use.com/customize/browser-settings); [Playwright attachment](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp))

The tool schemas exposed in this research session were inspected without calling the browser. They confirm page-scoped `pageId` routing, accessibility snapshots with element UIDs, UID-based clicks, and page JavaScript evaluation. The exposed evaluation schema has **no explicit frame selector**. This verifies useful primitives, not that snapshots/actions reliably cover SANE’s particular cross-origin preview frame, nor that the MCP controls the browser hosting SANE. Its endpoint, runtime version, and iframe behavior remain unverified; do not redirect an existing MCP connection blindly. ([MCP tools and routing documentation](https://github.com/ChromeDevTools/chrome-devtools-mcp); [Advanced attachment/concurrency](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md))

Cross-origin page scripting and privileged browser control are different boundaries. SANE cannot read an arbitrary preview’s DOM with `iframe.contentWindow.document`; `allow-same-origin` preserves the preview’s own origin, not SANE’s origin. A backend evaluate endpoint alone cannot reach a browser running on the frontend device. CDP-backed tooling can instead address frame execution contexts and out-of-process frames. Playwright explicitly provides `Frame`/`frameLocator` routing; page-level locators normally address the main frame. Browser-use documents `cross_origin_iframes`, defaulting to false, so generic “browser-use support” is not sufficient evidence of frame coverage. A small frame-aware adapter is the fallback if MCP’s snapshot/UID tools cannot reliably target the preview. ([Sandbox rationale, browser-view.tsx:7–9](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L7-L9); [Playwright frames](https://playwright.dev/docs/frames); [browser-use parameters](https://docs.browser-use.com/customize/browser/all-parameters))

On macOS, attachment has practical prerequisites. Chrome 136 stopped honoring command-line debugging flags against the default user-data directory; use a dedicated non-default profile for a newly owned browser. Separately, current MCP documentation describes permission-based Chrome 144+ `--autoConnect` after enabling remote debugging and approving access. That is not a reason to restart personal Chrome or reuse its locked profile directory. Playwright CDP attachment is Chromium-only and documented as lower automation fidelity than its native protocol; Safari/WebKit inspection is not a compatible CDP endpoint. ([Chrome debugging restriction](https://developer.chrome.com/blog/remote-debugging-port); [MCP attachment guide](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [Playwright CDP limitations](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp))

## Prove exact-frame control before changing the rendering architecture

**The smallest proposed PoC is attachment, not streaming or a native rewrite.** After identifying the host, use an approved existing Chromium debugging connection, select the SANE top-level page, and resolve `#browser-panel-<tabId> iframe` to its live frame. Use frame-aware Playwright/CDP operations rather than opening a new page or choosing the first available target. Observe existing transient state, perform one reversible interaction, and confirm it appears in that same visible frame without navigation/recreation. This is a proposed acceptance exercise, not verification performed for this report. ([Existing frame identity, browser-view.tsx:176–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176-L181); [Playwright existing-page attachment](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp))

If the host cannot expose suitable automation, an authorized extension plus local relay is a plausible integration path, but requires permissions, frame routing, and a new security boundary; it is not implemented today. OS-level computer control can operate the exact visible window, including a Safari-installed SANE app, at the cost of desktop permissions, focus interference, and weaker semantic targeting. For workspace applications under your control, an origin-validated cooperative `postMessage` bridge is narrower still, but does not automate arbitrary sites. ([Current frame-only implementation](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176-L183); [macOS event posting](https://developer.apple.com/documentation/coregraphics/cgevent/post(tap:)); [ScreenCaptureKit permissions](https://developer.apple.com/documentation/screencapturekit))

A dedicated external headed Chrome window is the simplest fallback shared-browser baseline: human and agent operate one native tab with no image transport. **It is a middle ground, not an embedded SANE browser**, and creates a different session unless automation attaches to an already-existing intended tab. Opening SANE’s iframe URL externally is not live-session migration. ([MCP headed/attachment modes](https://github.com/ChromeDevTools/chrome-devtools-mcp); [SANE external-link implementation:170](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L170))

## Local streaming best preserves today’s shell; native embedding improves fidelity

For a durable product beyond the attachment PoC, the following ranking prioritizes SANE’s current web-app architecture and local macOS operation. These are engineering judgments, not measured latency results.

| Priority | Architecture | Practical fit and limitation |
|---|---|---|
| 1 | Local Chromium + page streaming + CDP | Keeps SANE’s web shell; one target supplies pixels and semantic automation. Requires serious viewer/input work. |
| 2 | Native Chromium embedding | Best expected in-app interaction fidelity; requires a desktop shell and browser-engine maintenance. |
| 3 | Local Linux browser desktop + VNC/noVNC + CDP | Useful when browser chrome/dialogs matter; adds VM/container and desktop infrastructure on Mac. |
| 4 | Native Mac desktop VNC | Can expose the existing browser, but captures/controls a much broader desktop surface. Poor default for one pane. |
| Outside local requirement | Browserbase Live View | Hosted interactive embed; useful reference or cloud alternative, not established local deployment. |

Local streaming replaces the target-site iframe with a viewer of an automation-owned browser. CDP `Page.startScreencast` sends real JPEG/PNG page pixels; `Input` forwards mouse/keyboard events. The AI retains DOM tools against that same target: screenshots need not become its only observation method. Top-level browsing in the owned browser removes target-site iframe restrictions, but does not import today’s iframe state. The experimental screencast API is not a full Chrome desktop stream; tabs, address bar, downloads/uploads, dialogs, Retina coordinate mapping, IME, clipboard, backpressure, and reconnection need explicit handling. Steel’s open local viewer is a concrete accelerator worth inspecting, not proof of native-quality UX. ([CDP Page](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl); [CDP Input](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl); [Steel deployment](https://github.com/steel-dev/steel-browser); [Viewer source](https://github.com/steel-dev/steel-browser/blob/main/api/src/templates/live-session-streamer.ejs))

Electron `WebContentsView` instead embeds an actual Chromium surface; its in-process debugger can avoid a public CDP port. CEF offers native hosting, including macOS `NSView`, but introduces substantial helper-process, bundle, and message-loop integration. Neither adopts an arbitrary existing external Chrome tab. Both are larger changes than streaming for this repository, with responsibility for sandboxing and browser security updates. ([Electron view](https://www.electronjs.org/docs/latest/api/web-contents-view); [Debugger](https://www.electronjs.org/docs/latest/api/debugger); [CEF integration](https://chromiumembedded.github.io/cef/general_usage))

noVNC is a WebSocket VNC client, not a browser controller: pair it with a VNC server and keep CDP for semantic automation. Linux Xvfb plus VNC is a credible isolated-desktop stack; on macOS, Docker runs it in a Linux VM, not the native Mac Chrome session. Apple Screen Sharing documents broader Mac desktop control, not a private per-browser Cocoa desktop. Browserbase Live View supports interactive iframe embedding and per-tab views, but public sources establish managed infrastructure, not a supported all-local server distribution; its internal transport was not established. Browserless is another self-hostable service, but live/hybrid feature availability and SSPL/commercial terms require separate review. ([noVNC](https://github.com/novnc/noVNC); [Docker VM](https://docs.docker.com/desktop/features/vmm/); [Apple Screen Sharing](https://support.apple.com/guide/mac-help/turn-screen-sharing-on-or-off-mh11848/mac); [Browserbase Live View](https://docs.browserbase.com/features/live-view); [Browserless](https://github.com/browserless/browserless))

## Make target ownership and locality explicit product contracts

For the recommended streamed architecture, supervise one local browser with its own persistent non-default profile. Maintain an app-tab-to-CDP-target registry; for current iframe attachment, additionally map the hosting page and frame. Treat MCP `pageId` as an adapter identifier, not raw `targetId`. Route both observations and actions through this registry, invalidate stale frame/document bindings, and coordinate viewport ownership. Add explicit consent separate from Browser Pair, a human-priority Pause/Take over/Resume lease, and serialized mutations. Explicit page IDs prevent wrong-tab routing, not concurrent human/agent typing. ([CDP Target lifecycle](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl); [MCP concurrency](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md))

Keep privileged control behind authenticated local IPC or a tightly scoped gateway; never expose raw CDP to preview-site JavaScript. Loopback binding is not authentication. Also preserve device semantics: today `localhost` means the frontend device, whereas a supervised browser resolves URLs on its own host. Remote clients, Docker networking, and tunnels change reachability. ([MCP security warning](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [SANE device-local warning:125](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L125))

**Local browser infrastructure does not imply local inference.** A cloud model still receives the page material sent to it. Fully local processing also needs a local model, local artifacts/logs, and audited telemetry/cloud-sync settings. MCP documents opt-outs for usage statistics, CrUX requests, and update checks; browser-use has telemetry/cloud-sync controls. Public websites still receive ordinary browsing requests. No tests, browser verification, latency benchmarks, or app changes were performed; mutable upstream capabilities must be checked against pinned implementation versions. ([browser-use local-model support](https://github.com/browser-use/browser-use); [MCP privacy controls](https://github.com/ChromeDevTools/chrome-devtools-mcp); [browser-use configuration](https://github.com/browser-use/browser-use/blob/main/browser_use/config.py))

## Conclusion

The product decision is whether SANE should **borrow control of the browser hosting its UI or own the browser it presents**. Keep these as distinct modes: the former preserves today’s live frame; the latter establishes a cleaner long-term control boundary but starts a new session. Making that distinction explicit prevents a convincing-looking browser pane from concealing that the user and agent are operating different pages.
