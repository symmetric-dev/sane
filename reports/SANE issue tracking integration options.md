# Add workspace issues without workflow coupling

**For SANE’s simple, genuinely in-app scope, recommend a narrow native issue service and React UI, stored in a separate application-data database—not a full project-management platform.** This requires more SANE development than an adapter, but avoids operating another tracker. The fastest baseline is GitHub Issues links plus an optional read pane; GitHub is explicitly a proprietary-service exception. If reusing a finished open-source product matters more than native ownership, choose **Vikunja**; choose **Plane Community** when richer Linear-like functionality justifies its substantially larger stack. No mature, complete JavaScript issue-tracker library meeting this scope was verified: dnd-kit supplies UI primitives, not tickets or persistence. Keep issue lifecycle independent of skills, workstreams, and acceptance; optional agent tools can accompany **any** integration level. Most importantly, do not create issue state in an uninitialized `.sane`, or add arbitrary tables to `sane.db`.

Research snapshot: **2026-10-05**. This report synthesizes four research notes and a bounded source audit. Upstream facts are cited; SANE designs and rankings are proposals, not existing capabilities or measured estimates. No deployment, tests, browser verification, or code changes were performed. Repository findings describe the inspected working tree, which contains ongoing changes.

## Three levels rank integration effort, not hosting burden

These levels increase total **SANE implementation scope** for the stated UI, while operations remain a separate axis. A link to an existing Plane instance is still Level 1; adding its adapter and native editor is Level 2. Operating Plane from scratch can be more burdensome overall than building Level 3’s small local feature.

| Rank by SANE integration effort | Concrete approach | SANE UI and ownership | Separate operational complexity |
|---|---|---|---|
| **1 — Low: remote binding and links/read pane** | GitHub Issues baseline; existing Forgejo for an OSS backend | Confirm workspace→repository; “Open issues”/“New issue”; optionally native list/detail. Provider owns issue data. | Low with an existing service; hosting a new forge is additional work. |
| **2 — Medium: finished server plus adapter** | **Vikunja** first; **Plane Community** for richer Linear-like use; Lific only as an emerging pilot | Native minimal list/detail/create/edit/comment surface, backed by server APIs, with full-tracker deep links. | Vikunja: small SQLite deployment. Plane: much larger multi-service stack. Lific: second binary plus lifecycle/backups. |
| **3 — High: native service/domain/UI** | SANE-owned separate SQLite database and React views; optional **dnd-kit** board | Fully served through sane-app, no tracker runtime; SANE owns schema, persistence, migrations and UI. | Low extra hosting, but ongoing product maintenance and backup responsibility. |

**Agent-only integration is not an in-app tracker.** Direct `gh`, provider MCP, or CLI tools can enable issue operations in chat without implementing a SANE issue panel. Conversely, a useful Issues panel need not expose any agent tools. A native read pane adds more work than link-out; a complete editable board adds more than either. Do not hide these scope differences behind a product name.

## Existing remote issues win on speed; Vikunja wins on reuse

GitHub’s issue service is not open source, although its MIT CLI and official MCP server are. `gh issue` supports list/view/create/edit/comment/close/reopen; explicit `-R [HOST/]OWNER/REPO` and JSON output make a small backend wrapper feasible. Issues remain in GitHub’s database, **not source-code commits**. This is the quickest practical baseline when the user already accepts GitHub. Use argv spawning rather than shell interpolation; confirm the target and privacy before writing. Plain creation links avoid putting sensitive descriptions into URL history. GitHub issue REST lists also include pull requests, which the adapter must exclude. ([CLI](https://cli.github.com/manual/gh_issue), [CLI license](https://raw.githubusercontent.com/cli/cli/trunk/LICENSE), [REST issues](https://docs.github.com/en/rest/issues/issues), [official MCP](https://github.com/github/github-mcp-server))

For an OSS backend, **Forgejo** is the comparable repository-issues choice: v9 onward is GPL-3.0-or-later, with REST APIs and repository-restricted issue token scopes. Gitea’s OSS core is MIT. An already-running forge is economical; deploying an entire forge only for tickets undermines Level 1’s simplicity. Neither automatically inherits GitHub CLI/MCP compatibility. A plain-directory workspace or private backlog for public code can target a separately chosen private issue repository, without pushing code or adding a Git remote. ([Forgejo license](https://forgejo.org/faq/#is-forgejo-licensed-under-the-gpl), [API](https://forgejo.org/docs/latest/user/api/usage/), [token scopes](https://forgejo.org/docs/latest/user/authentication/token-scope/), [Gitea](https://docs.gitea.com/))

**Vikunja is the recommended finished OSS server for this simple scope.** Its server/frontend are predominantly AGPL-3.0-or-later; the desktop component differs. It provides projects, tasks, comments, labels, priorities and multiple views. The official SQLite deployment needs one app container with persistent database and file storage; PostgreSQL adds a database container. Its verified **v2.7.0 release was published October 2, 2026**, and includes official token-authenticated MCP. Integrate against REST `/api/v2`, bind each SANE workspace to a project, and retain the upstream UI for advanced features. Task completion is not automatically a Jira-style configurable status model: validate bucket/status semantics before promising an `in_progress` mapping. ([Release and licensing](https://github.com/go-vikunja/vikunja/releases/tag/v2.7.0), [deployment](https://vikunja.io/docs/full-docker-example/), [features](https://vikunja.io/features/), [REST v2](https://vikunja.io/docs/api-v2/), [MCP](https://vikunja.io/help/mcp/))

**Plane Community is the richer Linear-like alternative**, with work items, cycles, modules, views and pages, under AGPL v3. Community **v1.4.2 was published August 23, 2026**; later branch activity does not establish a newer Community release. The inspected stock Community Compose has 13 service entries, including a one-shot migrator—approximately 12 long-running services. These are topology counts, not resource benchmarks. Commercial is closed-source; its 12-seat Free limit must not be attributed to Community. CE supports PAT-based integration and the official MIT stdio MCP server, but not OAuth application registration. Pin the Community release: shared developer documentation can describe newer/cloud/commercial behavior. ([License](https://github.com/makeplane/plane/blob/preview/LICENSE.txt), [release](https://github.com/makeplane/plane/releases/tag/v1.4.2), [Compose](https://github.com/makeplane/plane/blob/preview/deployments/cli/community/docker-compose.yml), [edition boundaries](https://developers.plane.so/self-hosting/self-hosting-101), [self-host MCP](https://developers.plane.so/dev-tools/mcp-server-self-host))

Lific merits a **pilot, not a production-default endorsement**: Apache-2.0 Rust binary, SQLite, embedded Svelte UI, REST/CLI/MCP, comments and backups. The inspected manifest says 2.10.0, but repository creation was April 3, 2026 and last push October 2; a high version number does not establish maturity. It is a full sidecar app, not an importable React tracker library. Avoid default `init` service installation and agent-config/instruction-writing commands. ([README](https://github.com/VoidNullable/lific), [manifest](https://github.com/VoidNullable/lific/blob/master/Cargo.toml), [license](https://github.com/VoidNullable/lific/blob/master/LICENSE), [metadata](https://api.github.com/repos/VoidNullable/lific))

Prefer **one server per user/team or trust boundary**, mapping workspaces to projects, rather than one stack per worktree. Native SANE list/detail plus “Open in tracker” is the reliable integration plan. Authenticated iframe embedding remains unverified: CSP/X-Frame-Options, cookies, login redirects, asset paths and WebSockets can intervene. OpenProject explicitly restricts frame ancestors to self. CORS is not permission to frame; do not strip security headers as a shortcut. ([OpenProject release CSP](https://github.com/opf/openproject/blob/v17.9.1/config/initializers/content_security_policy.rb))

## Native reuse means primitives, not a hidden complete tracker

**dnd-kit is an MIT React drag-and-drop toolkit**, providing sensors, sortable behavior and accessibility primitives—not issue storage, comments, tenancy, or a finished board. It is a credible reuse choice if a board becomes necessary; begin with a list and status selector. The research snapshot found September 12, 2026 repository activity, but package-family selection and React 19 compatibility still require implementation-time verification. sane-app already uses React 19 and Bun; its domain code already uses `bun:sqlite`, so introducing a Node-native SQLite binding is not inherently necessary. ([dnd-kit](https://github.com/clauderic/dnd-kit), [license](https://github.com/clauderic/dnd-kit/blob/master/LICENSE), [metadata](https://api.github.com/repos/clauderic/dnd-kit); repo: [`packages/sane-app/package.json:11–40`](../packages/sane-app/package.json#L11-L40), [`packages/sane-core/src/repository.ts:343–350`](../packages/sane-core/src/repository.ts#L343-L350))

The proposed native MVP needs an issue UUID, workspace ID, per-workspace display number, title, Markdown description, status (`open`, `in_progress`, `closed`), timestamps and edit revision; priority/labels and comments are small optional additions. Supply list/detail/create/edit/status/search, conflict handling and backup/export. Defer attachments, cycles, epics, dependency graphs, offline synchronization and team RBAC. Serve through authenticated workspace issue routes; participate in App ownership/shutdown. Adding `issues` requires both the navigation type and backend whitelist, not merely a component. ([Navigation contract](../packages/sane-app/src/catalog-contract.ts#L24-L35), [validation](../packages/sane-app/src/catalog.ts#L210-L229), [shell](../packages/sane-app/frontend/app.tsx#L184-L241), [routing boundary](../packages/sane-app/src/bridge.ts#L1298-L1320), [shutdown](../packages/sane-app/src/bridge.ts#L2336-L2400))

Other candidates do not improve this decision. OpenProject Community is a mature broader-PM fallback, not a minimal default; its built-in MCP is Enterprise-only. Huly/Taiga add operational/domain complexity. Standalone Focalboard explicitly lacks maintenance. Current Planka and LibXAI have restricted/source-available licenses. **beads_rust’s “MIT” license includes an OpenAI/Anthropic rider and is excluded**, not treated as ordinary OSS. Go Beads supports Git-free stealth operation but now brings Dolt and agent-task-graph machinery; it is not a JavaScript tracker library. LineAgent has a genuine Rust library but is very young and has anomalous license text. These are exclusions or research leads, not equivalent production recommendations. ([OpenProject MCP gate](https://www.openproject.org/docs/system-admin-guide/integrations/mcp-server/), [Huly operations](https://github.com/hcengineering/huly-selfhost), [Taiga deployment](https://docs.taiga.io/setup-production.html), [Focalboard](https://github.com/mattermost-community/focalboard), [Planka license](https://github.com/plankanban/planka/blob/master/LICENSE.md), [LibXAI license](https://github.com/libxai/libxai-suite/blob/feature/time-tracking/LICENSE), [beads_rust license](https://github.com/Dicklesworthstone/beads_rust/blob/main/LICENSE), [Beads](https://github.com/gastownhall/beads#-git-free-usage), [LineAgent license](https://github.com/deepfounder-ai/LineAgent/blob/main/LICENSE))

## Storage and workspace identity must precede feature expansion

**Use a separate `<dataDir>/issues.db` or OS application-data store**, with private mappings/configuration; keep credentials in an OS vault or protected deployment secrets. Existing App data defaults to package `.data`, so choose an outside-checkout data directory when physically avoiding repositories is important. External servers should use independent volumes; keep deployment/env files, backups, caches and exports outside Git too. Here `.sane` and App `.data` are ignored, but ignore rules do not protect already-tracked files, another repository, or `git add -f`. Cover WAL/SHM and attachments if local ignored storage is selected. ([App defaults](../packages/sane-app/src/app-config.ts#L101-L109), [root ignore](../.gitignore#L1-L12), [App ignore](../packages/sane-app/.gitignore#L1-L10))

**Creating `.sane/issues.db` before SANE initialization currently breaks later initialization**: a nonempty `.sane` without its domain DB is classified as incomplete, and initialization refuses unrelated files. Moreover, `sane.db` validates exact schema objects/definitions: arbitrary issue tables produce `CORRUPT_STORE`. Reusing an initialized canonical `.sane` with a separate DB is conditional on coordination and lifecycle review; supporting uninitialized repositories would require an intentional initialization-contract change. Do not secretly run `sane init` to obtain issue storage. ([`packages/sane-core/src/repository.ts:312–342`](../packages/sane-core/src/repository.ts#L312-L342), [`packages/sane-core/src/schema-upgrade.ts:21–28`](../packages/sane-core/src/schema-upgrade.ts#L21-L28))

Use the existing catalog workspace ID, **shared across linked worktrees**, not branch or current checkout path. Catalog groups Git trees by canonical common Git directory and supports plain directories; a canonical workspace/root binding must survive worktree switches without duplicating backlogs. IDs are App-store local, not globally portable: preserve binding provenance during export/import, and reconcile moves explicitly. Repository `.sane` discovery already resolves the primary checkout, but issue tracking must not require an initialized SANE domain. ([Catalog grouping/pins](../packages/sane-app/src/catalog.ts#L78-L133), [App-store IDs](../packages/sane-app/src/app-store.ts#L9-L20), [canonical discovery](../packages/sane-core/src/repository.ts#L32-L55))

Keep the **adapter contract smaller than the native model**: connection status, list/get/create/update/comment/set-state, pagination and deep links. Remote references should include provider/host, immutable repository or project ID, issue ID, display key and URL. Bind targets server-side; remotes only suggest a target. GitHub `open/closed` need not fabricate `in_progress`; Plane needs configured state IDs, and Vikunja needs explicit completion/bucket mapping. Preserve provider-native fields without demanding a universal PM schema. Foreign links to files, sessions or workstreams can be nullable relation metadata; issue closure must never approve SANE phases or complete jobs.

## Optional harness access should reuse policy, not workflow admission

Both OpenCode and Claude Code support MCP; OpenCode plugins and Claude hooks have different contracts. Start with user-managed direct provider access if sufficient; add a small SANE issue MCP facade only when consistent app/agent workspace policy is valuable. Read/list first, then explicitly approved create/comment/status tools. Hooks can refresh context or invalidate caches—not create tickets on every failure or close them on `Stop`. Existing SANE native caller machinery requires repository discovery/enrollment and cannot be reused unchanged for ordinary directory-workspace issues. ([OpenCode MCP](https://opencode.ai/v2/docs/mcp-servers), [plugins](https://opencode.ai/v2/docs/build/plugins), [Claude MCP](https://code.claude.com/docs/en/mcp), [hooks](https://code.claude.com/docs/en/hooks), [native caller](../packages/sane-cli/src/native-caller.ts#L18-L48))

Resolve tool scope from a validated execution-session binding, not model-supplied paths or the currently browsed workspace: SANE browsing and conversation execution can differ. Backend credentials must never enter frontend bundles, transcripts or tool arguments. Validate configured destinations, constrain redirects/timeouts, check issue membership, and enforce human mutation approval at a trusted boundary. Existing bridge authentication is owner-scoped, **not multi-user RBAC**; UI filters and broad provider tokens do not create tenant isolation. Treat issue text as untrusted input. ([Execution separation](../packages/sane-app/src/catalog-contract.ts#L13-L21), [bridge auth](../packages/sane-app/src/bridge-auth.ts#L12-L37), [Vikunja token scope caveat](https://vikunja.io/help/mcp/))

Fetch on open/manual refresh, with bounded pagination and stale/error indicators; defer webhooks and offline write queues. Unknown create outcomes must not trigger blind retries. GitHub narrow issue permissions and secure `gh` storage need checking because CLI login can fall back to plaintext. ([Issue permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens#repository-permissions-for-issues), [CLI credential caveat](https://cli.github.com/manual/gh_auth_login))

## Conclusion

Choose one authoritative store and one small UI, not a synchronization platform. **Build native for simple local SANE tracking; use Vikunja to reuse a finished OSS tracker; use Plane only for genuinely richer needs.** GitHub/Forgejo links are a useful immediate baseline, not a substitute for a native editor. A tiny service boundary and preserved foreign IDs enable a later provider migration without dual-writing issue lifecycles or designing a plugin marketplace now.

The remaining decision is whether issues belong to one App installation or a shared team service. Before implementation, confirm that ownership choice, the selected release’s API/status permissions, and a backup location. Embedding, real authorization behavior and installed harness compatibility remain unverified; they require separately authorized validation, not assumptions from feature lists. Copyleft distribution/modification obligations also need review for the actual shipped combination.
