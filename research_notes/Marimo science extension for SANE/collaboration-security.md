# marimo scientific extension: collaboration, trust boundaries, and reproducibility

Research date: 2026-10-06. Scope: optional, separately packaged `sane-science`, off by default; editable notebooks under `.sane/`, presented in sane-app's webview. Research only: no application changes, tests, test authoring, browser verification, package installation, or notebook execution. Local repository observations are narrow, read-only observations of the current working copy, not a broad application security audit.

Evidence labels: **Confirmed-docs** = upstream documentation; **Confirmed-source** = inspected upstream or local implementation; **Inference/proposal** = risk assessment or proposed integration behavior, not verified integration behavior. Upstream source snapshot: [main commit c4de758474b59f445ce8b0661d541cb134a78fc3](https://github.com/marimo-team/marimo/commit/c4de758474b59f445ce8b0661d541cb134a78fc3). Latest release discovered through GitHub's release API was [0.25.1, published 2026-10-01](https://github.com/marimo-team/marimo/releases/tag/0.25.1). Living documentation and main source are not automatically a compatibility promise for that release.

## 1. What can agents edit, and how should users and agents coordinate?

### Takeaway

Use Python notebook source as the durable, reviewable artifact, but do not let an agent write the same file that a live UI is saving. Current marimo offers a promising live agent interface, `marimo pair`, including cell-level stale-read protection; the recommended integration is explicit user-controlled editing turns through a pinned, verified live-cell adapter, with a closed-editor/source-patch fallback—not an assumption of conflict-free real-time collaboration.

### Cited Findings

- **Confirmed-docs/source — Python format.** Notebooks are pure Python files. Typical structure is `import marimo`, `__generated_with`, `app = marimo.App()`, cells as decorated functions, and `if __name__ == "__main__": app.run()`. Cell parameters describe references; returned names describe definitions. Cells are serialized in presentation order, not execution order. `app.setup`, `@app.function`, and `@app.class_definition` support reusable top-level code. The editor maintains cell signatures/returns, and direct text editing is supported. [External-editor guide](https://docs.marimo.io/guides/editor_features/watching/); [file-format tutorial source](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_tutorials/fileformat.py).
- **Confirmed-docs — Markdown is also supported, with limitations.** Frontmatter contains metadata and fenced blocks containing the `marimo` class identify executable cells. Markdown notebooks cannot be imported as libraries or run directly as scripts, and do not support reactive tests. `.py` is therefore the stronger MVP interchange format; `.ipynb` is a conversion/export format, not the native editable artifact. [External-editor/Markdown guide](https://docs.marimo.io/guides/editor_features/watching/); [CLI conversion/export reference](https://docs.marimo.io/cli/).
- **Confirmed-docs — Machine checks.** `marimo check [FILES]...` checks/formats notebooks; `--format json` provides machine-readable diagnostics, `--strict` makes warnings nonzero, `--fix` changes files in place, and `--unsafe-fixes` explicitly allows behavior-changing fixes. `marimo run` has a default static check, but running is execution, not a substitute for a non-executing admission workflow. None of these commands were run in this research. [CLI reference](https://docs.marimo.io/cli/).
- **Confirmed-docs/source — Watching is synchronization, not a documented merge protocol.** `marimo edit notebook.py --watch` streams saved external changes to the browser. By default those synced cells become stale rather than executing; `runtime.watcher_on_save = "autorun"` changes that. Watchdog is optional, with polling as fallback. Current source serializes file-change processing, suppresses its own writes, and skips reloads containing Git conflict-start markers. These are useful safeguards, but no reviewed documentation promises preservation of competing unsaved UI edits or conflict-free multi-writer merges. [Watching guide](https://docs.marimo.io/guides/editor_features/watching/); [file-change coordinator](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_session/file_change_handler.py).
- **Confirmed-source — Internal write locks have a bounded scope.** `AppFileManager` uses an `RLock`, invalidates queued autosave generations after foreground writes, and locks notebook-header reads/writes with metadata edits. Its `save()` applies a supplied notebook cell list before persistence. The default filesystem storage calls `Path.write_text`, not an external-writer compare-and-swap protocol. These internal protections should not be presented as enforcement against arbitrary agent writes from another process. [File manager](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_session/notebook/file_manager.py); [filesystem storage](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_session/notebook/storage.py).
- **Confirmed-docs — Live user/agent pairing now exists.** `marimo pair` is upstream's recommended agent collaboration workflow. It supports reading variables, scratchpad exploration, running/adding/removing cells, and UI manipulation. Its CLI guidance says: use cells as the unit of work; scratchpad changes are temporary; persistent edits go through code mode; do not directly edit the notebook file. Cell creation does not run a cell; explicitly request `run_cell`. The documented workflow can use `--token-file`; examples also suggest `--no-token`, which SANE should not copy. [Pairing guide](https://docs.marimo.io/guides/generate_with_ai/marimo_pair/); [CLI pair reference](https://docs.marimo.io/cli/).
- **Confirmed-source — Live edit safeguards exist, but the API is internal.** `marimo._code_mode` explicitly warns that it is an internal, agent-only API with no versioning guarantees. Its context documents atomically applying queued mutations on exit, a default dry-run compile/graph check, and default `StaleCellError` when an agent edits a cell whose current version it has not read. `skip_validation` and `skip_staleness_check` can disable protections. The examined 0.25.1 tag contains `pair execute`, `--token-file`, and `StaleCellError`; this establishes feature presence, not end-to-end interoperability with SANE. [Current context implementation](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_code_mode/_context.py); [0.25.1 context](https://github.com/marimo-team/marimo/blob/0.25.1/marimo/_code_mode/_context.py); [0.25.1 pair CLI](https://github.com/marimo-team/marimo/blob/0.25.1/marimo/_cli/pair/commands.py).
- **Confirmed-docs — Session targeting is not stable across reloads.** Pair instructions prefer known `--file` to resolve the current session; if multiple sessions match, use the intended session explicitly. Session IDs change after page reload. Both `--session` and `--file` together give precedence to `--session`. Instructions explicitly forbid switching targets after authentication/connection errors or unconfirmed execution. [CLI pair reference](https://docs.marimo.io/cli/).
- **Confirmed-docs — Reactive execution has limits.** Running a cell normally reruns descendants; UI interactions can also cause reruns. Object mutations and attribute assignments are not tracked, so cross-cell dataframe/list mutation can produce results outside the reactive dependency model. Deleting cells removes their variables. Lazy execution marks descendants stale, but running a cell with stale ancestors also runs those ancestors. This is not complete purity, determinism, or side-effect isolation. [Reactivity](https://docs.marimo.io/guides/reactivity/); [runtime configuration](https://docs.marimo.io/guides/configuration/runtime_configuration/).

### Inferences

#### Proposed MVP user/agent coordination

1. **Choose one authoritative write path per active notebook.** While open, use a version-pinned `sane-science` adapter around live cell operations if compatibility verification succeeds. Do not combine direct agent file patches, editor autosave, and live code-mode edits. Preserve code-mode validation and stale-read checks. If the live API is unsuitable, require the UI session to save and close before applying source patches; reopen afterward. Basis: [pair instructions](https://docs.marimo.io/cli/) and [file-manager write model](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_session/notebook/file_manager.py).
2. **Explicit editing turns, not a collaboration claim.** Show `User editing`, `Agent proposing`, `Agent applying`, and `Needs reconciliation`. Default agent activity to proposals/inspection; the user grants a bounded apply/run turn and can revoke it. While applying, suspend competing UI source edits and state-changing interactions, or stop applying if they cannot be fenced. Permit passive viewing, but do not imply sliders/buttons are harmless while an agent reads dependent state. A SANE lease is cooperative unless every relevant write path actually honors it. Basis: [reactive UI behavior](https://docs.marimo.io/guides/configuration/runtime_configuration/) and [internal stale-cell guard](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_code_mode/_context.py).
3. **Bind identity before acting.** Record repository ID, canonical checkout, canonical notebook path, server instance/generation, current file hash, intended session, and cell IDs/versions. Never infer a target from whichever tab is active or silently reconnect to another notebook. Re-read cells after a stale error; re-resolve the same authorized file after reload. Basis: [pair target-selection guidance](https://docs.marimo.io/cli/).
4. **Separate source change from execution approval.** Show the changed cells and likely dependent/ancestor execution scope; do not run on save by default. Suggested launch configuration is edit mode, startup autorun disabled, watcher-on-save lazy, module autoreload off/lazy, and lazy reactive execution for expensive/side-effectful notebooks. Explicit Run is still potentially broader than one visible cell. Basis: [watching](https://docs.marimo.io/guides/editor_features/watching/) and [runtime configuration](https://docs.marimo.io/guides/configuration/runtime_configuration/).
5. **For offline source patches, use optimistic publication.** Save a user checkpoint, close the editing session, take the base hash, produce an isolated candidate, propose `marimo check --strict --format json <explicit-candidate>` without `--fix`, recheck the base hash/identity, then publish via confined same-directory atomic replacement. Conflict means retain both candidates for review, not overwrite. Format/fix only the candidate, never the open shared file. This is an integration proposal, not marimo's current storage guarantee. Basis: [check CLI](https://docs.marimo.io/cli/) and [storage implementation](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_session/notebook/storage.py).
6. **Distinguish accepted edits, persisted source, and completed execution.** Journal operation IDs, actor, base/result hash, intended target, execution request/outcome, and kernel generation. If a connection drops, mark the operation unconfirmed and reconcile before retrying; repeated execution can duplicate network/file side effects. Scratchpad success is not a saved scientific result: promote useful logic into cells and record inputs. Basis: [pair's unconfirmed-execution rule](https://docs.marimo.io/cli/) and [untracked mutation behavior](https://docs.marimo.io/guides/reactivity/).

### Gaps

- No reviewed source establishes a conflict-free real-time multi-user protocol, the safety of concurrent unsaved browser drafts plus code-mode transactions, or safe concurrent independent agents. Stale-cell checks are useful but insufficient evidence for those guarantees.
- The live adapter needs exact release/CLI compatibility verification, including autosave durability acknowledgement, session reload behavior, interrupt/revoke semantics, and whether it can constrain individual agents rather than sharing one server credential. Internal API stability is explicitly not promised.
- The safety boundary of `marimo check` against every malicious configuration/parser input was not audited. Treat it as a proposed non-executing static check, not a security scanner or proof that Python is safe; do not import notebook modules merely to inspect them.

## 2. What are the execution, webview, authentication, and dependency trust boundaries?

### Takeaway

A token authenticates access to an interpreter; neither that token, a local listener, a microservice, nor marimo's package “sandbox” confines Python filesystem/network access. Ship only as explicitly trusted local execution for the MVP, with separate web content isolation, strict network/authentication controls, and no automatic trust or dependency installation; use an OS-enforced sandbox/container/VM if untrusted execution is promised.

### Cited Findings

- **Confirmed-docs — Arbitrary Python is an intentional capability.** The upstream security model says cells can execute arbitrary code and should run only from trusted sources or after review. Edit mode statically loads notebook source rather than importing/executing it as a Python module. Before execution, content is sanitized; after execution, outputs are trusted. The current security page says edit startup `auto_instantiate` is disabled by default. `marimo run` treats content as a trusted website and runs the notebook as an application. [Security model](https://docs.marimo.io/security/).
- **Confirmed-docs — Package sandbox is not a security sandbox.** Upstream explicitly states isolated notebook environments do **not** restrict access to files or network. PEP 723 dependencies can be installed automatically; tool-specific metadata may select local editable packages and alternative indexes/sources. Creating a lockfile is a separate step. [Package overview](https://docs.marimo.io/guides/package_management/); [sandbox guide](https://docs.marimo.io/guides/package_management/sandboxes/).
- **Confirmed-docs/source — Opening a project brings extra trust.** marimo respects most configuration from `pyproject.toml`/`.marimo.toml`; notebook inline metadata strips some settings for security. Runtime configuration supports dotenv loading and defaults to `.env` next to the project file, or next to a notebook without a project; `dotenv = []` disables loading. Source supports `server_startup_command` via shell execution during server startup. Thus static notebook loading does not mean arbitrary surrounding project configuration/dependency setup is inert. [Security project-files policy](https://docs.marimo.io/security/); [dotenv behavior](https://docs.marimo.io/guides/configuration/runtime_configuration/); [startup implementation](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/start.py).
- **Confirmed-docs/source — Token is coarse server access.** Edit/new/tutorial authentication is on by default; run mode has no default token according to CLI. The authentication guide documents random edit tokens and deterministic code-derived run tokens unless overridden. Source accepts session cookies, `access_token` query parameters, form passwords, Bearer headers, and Basic auth. Valid edit authentication yields `read` and `edit` credentials for the same generic user, not a demonstrated per-notebook/agent RBAC system. Current cookies store a keyed token hash rather than the raw token and are named by port/base URL. [Authentication guide](https://docs.marimo.io/guides/deploying/authentication/); [CLI defaults](https://docs.marimo.io/cli/); [auth source](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/api/auth.py); [auth backend](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/api/middleware.py).
- **Confirmed-docs — Explicit local/network controls are available.** `marimo edit` defaults to host `127.0.0.1`; `--headless` suppresses browser opening; `--token-password-file` reads a file or stdin; `--base-url`, `--proxy`, and `--allow-origins` support deployment. `--allow-origins '*'` is supported, but should not be used here. `--skip-update-check` disables update lookup. The fact these flags exist does not establish that HTTP CORS settings enforce WebSocket origins. [CLI reference](https://docs.marimo.io/cli/).
- **Confirmed-source — Agent execution is powerful and separately relevant to auth.** `/api/kernel/execute` is edit-authorized; the skew-protection middleware explicitly skips it. Skew protection is a server-version check, not a user/agent permission system. A token capable of reaching this endpoint gives Python execution, not just “read notebook” capabilities. [Execution endpoint](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/api/endpoints/execution.py); [middleware](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/api/middleware.py).
- **Confirmed-docs — Prior authorization bypasses justify reviewing the entire exposed surface.** A terminal WebSocket pre-auth RCE advisory names fixed version 0.23.0; current source checks authentication before accepting terminal WebSockets. A separate unauthenticated `/mpl/<port>/<route>` proxy advisory names fixed version 0.16.4. Do not use these histories to imply a patched release is currently vulnerable; use them to prioritize terminal, visualization proxy, LSP, and auxiliary routes, not just the primary notebook socket. [Terminal advisory](https://github.com/marimo-team/marimo/security/advisories/GHSA-2679-6mx9-h9xc); [current terminal endpoint](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/api/endpoints/terminal.py); [MPL proxy advisory](https://github.com/marimo-team/marimo/security/advisories/GHSA-xjv7-6w92-42r7).
- **Evidence conflict — affected ranges differ between official surfaces.** The security documentation lists the terminal affected range as 0.7.10 through 0.22.x, whereas the GitHub advisory currently says `<= 0.20.4`. Both name 0.23.0 as fixed. The MPL documentation lists 0.9.20–0.16.3, while its advisory's range field says `>0.9.20` with patch 0.16.4. Preserve this discrepancy rather than asserting a precise consolidated range. [Security page](https://docs.marimo.io/security/); [terminal advisory](https://github.com/marimo-team/marimo/security/advisories/GHSA-2679-6mx9-h9xc); [MPL advisory](https://github.com/marimo-team/marimo/security/advisories/GHSA-xjv7-6w92-42r7).
- **Confirmed-docs — Frontend trust changes after execution.** Executed outputs are trusted; custom HTML head injection can load external scripts in run mode, but current docs explicitly say it is not applied in edit mode. This is a reason to isolate notebook-origin content, not a claim that edit mode injects custom head scripts. [Security model](https://docs.marimo.io/security/); [HTML-head guide](https://docs.marimo.io/guides/configuration/html_head/).
- **Confirmed-local-source — SANE has relevant browser-boundary precedents.** `BridgeAuth.browserBoundary` checks Host first and Origin on non-GET/HEAD requests; it deliberately ignores forwarded headers for loopback admission. Terminal WebSocket routing additionally requires exact Origin, refuses query credentials/overrides, and rechecks authorization before upgrading. Login sets HttpOnly/SameSite=Strict cookies, Secure for HTTPS. These are conventions worth extending, not proof that an added science proxy automatically inherits them. [Bridge auth lines 48–75](file:///Users/beto/sane/packages/sane-app/src/bridge-auth.ts); [terminal routes lines 2310–2333](file:///Users/beto/sane/packages/sane-app/src/bridge.ts).

| **P1** | Agent's nominal inspection step executes arbitrary scratchpad code; one coarse token authorizes unrelated operations/notebooks. | Don't give every agent a raw server token. Inventory/allowlist needed HTTP and WS routes; block terminal and unnecessary auxiliary features server-side, not just hide controls. Never trust a caller-supplied URL/port; strip upstream auth/cookies/forwarded headers appropriately; check redirect and base-URL behavior. Basis: [proxy advisory](https://github.com/marimo-team/marimo/security/advisories/GHSA-xjv7-6w92-42r7), [current proxy middleware](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/api/middleware.py). |

Additional proposals: launch by fixed executable plus argument vector (not concatenated shell text); use a minimal environment rather than inherited SANE/agent/API credentials; control HOME/XDG/config loading intentionally; set `dotenv = []`; avoid exposing SANE passwords, database paths, native-agent bridges, or arbitrary filesystem selectors. These reduce accidental exposure but do not stop trusted-local Python from reading accessible host files. Keep a security-supported pinned marimo release and update policy rather than blindly installing `latest` on each open. Basis: [runtime config](https://docs.marimo.io/guides/configuration/runtime_configuration/), [security/update guidance](https://docs.marimo.io/security/).

### Gaps

- Exact Host/Origin validation across marimo's main WebSocket, terminal, LSP, visualization proxy, and agent routes was not fully audited. CORS should not be treated as a verified WebSocket or DNS-rebinding defense. The gateway/native webview must enforce its own documented boundary.
- The applicable webview's iframe CSP/sandbox restrictions, native bridge exposure, navigation permissions, cookie behavior, and handling of cross-origin localhost frames need integration verification by the app-focused worker. “Different port” alone is not a credential isolation claim: cookie scope and same-site rules must be assessed separately.
- No proof was found that a marimo token supports per-user/per-agent/per-notebook scopes or read-only scratchpad execution. Logout/revocation semantics for upstream signed cookies also need a pinned-version assessment.
- No particular Docker/VM/OS sandbox profile was evaluated. `--untrusted` for remote notebook handling invokes a Docker path according to CLI, but that does not prove a SANE-specific sandbox safely constrains mounts, network, resources, identities, or local file execution.

## 3. How should lifecycle, `.sane` storage, artifacts, and reproducibility work?

### Takeaway

Keep durable scientific source/manifest/provenance separate from runtime environments, tokens, caches, and large outputs. The scientific extension must own launch-to-teardown lifecycle and explicitly target hidden `.sane` paths; killing one server PID, relying on disconnect defaults, or recursively scanning the repository is insufficient.

### Cited Findings

- **Confirmed-docs/source — Session/server lifetime is configurable.** Edit mode's `--session-ttl` defaults to no automatic session close, whereas run mode documents a 120-second default; `--timeout` provides server inactivity shutdown. Current session-manager shutdown cancels pending launches, closes sessions, and stops app hosts, LSP and watchers. [CLI lifecycle flags](https://docs.marimo.io/cli/); [session manager](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/session_manager.py).
- **Confirmed-docs/source — Server and kernel are not one process group.** Edit mode normally launches a kernel subprocess; the source contrasts this with thread-based run mode. Kernel process cleanup attempts process-group termination; upstream utility comments state the kernel becomes its own group/session leader. The reactivity guide confirms interrupt targets the kernel group on Unix and explicitly describes how a subprocess started with `start_new_session=True` survives that interrupt. Killing just the outer server group cannot be assumed to collect separate kernel groups or escaped descendants. [Kernel manager](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_session/managers/kernel.py); [process helpers](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_utils/subprocess.py); [interrupt documentation](https://docs.marimo.io/guides/reactivity/).
- **Confirmed-source — Cleanup is best-effort, not evidence of hostile-process containment.** `try_kill_process_and_group` returns if the direct process is already finished; its asynchronous escalation similarly checks direct-process completion. Notebook descendants could therefore require additional owner reconciliation even if their leader is gone. Terminal source creates a separate PTY child and primarily signals/reaps that child; extra process trees need explicit consideration. This is an inferred integration risk from code paths, not a reproduced defect. [Process helpers](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_utils/subprocess.py); [terminal source](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/api/endpoints/terminal.py).
- **Confirmed-local-source — SANE already distinguishes uncertain termination.** `ClaudeRunService` launches detached children, signals the owned group and direct child, escalates SIGTERM/SIGKILL, waits for both child exit and group disappearance, and requires reconciliation if termination is unconfirmed. Reuse the ownership/reconciliation principle, not an assumption that its single-group algorithm fits marimo's multi-group topology. [Run service lines 197–217, 339–354](file:///Users/beto/sane/packages/sane-app/src/claude-run-service.ts).
- **Confirmed-source — Hidden-directory discovery hazard.** marimo's directory scanner explicitly skips every entry whose name starts with `.` and skips symlinks. Thus repository-root home/gallery scanning will omit `.sane`; this does not show that an explicitly supplied notebook path under `.sane` is unsupported. Its workspace can be rooted at an explicit directory, and exact-path opening is documented. Recursive cache CLI discovery also documents skipping dot-folders. ### Inferences

#### Proposed layout and reproducibility contract

The following is a proposal, not an existing SANE namespace or upstream-required layout:

```text
<primary-checkout>/.sane/science/<project-id>/
  manifest.json                    # canonical checkout/data references, notebook IDs
  pyproject.toml + uv.lock          # OR per-notebook PEP 723 + .py.lock; choose one policy
  notebooks/<notebook-id>.py        # durable user/AI-editable source
  src/                             # reviewed scientific helper code, if needed
  data-manifest.json               # inputs, versions, checksums, origin/access policy
  runs/<run-id>/provenance.json     # source/lock/input hashes, args, seeds, environment
  runs/<run-id>/artifacts/          # bounded, deliberately retained outputs

<sane-science-private-runtime-dir>/<instance-id>/
  environment/cache/logs           # not repository artifacts; bounded retention
  token/ownership-record          # private, never committed or returned in notebook UI
```

- Put science in a separate namespace after successful SANE initialization; do not create `.sane/science` before core initialization or place virtualenvs under a confined workstream artifact tree. Virtualenv symlinks and shared cache hardlinks can conflict with existing tree validation when placed inside its scope. The exact science registration schema still needs owner design. Basis: [initialization](file:///Users/beto/sane/packages/sane-core/src/repository.ts), [artifact confinement](file:///Users/beto/sane/packages/sane-core/src/confined-lifecycle-filesystem.ts).
- Distinguish primary `.sane` location from the selected execution checkout. Bind both in the manifest, and define the notebook's cwd explicitly; use notebook-directory helpers or explicit data-root arguments, not ambiguous shell cwd. Avoid importing helper files from a different worktree unintentionally. Basis: [primary/invocation checkout mapping](file:///Users/beto/sane/packages/sane-core/src/repository.ts), [runtime Python path behavior](https://docs.marimo.io/guides/configuration/runtime_configuration/).
- Make `.sane` notebook discovery explicit: SANE enumerates its registered notebook IDs and passes exact paths; do not depend on marimo root discovery or broad hidden-directory globs. Existing marimo output locations may remain adjacent to source; classify/ignore them deliberately rather than assume a generic redirect flag exists. Basis: [scanner](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/files/directory_scanner.py), [snapshot paths](https://docs.marimo.io/guides/exporting/sessions/).
- Version source, manifests, reviewed helper code, and locks selectively; do not add all of `.sane` to Git. Keep database/locks/tokens/private datasets/temporary artifacts out of version control. Review `.gitignore`, backup, cleanup and agent-search behavior for hidden paths explicitly. Reproducibility records should include source hash, marimo/Python/backend version, exact dependency lock hash, platform/native-library details, dataset hash/version/query, input parameters, RNG seeds, actual execution cwd, execution time/status, and output hashes. Basis for the need: [separate lockfiles/data sharing](https://docs.marimo.io/guides/package_management/sandboxes/) and [untracked mutations](https://docs.marimo.io/guides/reactivity/).
- Treat notebook outputs as possibly sensitive and active HTML, not interchangeable with source. Record provenance for retained outputs, bound size/retention, review before sharing, and distinguish fresh execution from cache/session preview. Reactive DAG consistency does not establish scientific reproducibility with changing external data, random values, mutable state, native numerical libraries, or network services. Basis: [reactivity limits](https://docs.marimo.io/guides/reactivity/), [session snapshots](https://docs.marimo.io/guides/exporting/sessions/), [trusted executed outputs](https://docs.marimo.io/security/).

#### Proposed lifecycle ownership

- Extension-off state means no Python process, no listener, no notebook enumeration/execution, no install/download, no update check, and no notebook watcher. Explicit enable/open creates one owned instance with workspace/notebook scope and a bounded startup deadline.
- Separate states: `disabled`, `starting`, `ready`, `busy`, `stopping`, `stopped`, `failed`, `cleanup-unconfirmed`. Track executable/version, canonical paths, process-start identity, known server/kernel/helper ownership, listener, instance generation and current authorization. Never kill a reused PID merely because a stale record exists.
- On disable, app exit, workspace close/switch, logout, explicit Stop, startup failure, or parent crash recovery: revoke operations/attachments, request orderly marimo/session shutdown, wait a bounded interval, then terminate all **owned** groups/helper processes and confirm listeners/resources are gone. Explicit TTL and inactivity timeout are backstops, not the ownership algorithm.
- If using a container/VM, stop the owned container/VM to collect nested groups and enforce quotas; ordinary host-group teardown is not a hostile-code containment mechanism. For trusted host execution, document unsupported escaped/daemon descendants and show cleanup-unconfirmed rather than claiming success. Enforce concurrency, memory/disk/output limits where supported and avoid freezing sane-app's event loop while waiting.

These are proposals informed by [marimo's separate kernel/helper lifecycle](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_server/session_manager.py), [kernel-group utilities](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_utils/subprocess.py), and [SANE's owned-run reconciliation convention](file:///Users/beto/sane/packages/sane-app/src/claude-run-service.ts).

#### Proposed verification checklist — not executed or authored as tests

- **Disabled/install boundary:** default startup performs no Python spawn/listen/scan/download. Enablement consent separates project trust, dependency installation, host execution and output sharing. Reviewed effective configuration cannot silently enable autorun/startup shell commands/dotenv or an unwanted package index.
- **Editor/source coordination:** `.sane` exact-path open/save/reload works; UI drafts survive declined agent proposals; same-cell user changes cause agent reconciliation rather than silent overwrite; delete/reorder/config/package-header edits behave correctly; interrupted autosave and process death recover source; watcher atomic-replace/polling events converge; live pair changes are confirmed durable before recording success.
- **Reactive execution:** startup and watched-file changes do not execute without approval under chosen config; stale ancestors/descendants are surfaced; slider changes, side-effect cells, untracked mutation and scratchpad promotion are understood; run cancellation/unconfirmed response does not cause an automatic duplicate retry.
- **Authentication/network:** invalid/no token is denied on all exposed HTTP/WS paths including kernel execution, terminal, LSP and visualization proxy. Wrong/missing/null Origin, wrong Host, encoded path/base-URL bypasses, arbitrary upstream ports/URLs and remote forwarding fail closed. Validate IPv4/IPv6 listeners, loopback direct access and the webview's actual cookie/origin model. No credential appears in logs, command arguments, URLs, agent prompts or exported artifacts.
- **Webview isolation:** executed HTML/JS, external images/assets, links, popups, downloads and navigation cannot access sane-app parent/native APIs or unexpectedly send credentials. Verify an isolated origin rather than relying on a path prefix. A same-user Python kernel's ability to reach local SANE services must be explicitly included in the trust model.
- **Lifecycle:** graceful and forced close, timeout, interrupt, kernel restart, browser disconnect/reconnect, app crash, install cancellation/failure, child ignoring SIGTERM, detached child/new session, LSP/terminal/visualization helpers, port reuse and PID reuse. Confirm no owned orphan listeners/processes; report cleanup-unconfirmed on uncertain outcomes.
- **Path/storage:** traversal, URL encoding, symlink/hardlink/ancestor swaps, save-as/rename, imported local package paths and cross-worktree target changes. `.sane` hidden discovery, Git ignoring, explicit-path static checks/exports, cache retention and lifecycle-tree compatibility all need targeted verification.
- **Reproducibility:** replay from source plus lock plus input manifest in a clean process without relying on prior live memory/cache; changed input hashes invalidate claims; dependency/network actions are visible; outputs are classified and bounded; provenance records both successful and failed/cancelled runs.

Checklist rationale sources: [security model](https://docs.marimo.io/security/), [pair CLI](https://docs.marimo.io/cli/), [watching](https://docs.marimo.io/guides/editor_features/watching/), [dependency locks](https://docs.marimo.io/guides/package_management/sandboxes/), [process utilities](https://github.com/marimo-team/marimo/blob/c4de758474b59f445ce8b0661d541cb134a78fc3/marimo/_utils/subprocess.py), [SANE filesystem scope](file:///Users/beto/sane/packages/sane-core/src/confined-lifecycle-filesystem.ts).
