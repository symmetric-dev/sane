# Fully local shared Chromium alternatives

## Which architectures best satisfy one visible browser controlled by a human and AI?

### Takeaway

For an in-app experience on macOS, the two strongest middle grounds are **native embedded Chromium with a narrowly scoped automation bridge** (best interaction fidelity, larger integration) and **a locally owned Chromium process streamed into the existing app with CDP input** (less shell disruption, more input/rendering compromises). A separate headed Chrome window is the simplest shared-session baseline, but does not meet “inside the app” literally. These are architectural judgments, not measured benchmarks. [Electron WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view); [CDP Page protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl); [CDP Input protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl)

### Cited Findings

- **Shared browser is different from shared credentials.** Playwright can attach over CDP to an existing Chromium instance and access its existing default context and pages. Launching a second browser or importing storage state is not the same connection pattern. Its persistent context stores cookies/local storage in a user-data directory, and that directory cannot be used by multiple browser instances simultaneously. [Playwright BrowserType](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)
- **Local headed Chromium + automation:** Chrome DevTools MCP controls a live Chrome browser using Puppeteer; its default is headed, and `--browser-url`/`--ws-endpoint` attach rather than launching another instance. Browser-use documents `cdp_url` for the same purpose, and Playwright MCP documents `--cdp-endpoint`. None of these attachment APIs is itself an app embedding/view API. [Chrome DevTools MCP README](https://github.com/ChromeDevTools/chrome-devtools-mcp); [configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md); [browser-use browser settings](https://docs.browser-use.com/customize/browser-settings); [Playwright MCP](https://github.com/microsoft/playwright-mcp)
- **DOM/semantic automation is independent of pixel transport.** Playwright MCP uses structured accessibility snapshots rather than requiring screenshots/vision; Chrome DevTools MCP additionally supplies console, network and performance inspection. Playwright `connectOverCDP` is Chromium-only and explicitly documented as “significantly lower fidelity” than the native Playwright protocol connection. This warning concerns automation capability/compatibility, not the browser's image quality. [Playwright MCP](https://github.com/microsoft/playwright-mcp); [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp); [Playwright connectOverCDP](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)
- **Electron embeds actual Chromium page content.** A `WebContentsView` displays a `WebContents` as a child view in a desktop window. Multiple views can be arranged in one window. An existing Electron `WebContents` can be adopted, but may be presented in only one `WebContentsView` at a time. These docs do not describe adopting an arbitrary external Chrome tab/process. [WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view)
- **Electron offers in-process CDP without a public TCP port.** `webContents.debugger` is an alternative transport for Chrome's remote debugging protocol; it supports attaching, receiving protocol messages and sending commands. Its documented detach event occurs when the WebContents closes or DevTools is invoked for that WebContents. A `persist:` session partition shares persistent state among pages in that app using that partition. [Debugger](https://www.electronjs.org/docs/latest/api/debugger); [Session source documentation](https://github.com/electron/electron/blob/main/docs/api/session.md)
- **CEF is a genuine embedding option, not a hosted service.** It provides C/C++ APIs and binary distributions for embedding Chromium in native applications, supports Windows/macOS/Linux, and supports off-screen rendering as well as native hosting. Its documented macOS browser handle is `NSView*`; macOS requires a particular app-bundle/helper-process structure, and the multithreaded message-loop option is only available on Windows/Linux. [CEF README](https://github.com/chromiumembedded/cef); [CEF general usage](https://chromiumembedded.github.io/cef/general_usage)
- **CEF also has a local protocol bridge.** `CefBrowserHost::SendDevToolsMessage`, `ExecuteDevToolsMethod` and observer APIs do not require an active DevTools frontend or remote-debugging session. The header warns that changes to global browser state from one session may not be reflected in other session UIs. [CEF browser API header](https://github.com/chromiumembedded/cef/blob/master/include/cef_browser.h)
- **CDP page streaming is real page pixels, not DOM recreation.** `Page.startScreencast` emits compressed images through `Page.screencastFrame`; supported formats are JPEG/PNG, with quality, maximum dimensions and every-Nth-frame controls. Frames carry metadata and an acknowledgement `sessionId`; the frontend sends `Page.screencastFrameAck`. These APIs are experimental. Current tip-of-tree also exposes `maxFramesInFlight` and `sendLastFrame`, but availability must be checked against the shipped Chromium version. [Page protocol source](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl)
- **CDP provides interactive input separately.** `Input.dispatchMouseEvent` supports press/release/move/wheel and takes coordinates relative to the main frame viewport in CSS pixels. `dispatchKeyEvent` includes key/code/modifier information; experimental `insertText` and `imeSetComposition` address text/IME cases. [Input protocol source](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl)
- **VNC/noVNC is desktop transport, not DOM automation.** noVNC is a JavaScript VNC client/library using WebSockets; a VNC server is still necessary, with websockify bridging WebSockets to TCP when needed. It supports desktop scaling/resizing, local cursor rendering and clipboard transfer. Its own quickstart shows loopback-only binding. [noVNC README](https://github.com/novnc/noVNC)
- **Linux virtual displays are a substantiated deployment path.** Playwright documents Xvfb for Linux headed execution. Pairing a Linux virtual display with a VNC server and embedding noVNC is therefore a different stack from CDP page streaming: the human sees the desktop containing the browser, while CDP remains the DOM/control channel. The pairing is an architectural inference from these primitives, not a Playwright turnkey feature. [Playwright headed execution](https://playwright.dev/docs/ci#running-headed); [noVNC server requirements](https://github.com/novnc/noVNC#server-requirements)
- **macOS VNC has a materially broader capture/control boundary.** Apple describes Screen Sharing as viewing the Mac desktop and controlling files/windows/apps, including restarting the computer; VNC viewers can control it with a configured password. It is not documented there as a per-browser embedded surface. Docker Desktop, by contrast, runs containers in a Linux VM; a local Linux browser desktop in Docker is local to the device, but is not the same browser as the person's native Mac Chrome. [Apple Screen Sharing](https://support.apple.com/guide/mac-help/turn-screen-sharing-on-or-off-mh11848/mac); [Docker VMM](https://docs.docker.com/desktop/features/vmm/)

### Inferences

**Practical ranking for this requirement, not an empirical latency comparison:**

| Rank / option | Visual fidelity and latency | DOM automation and live state | Scope / macOS suitability | Privacy/security tradeoff |
|---|---|---|---|---|
| **1. Embedded Chromium: Electron WebContentsView, or CEF for a native shell** | Expected best in-app interaction: actual native browser surface, no image encode/decode relay | Same WebContents/browser instance for human and AI; local CDP bridge; own persistent app profile | Medium-to-large if shell already matches framework; large if migrating shell; CEF macOS helper/message-loop packaging is substantial | Avoids raw CDP network port when using in-process bridge; app must securely host arbitrary web content and ship browser security updates |
| **2. Owned local Chromium + CDP screencast/Input in existing app** | Real page rendering, but image compression/scaling and input forwarding add latency/complexity; PNG vs JPEG is a bandwidth/fidelity choice | Excellent shared-tab identity if stream and automation attach to the exact same target; retain DOM tools | Medium implementation; attractive on macOS without introducing Linux desktop infrastructure; does not require full shell migration | Browser/profile stay local; localhost CDP and viewer gateway remain highly privileged |
| **3. Local Steel browser/viewer as an implementation accelerator** | Concrete JPEG/canvas live viewer exists; performance is unmeasured | CDP automation and local tab viewer provided in open repository | Potentially less custom code, but requires integrating/service-hardening and verifying current release behavior; documented native Mac and arm64 Docker paths | Apache-2.0 core; audit default networking/telemetry and viewer authorization rather than assuming local means hardened |
| **4. Local Linux VM/container + headed Chrome + Xvfb/VNC/noVNC + CDP** | Can show full browser chrome and desktop dialogs; remote-display scaling/encoding; VM adds overhead | CDP keeps DOM automation; both parties share the browser in that desktop | More services, process supervision and packaging; works locally on Mac through Linux VM, but is Linux UX rather than native Mac browser/profile | Stronger separate-desktop boundary if configured well; more listening services and file/clipboard bridges |
| **5. VNC of the native Mac desktop + CDP** | Shows native Chrome UI, but captures desktop scope and competes with local desktop focus | Same native browser possible | Awkward default for a single in-app browser pane; OS sharing setup; per-window isolation not established | Broad desktop exposure/control makes this least attractive here |
| **Baseline, outside strict requirement: separate native headed Chrome + CDP** | Native Chrome quality and interaction, no streaming cost | Easiest exact-session shared control | Smallest implementation, excellent native Mac fit, but **outside app** | Dedicated automation profile and controlled CDP access still required |

Sources behind these judgments: [Electron view](https://www.electronjs.org/docs/latest/api/web-contents-view), [debugger](https://www.electronjs.org/docs/latest/api/debugger), [security](https://www.electronjs.org/docs/latest/tutorial/security); [CEF general usage](https://chromiumembedded.github.io/cef/general_usage); [Page](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl), [Input](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl); [Steel README](https://github.com/steel-dev/steel-browser), [viewer implementation](https://github.com/steel-dev/steel-browser/blob/main/api/src/templates/live-session-streamer.ejs); [noVNC](https://github.com/novnc/noVNC); [Apple Screen Sharing](https://support.apple.com/guide/mac-help/turn-screen-sharing-on-or-off-mh11848/mac); [Docker VM](https://docs.docker.com/desktop/features/vmm/).

- **Recommendation without inspecting SANE:** pick rank 2 if preserving the current app shell is the priority; pick rank 1 if the app already has a suitable Electron/native surface or native browser feel outweighs embedding effort. These choices do not require Browserbase. Do not turn “all local” into a needless container requirement. [Electron view](https://www.electronjs.org/docs/latest/api/web-contents-view); [Page protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl)
- A page screencast should not be sold as a full browser UI stream: address bar, tab strip and browser/OS dialogs are outside the page-domain contract. Build app-level tabs/address bar and explicit download/upload/dialog handlers. Native embedding also requires browser-shell UX rather than supplying all of Chrome's product UI automatically. [Page protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl); [Electron WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view)
- A canvas viewer needs: newest-frame/backpressure policy; CSS-pixel and device-scale mapping; resize ownership; keyboard modifiers/shortcuts; text composition; focus; selection/clipboard; drag/drop; reconnect; tab/popup routing. A visually plausible JPEG viewer alone is not equivalent to a native interactive browser. The underlying APIs expose the pieces, not a finished viewer. [Page protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl); [Input protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl); [Steel viewer example](https://github.com/steel-dev/steel-browser/blob/main/api/src/templates/live-session-streamer.ejs)
- VNC can carry full desktop UI, but it does not improve DOM access; use it only if full browser chrome/native dialogs justify the larger desktop stack. On macOS do not assume Linux Xvfb is a drop-in replacement for an isolated Cocoa desktop. The retrieved Apple documentation substantiates desktop sharing, not a private virtual Cocoa display per browser. [Apple Screen Sharing](https://support.apple.com/guide/mac-help/turn-screen-sharing-on-or-off-mh11848/mac); [Playwright Linux Xvfb](https://playwright.dev/docs/ci#running-headed)

### Gaps

- No browser verification or tests were performed; no latency, FPS, CPU or rendering-parity numbers are claimed.
- Compatibility of particular websites, OAuth/SSO, passkeys, DRM/proprietary codecs, browser extensions and IME with each embedding/streaming route requires evaluation against the exact release. Chromium engine identity alone does not establish full Google Chrome product parity.
- Exact SANE shell, current engine and integration cost are deliberately not investigated here. No claim is made that a given Electron/CEF route is a small patch to SANE.
- Background/occluded/minimized headed-tab screencast behavior, GPU workloads and performance under Retina scaling remain unverified.

## How should local attachment, profile sharing, target selection and concurrency work?

### Takeaway

Own one browser process/profile and explicitly route both the app viewer and agent to the same target. Preserve the user's already-attached Chrome DevTools MCP session: a separate app browser gets its own profile/endpoint and connection, while intentional sharing of an existing session requires explicit target ownership and a human/AI control lease. [MCP advanced usage](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [CDP Target protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl)

### Cited Findings

- **Chrome 136 restriction:** `--remote-debugging-port` and `--remote-debugging-pipe` are no longer honored for Chrome's default data directory. Use `--user-data-dir` pointing to a **non-standard directory**. Google recommends Chrome for Testing for automation and says it continues to respect existing behavior. A different `--profile-directory` inside the normal default user-data root is not what the requirement specifies. [Chrome announcement, March 17 2025](https://developer.chrome.com/blog/remote-debugging-port)
- **Important current alternative, not a contradiction:** Chrome DevTools MCP now documents Chrome 144+ automatic attachment: enable remote debugging through `chrome://inspect/#remote-debugging`, use `--autoConnect`, and approve the connection in Chrome. With multiple active profiles it chooses Chrome's default profile, with access to all its open windows. The Chrome 136 announcement addresses command-line flags; this later permission-based workflow is separate. [MCP advanced usage](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md)
- **Do not casually close someone else's running Chrome.** The manual MCP guide describes closing running Chrome before its example launch, but Playwright separately documents that one user-data directory cannot belong to multiple browser instances. For a new app-owned session, the meaningful safety boundary is a separate app-owned profile/process rather than reusing the personal root. [MCP manual attachment](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [Playwright persistent context](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context)
- **CDP attachment details:** MCP supports `--browser-url=http://127.0.0.1:9222` or an explicit browser WebSocket endpoint with `--ws-endpoint`. `/json/version` exposes `webSocketDebuggerUrl`. An explicit endpoint identifies the browser instance; it does not by itself establish which tab the app should show. [MCP configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)
- **Loopback is not authentication.** Chromium's remote-debugging server implementation attempts `127.0.0.1` then `::1`; MCP warns that any application on the machine can connect to the debugging port and control the browser. Thus a loopback endpoint must still be treated as privileged. [Chromium remote-debugging server source](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/devtools/remote_debugging_server.cc); [MCP security warning](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md)
- **Target identity has first-class support.** `Target.getTargets` enumerates targets; `Target.attachToTarget(targetId, flatten)` returns a CDP session ID. Target created/destroyed/info-changed events support tracking live tabs. `Target.activateTarget` focuses a target. [Target protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl)
- **MCP routing is version-sensitive but current defaults help.** Current Chrome DevTools MCP uses explicit `pageId` routing by default for page-scoped tools, including shared-server concurrency; `--no-page-id-routing` restores selected-page-only behavior. Multiple independent MCP servers using the same default persistent profile can conflict; `--isolated` gives them separate temporary profiles, which deliberately does **not** preserve a common shared live browser. [MCP concurrent sessions](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)
- **Attachment can alter state even without intentional navigation.** Playwright now documents `connectOverCDP(..., {noDefaults:true})` to avoid overriding downloads, focus emulation and media preferences in the default context; availability depends on installed Playwright version. Non-Playwright browser launch arguments can also impair some Playwright features. [Playwright connectOverCDP](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)
- **browser-use documentation needs care:** its browser settings document `cdp_url`, `headless`, `keep_alive`, `no_viewport` and profile controls, but also suggests `Browser.from_system_chrome()`/closing Chrome. Do not turn that suggestion into advice to bypass Chrome 136 or open an already-used personal profile. Prefer attachment to the explicitly owned running browser. [browser-use settings](https://docs.browser-use.com/customize/browser-settings); [Chrome restriction](https://developer.chrome.com/blog/remote-debugging-port)

### Inferences

Recommended control-plane contract (application design, not a turnkey MCP guarantee):

1. **Browser supervisor:** start one app-owned headed Chromium with a persistent non-default profile; choose a dedicated available local port and retain process ownership/lifecycle. The pre-existing MCP browser remains untouched unless the user explicitly chooses it. The same profile on disk is persistence, not a mechanism for two concurrent browser processes. [Chrome restriction](https://developer.chrome.com/blog/remote-debugging-port); [Playwright profile constraints](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context)
2. **Target registry:** maintain stable app-tab-ID → actual CDP `targetId` → attached `sessionId`; separately map MCP `pageId` because it is an adapter-level identifier, not something to assume equals the raw target ID. Only offer app-owned/authorized page targets, not arbitrary browser internals/workers. Both displayed stream and agent request resolve through the same registry. [Target protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl); [MCP page routing](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md)
3. **One input broker, human priority:** expose an explicit human/AI owner lease per visible tab, Pause/Take over/Resume, and serialize mutating actions. User input cancels/suspends the agent's next action; release stuck keys/buttons and take a fresh DOM snapshot after handoff. Separate tabs can run independent actions, but browser-global changes/profile operations need broader locks. CDP provides targeting and events, not a documented human-vs-agent transactional lock. [Input protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl); [Target protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl); [CEF warning about shared global state](https://github.com/chromiumembedded/cef/blob/master/include/cef_browser.h)
4. **Avoid selected-page races:** explicit page IDs prevent accidental cross-session tab selection, but do not prevent two agents from typing into the same field or one controller navigating while the other clicks. Check target identity and observation freshness immediately before a mutation; avoid assuming “current tab” means the same thing across transports. [MCP routing](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [Target protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl)
5. **One viewport owner:** in native embedding use the visible view size; in streamed embedding negotiate the app pane size and map coordinates to main-frame CSS pixels. Do not let automation silently impose a different viewport or repeatedly focus another tab while the user interacts. [Input CSS coordinates](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl); [Playwright noDefaults](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)
6. **Secure the local bridge:** prefer stdio/Unix-domain IPC or in-process Electron/CEF APIs; if a viewer WebSocket/HTTP gateway is needed, bind host-side ports to loopback and validate origin/session authorization. Do not expose raw browser CDP to untrusted website JS; forward only authorized targets and operations. For Docker use host publication such as `127.0.0.1:3000:3000`, not an unqualified published port. This is a recommended hardening design, not a claim these upstream examples implement it. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security); [MCP local-control warning](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [noVNC localhost binding example](https://github.com/novnc/noVNC)

### Gaps

- The installed version, actual endpoint, owning process and target policy of the user's other Chrome DevTools MCP session were not inspected, by design. Do not redirect or reconnect that server on the basis of these notes.
- A broker cannot truly serialize all manual input if the user also interacts with an unmanaged external native Chrome window; product-level pause affordances are needed, or restrict human input to the app-controlled surface.
- No claim is made that browser-use, Playwright, Electron debugger and MCP can all attach concurrently without version-specific side effects. Choose one authoritative automation layer first; use extra observational connections only where needed and validate compatibility later.

## Which packaged alternatives are genuinely local, and what privacy/licensing limits matter?

### Takeaway

Browserbase Live View demonstrates the UX but the retrieved documentation describes a managed browser platform, not an all-local browser engine distribution. Steel is substantiated as a locally runnable Apache-2.0 browser API **with actual interactive viewer source**; Browserless is substantiated as self-hostable but its current licensing and premium live/hybrid feature split mean it should not be presented as a free permissive drop-in equivalent. [Browserbase overview](https://docs.browserbase.com/introduction/what-is-browserbase); [Live View](https://docs.browserbase.com/features/live-view); [Steel](https://github.com/steel-dev/steel-browser); [Browserless](https://github.com/browserless/browserless)

### Cited Findings

- **Browserbase:** its overview describes fleets of headless browsers with isolated sessions and global infrastructure. Live View supports human click/type/scroll, iframe embedding and a separate URL for each tab obtained from the session debug API. The local app embedding an iframe does not make that managed browser local. No supported self-hosted all-local Browserbase server distribution was established in the sources retrieved. [Browserbase overview](https://docs.browserbase.com/introduction/what-is-browserbase); [Live View](https://docs.browserbase.com/features/live-view)
- **Steel local execution is explicit.** The repository documents a combined API/UI Docker image (`ghcr.io/steel-dev/steel-browser`), local UI at `/ui`, native Node development with local Chrome paths including macOS, and Apple Silicon Docker configuration. SDKs can point `baseURL`/`base_url` at localhost; browser control uses Puppeteer/CDP with Playwright/Selenium integration. [Steel README](https://github.com/steel-dev/steel-browser)
- **Steel viewer is not merely a cloud marketing assertion.** `SessionViewer` embeds the session `debugUrl` and implements clipboard bridging. The API's `live-session-streamer.ejs` contains tab discovery via WebSocket, tab activation/update handling, base64 JPEG decoding into a canvas, coordinate scaling, and keyboard/mouse event forwarding gated on interactive mode. This establishes an open local viewer implementation; it does not establish native-browser interaction parity or a measured latency guarantee. [UI SessionViewer](https://github.com/steel-dev/steel-browser/blob/main/ui/src/components/sessions/session-viewer/session-viewer.tsx); [interactive stream template](https://github.com/steel-dev/steel-browser/blob/main/api/src/templates/live-session-streamer.ejs)
- **Steel licensing:** the top-level license is Apache-2.0. That supports evaluating/reusing the local implementation without assuming Steel Cloud terms apply to the open repository; dependencies and bundled browser notices still need normal redistribution review. [Steel LICENSE](https://github.com/steel-dev/steel-browser/blob/main/LICENSE)
- **Browserless local execution is explicit.** Its README provides `ghcr.io/browserless/chromium`, local WebSocket connections, a debug viewer and ARM64/Apple Silicon support. However it labels “hybrid automations” with streaming live sessions and persistent sessions as premium/cloud/Enterprise features. It also offers Enterprise Docker self-hosting. Do not conflate general debug viewer availability with unrestricted free production hybrid streaming. [Browserless README](https://github.com/browserless/browserless)
- **Browserless licensing is not permissive Apache/MIT.** Current README states `SSPL-1.0 OR Browserless Commercial License` and says proprietary commercial/closed-source CI use needs a commercial license. That is the vendor's stated position, not an independent legal opinion; evaluate license terms before embedding it in a proprietary app. [Browserless licensing](https://github.com/browserless/browserless#-licensing)
- **Core framework/tool licenses:** Electron's license is MIT; CEF describes itself as BSD-licensed; browser-use describes its Python library as MIT; Chrome DevTools MCP and Playwright are Apache-2.0; noVNC is mainly MPL-2.0 with its license document covering details. Those are component licenses, not blanket clearance for every bundled codec, browser build or dependency. [Electron LICENSE](https://github.com/electron/electron/blob/main/LICENSE); [CEF README](https://github.com/chromiumembedded/cef); [browser-use README](https://github.com/browser-use/browser-use); [Chrome MCP repository](https://github.com/ChromeDevTools/chrome-devtools-mcp); [Playwright LICENSE](https://github.com/microsoft/playwright/blob/main/LICENSE); [noVNC](https://github.com/novnc/noVNC)
- **Local browser is not fully local inference.** browser-use explicitly allows a local browser and local model through Ollama; API inference/hosted browsers are separate paid services. A cloud model still receives whatever page data/screenshots the agent sends, even when Chromium and CDP are on the Mac. [browser-use local/model distinction](https://github.com/browser-use/browser-use)
- **Telemetry and secondary requests need explicit treatment.** Chrome DevTools MCP usage statistics are on by default; disable with `--no-usage-statistics`. Performance tools may send trace URLs to Google CrUX; use `--no-performance-crux`. Update checks can be disabled with `CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS`. Browser-use's current config source defaults `ANONYMIZED_TELEMETRY` to true and makes `BROWSER_USE_CLOUD_SYNC` default to that setting; set both false for an explicitly local configuration, then audit the pinned release rather than assuming this exhausts every egress path. [Chrome MCP README](https://github.com/ChromeDevTools/chrome-devtools-mcp); [browser-use config source](https://github.com/browser-use/browser-use/blob/main/browser_use/config.py)
- **Embedding shifts security ownership to the app.** Electron recommends no Node integration for remote content, context isolation, sandboxing, permission handlers, validating IPC senders, restricting unexpected windows/navigation and keeping Electron current. CEF warns that Chromium vulnerabilities affect corresponding CEF releases and applications must update their shipped framework. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security); [CEF security updates](https://github.com/chromiumembedded/cef#security-updates)

### Inferences

- For **strictly local browser infrastructure**, choose app-owned Chromium/CDP, embedded Chromium or self-hosted Steel/appropriately licensed Browserless; do not require Browserbase. For **strictly local AI processing**, also choose local inference, local logs/artifacts, disabled optional telemetry/cloud sync and appropriate outbound policy. Browsing the public web still necessarily contacts the visited sites; “local” should specify infrastructure/data-processing locality, not pretend websites are offline. [browser-use local inference](https://github.com/browser-use/browser-use); [MCP telemetry](https://github.com/ChromeDevTools/chrome-devtools-mcp); [Steel deployment](https://github.com/steel-dev/steel-browser)
- Best packaged candidate to examine first for reducing viewer work: **Steel's local viewer source**, because local deployment and interactive implementation are both evidenced. This is a candidate, not an endorsement of code quality or a promise of native fidelity. Browserless is better framed as another local browser service, with live-interaction feature/license terms checked separately. [Steel implementation](https://github.com/steel-dev/steel-browser/blob/main/api/src/templates/live-session-streamer.ejs); [Browserless features/licensing](https://github.com/browserless/browserless)
- For confidentiality, separate an automation-capable app profile from unrestricted personal browsing, keep the privileged controller out of remote website contexts, minimize logged page content and require confirmation for sensitive actions. A local CDP port is powerful enough to defeat simplistic “it's only localhost” safety assumptions. [MCP security warning](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md); [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)

### Gaps

- Browserbase's actual Live View transport/codec and any private enterprise on-premises offerings were not established. Do not assert it uses VNC or CDP screencasting internally, nor assert that every possible Browserbase enterprise arrangement forbids self-hosting. The substantiated statement is that the retrieved public docs are managed-platform docs, not instructions for running its server locally.
- Steel Cloud/self-host feature parity, authentication defaults, multi-session isolation, runtime egress and production durability were not audited. Open viewer code does not prove all desired browser-shell behaviors.
- Browserless free debug viewer interactivity versus premium hybrid streaming needs exact-version/product verification; no claim of feature equivalence was made.
- No redistribution/commercial legal review was performed. Chrome binaries, codec/DRM support, container tooling and transitive dependency obligations are outside the component-license summary.
- Web search returned HTTP 402; research therefore relied on directly retrieved current primary documentation and upstream source files. Mutable `main`/tip-of-tree docs should be checked against the versions chosen for implementation.
