# SANE repository: controlling the exact embedded browser session

## 1. What actually creates and owns the browser view, tabs, and session?

### Takeaway
SANE App is a Bun-served React web application, optionally installed as a PWA. Its “browser view” is a set of ordinary sandboxed HTML iframes inside the user's hosting browser—not an Electron BrowserView, a Tauri WebView, or a repository-created Chromium instance. The exact live session therefore resides in the browser/device/window already hosting SANE.

### Cited Findings
- The package launches with `bun start.ts`, depends on React/ReactDOM, and does not list an Electron/Tauri/native-webview runtime in its dependencies. The server entry calls the bridge; the bridge uses `Bun.serve` for its frontend/API listener. Sources: [package.json:5–10](file:///Users/beto/sane/packages/sane-app/package.json#L5), [package.json:11–46](file:///Users/beto/sane/packages/sane-app/package.json#L11), [server.ts:4–7](file:///Users/beto/sane/packages/sane-app/server.ts#L4), [bridge.ts:4944–4952](file:///Users/beto/sane/packages/sane-app/src/bridge.ts#L4944).
- The README explicitly calls this a browser app and documents installation using browser install UI, Safari Add to Dock, or iPhone/iPad Add to Home Screen. Installation creates a standalone frontend window, **not native services or a background App server**. Sources: [README.md:3–10](file:///Users/beto/sane/packages/sane-app/README.md#L3), [README.md:173–183](file:///Users/beto/sane/packages/sane-app/README.md#L173).
- Actual browser surface creation is `BrowserFrame` returning `<iframe ... src={tab.url} ... sandbox={PREVIEW_SANDBOX} referrerPolicy="no-referrer" />`. The sandbox permits same-origin identity, scripts, forms, popups, escaping popups, and downloads. The comment explicitly says app previews need their own origin for scripts/API/storage. Sources: [browser-view.tsx:7–9](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L7), [browser-view.tsx:176–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176).
- These are **SANE UI tabs, not native browser tabs/CDP page targets**: the state is `{id,url}` records; maximum eight; each state entry is mapped to a `BrowserFrame`; selected versus grid display toggles visibility. Sources: [browser-tabs.ts:1–4](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L1), [browser-view.tsx:133–145](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L133).
- Tab records, active ID, and grid preference are persisted to the hosting browser's `localStorage` under `sane.browser.tabs.v1.<workspaceId>`. Only URLs/IDs/display state are serialized—not cookies, page DOM, frame JS state, native target IDs, or browser profiles. Sources: [browser-tabs.ts:18–29](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L18), [browser-tabs.ts:32–60](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L32).
- There is no proxy for preview URLs: resolution is on the frontend device. URL normalization allows HTTP/HTTPS only, rejects embedded credentials, and defaults bare host input to HTTP. The UI separately explains localhost means the frontend device, not the SANE server. Sources: [browser-tabs.ts:7–15](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L7), [browser-view.tsx:123–127](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L123).
- Views are lazy-loaded after visiting Browser and remain mounted when moving to another main view; the view is hidden/inert rather than removed. Within a workspace, hidden tabs also retain their frame component. However, changing workspace changes `BrowserView`'s React key, and changing URL or refresh count changes the iframe key. Thus workspace switching, reload, URL changes, or closing tabs can destroy a live frame; preservation is not universal. Sources: [browser-view.tsx:133–145](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L133), [browser-view.tsx:176–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176), [app.tsx:408–409](file:///Users/beto/sane/packages/sane-app/frontend/app.tsx#L408).
- The address bar changes the stored `src`; refresh increments a React reload counter. “Open externally” is a normal `_blank` link. There is no back/forward implementation in this component, and the UI states the address shows the entered URL, **not subsequent navigation inside the page**. Sources: [browser-view.tsx:17–21](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L17), [browser-view.tsx:125–127](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L125), [browser-view.tsx:150–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L150).
- SANE's own API login cookie is `sane_app`, HttpOnly, SameSite=Strict, Secure on HTTPS. This is the App authentication boundary, not a cookie/session manager for arbitrary preview sites. Sources: [bridge-auth.ts:35–41](file:///Users/beto/sane/packages/sane-app/src/bridge-auth.ts#L35), [bridge-auth.ts:62–67](file:///Users/beto/sane/packages/sane-app/src/bridge-auth.ts#L62).

### Inferences
- **No repository-defined preview profile isolation:** workspace/tab separation is metadata/UI separation, not explicit cookie jars or browser contexts. There is no per-tab profile option on the iframe. Preview cookies/storage follow the actual hosting browser's origin, third-party-cookie, and partitioning policies. Do not promise that two same-site iframes share everything, or that an external top-level tab shares the iframe's partitioned state. Basis: [iframe construction](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176), [persistence schema](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L18), [documented third-party-cookie caveat](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L126).
- **“Same profile” is weaker than “same live session.”** A second page with matching cookies can still have different frame DOM, history, in-memory JS, per-tab/session storage, sockets, and application state. Here the live object is the existing iframe, whose lifecycle is visible in React—not merely a URL in localStorage. Basis: [frame lifecycle/keys](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L133), [iframe key](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L181), [persisted fields](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L44).

### Gaps
- Static repository evidence does not identify which browser actually hosts this user's current SANE window. Chrome/Chromium, Safari-installed web app, and other supported browsers imply different automation attachment choices. No browser inspection was performed, as requested.
- Browser-specific third-party storage partition behavior cannot be established from this repository alone. It must not be presented as a SANE-specific guarantee.

## 2. What bridges, IPC, automation, screenshots, or browser pairing already exist?

### Takeaway
Existing “Browser Pair” links a conversation beside a browser tab; it intentionally does **not** give the AI browser access. There is no browser-control API, screenshot pipeline, native evaluateJavaScript bridge, or CDP attachment implemented in the inspected browser feature.

### Cited Findings
- The shared contract's very first line is: **“Passive metadata only. A link grants no browser or execution capabilities.”** The target is just `{workspaceId,tabId}`; links identify conversations/harness authorities, not browser processes or debugging targets. Source: [browser-pair-contract.ts:1–9](file:///Users/beto/sane/packages/sane-app/shared/browser-pair-contract.ts#L1).
- `/api/browser-pairs` GET reads stored links; PUT validates metadata changes and writes them. The source explicitly says: **“Metadata only: no native refresh, prompt preparation or dispatch. The browser owns its tab IDs; the server never fetches a tab's URL.”** Source: [bridge.ts:3566–3596](file:///Users/beto/sane/packages/sane-app/src/bridge.ts#L3566).
- The pairing dialog tells users: “Saved links do not trigger agent actions or grant browser access” and “Only your message is sent. Browser URLs, screenshots, and page content are not included.” Its optional-message action calls ordinary `store.send(text, ...)`. Sources: [browser-pair-dialog.tsx:119–121](file:///Users/beto/sane/packages/sane-app/frontend/browser-pair-dialog.tsx#L119), [browser-pair-dialog.tsx:155–170](file:///Users/beto/sane/packages/sane-app/frontend/browser-pair-dialog.tsx#L155).
- `BrowserFrame` has no frame ref, load/navigation handler, `postMessage` bridge, page-evaluation function, DOM-access helper, or screenshot callback; it renders the sandboxed iframe and visibility controls only. Source: [browser-view.tsx:176–183](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176).
- The backend has an authenticated HTTP boundary; non-GET/HEAD operations require the exact configured Origin. The running listeners shown are the frontend/API listener, terminal WebSocket handler, and loopback native/hook listener—not a Chromium debugging listener. Sources: [bridge-auth.ts:48–59](file:///Users/beto/sane/packages/sane-app/src/bridge-auth.ts#L48), [bridge.ts:4944–4952](file:///Users/beto/sane/packages/sane-app/src/bridge.ts#L4944).
- Embedding restrictions are explicitly acknowledged: sites may block embedding, third-party cookies, or HTTP under HTTPS; users are advised to open those externally. SANE also refuses embedding its own exact origin both on URL submission and when restoring saved tabs. Sources: [browser-view.tsx:123–127](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L123), [browser-view.tsx:158–165](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L158), [browser-view.tsx:176–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176).

### Inferences
- **Current MCP tooling and pairing are separate capabilities.** A Chrome DevTools MCP supplied by the agent harness is not automatically connected to the browser hosting SANE, and the pairing metadata provides no mechanism to select that browser/iframe. Its presence in the current assistant tool catalog is not evidence of an App integration. Basis: [pair target contract](file:///Users/beto/sane/packages/sane-app/shared/browser-pair-contract.ts#L1), [server metadata-only route](file:///Users/beto/sane/packages/sane-app/src/bridge.ts#L3580).
- Adding a backend “evaluate JS” endpoint alone cannot reach a cross-origin frontend iframe: the backend does not own the rendering browser. Likewise, adding `iframe.contentWindow` code in the SANE page would not bypass normal cross-origin DOM protections. `allow-same-origin` preserves the preview site's own origin; it does not make a different site same-origin with SANE. Basis: [sandbox rationale](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L7), [no-proxy contract](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L7), [iframe construction](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L181).
- Repository searches found no implemented `evaluateJavaScript`, `connectOverCDP`, `remote-debugging`, browser-use, Puppeteer, Playwright browser controller, or Chrome DevTools browser-control integration in the inspected App sources. This is a scoped static-search finding, not a claim about the user's globally installed tools or every dependency. The strongest positive evidence is the complete iframe-only implementation and explicit metadata-only pairing contract cited above.

### Gaps
- No runtime port/process enumeration, installed-browser extension inspection, browser verification, or test execution was performed. Thus no claim is made that the hosting browser already exposes a usable debugging port or automation extension.
- Exact Chrome DevTools MCP configuration is outside the inspected App implementation; whether the existing MCP supports attaching to the current host/browser must be checked by the coordinator against that tool's documentation/configuration.

## 3. What is the lowest-change path to exact shared-session control?

### Takeaway
**Recommendation: first attach automation to the browser already hosting SANE, select the SANE top-level page, and target the existing preview iframe.** This preserves the actual live DOM/session and needs no SANE engine rewrite. If that host cannot expose supported automation, use an authorized browser extension or OS-level computer control of that same window; only move to streamed/VNC browsers when willing to change where the session lives.

### Cited Findings
- The existing page supplies stable-looking UI identifiers: `#browser-panel-<tab.id>`, an iframe `src`/title, selected-tab `data-browser-tab`, and tab state `{id,url}`. These are useful integration points for resolving SANE tab metadata to the actual frame, but they are not CDP target IDs. Sources: [browser-view.tsx:67–77](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L67), [browser-view.tsx:176–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176), [browser-tabs.ts:1–4](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L1).
- A frame already retained in the mounted browser view is the object to control; reopening its URL is unnecessary and can destroy the relevant state if implemented via refresh/key changes. Sources: [browser-view.tsx:133–145](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L133), [browser-view.tsx:176–181](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176).
- The current feature cannot embed every arbitrary website and has no native browser engine to expose a debugging switch on. Its host is the installed/browser frontend, and preview framing limits remain even if automation succeeds. Sources: [README.md:173–183](file:///Users/beto/sane/packages/sane-app/README.md#L173), [browser-view.tsx:123–127](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L123).

### Inferences
Ranked implementation options below are architectural proposals, **not runtime-verified product compatibility claims**:

1. **Existing Chromium host + attach-capable CDP/MCP/browser-use adapter: lowest SANE change.** Point the controller at the **hosting browser's** authorized debugging connection, choose the existing SANE top-level page rather than opening a new page, then resolve and control the child frame. A controller must support frame-aware locators/evaluation or explicit child-frame/CDP handling; a tool that only lists top-level tabs or automatically launches its own browser will not suffice. Cross-origin iframes may require extra frame/target handling in the controller. Basis: [actual iframe surface](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176), [UI versus stored tab identity](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L1). **Important:** attaching to the same process/profile but choosing a new tab is still not the exact existing live page.
2. **Authorized browser extension + localhost/MCP relay: best integrated middle ground if CDP attachment is awkward.** A privileged extension in the actual hosting browser could target that tab/frame, capture observations, and perform actions through permitted extension/debugger facilities. SANE could later expose explicit consent and conversation-to-actual-tab/frame routing, reusing pair metadata only as identity/UI context—not treating current pairing as authorization. This requires a new bridge, explicit permissions, frame mapping, lifecycle invalidation, and security work; the existing App iframe itself supplies none. Basis: [passive pair contract](file:///Users/beto/sane/packages/sane-app/shared/browser-pair-contract.ts#L1), [frame DOM IDs](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L179), [existing authenticated boundary](file:///Users/beto/sane/packages/sane-app/src/bridge-auth.ts#L48).
3. **OS-level screenshot/mouse/keyboard control of the existing window: no App code changes, coarser control.** This conceptually operates the exact pixels/session regardless of iframe origin and is useful if SANE is a Safari-installed web app or another non-CDP host. It needs separate desktop-control authorization and will inherit focus, visibility, coordinate, user-interference, and modal-dialog limitations. It does not magically add DOM selectors or server-side screenshots. Basis: [multiple supported installation hosts](file:///Users/beto/sane/packages/sane-app/README.md#L173), [iframe surface and visibility](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L133).
4. **Cooperative preview-app bridge: targeted alternative for apps the user controls.** Add a consented, origin-validated `postMessage` bridge inside the preview application, with a SANE/agent transport. This could provide semantic observation/actions in the existing live frame without privileged browser attachment, but only for instrumented/cooperative apps, not arbitrary sites. No such bridge exists now. Basis: [iframe-only frame implementation](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L176), [preview trusted-app scope](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L123).
5. **Dedicated local/remote automated Chromium + streamed view (VNC/noVNC or vendor live-view): larger change, clearer single owner.** Replace the iframe-to-target-site model with a viewer of one automation-owned browser. The AI and user would then share that **new browser's** live session. This is not an automatic attachment to today's existing iframe session; browser migration, authentication, target URL reachability, local services/tunnels, and state discontinuity must be acknowledged. Basis: [current direct-device URL resolution](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L7), [existing surface](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L181), [frontend-device localhost caveat](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L125).

Minimum design requirements for any integrated control path: explicit opt-in separate from existing pairing; resolve `{workspaceId,tabId}` to the **current host window/top-level target + frame**, not just URL; invalidate on frame replacement, workspace change, close, or navigation; bound permissions to intended origins/tabs; coordinate user versus AI actions; surface observations/screenshots from that same target. These requirements follow from today's passive pairing, local-only tab IDs, and React frame lifecycle. Sources: [pair contract](file:///Users/beto/sane/packages/sane-app/shared/browser-pair-contract.ts#L1), [tab identity/persistence](file:///Users/beto/sane/packages/sane-app/frontend/browser-tabs.ts#L18), [frame lifecycle](file:///Users/beto/sane/packages/sane-app/frontend/browser-view.tsx#L133), [workspace key](file:///Users/beto/sane/packages/sane-app/frontend/app.tsx#L409).

### Gaps
- External product support (browser-use attach modes, current Chrome DevTools MCP attach flags, Browserbase live-view characteristics, extension framework choices) is intentionally left to the independent web researchers. This note establishes what the repository needs and does not claim those products already meet it.
- The next decision is the actual host: ordinary Chrome tab, Chromium-installed PWA, Safari-installed app, or a remote client. Once known, verify that controller's attachment/frame support against its current documentation before proposing exact commands.
- Research was read-only except this notes file. No tests, test creation, App edits, skills/context edits, or browser verification were performed.
