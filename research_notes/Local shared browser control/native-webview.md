# Local AI control of the exact live native webview

Research reference date: **October 26, 2026** (session date). Sources were fetched during this research; undated documentation and mutable repository branches are not represented as having an October publication date. Tauri's WebDriver page explicitly reports **last updated June 29, 2026**; WebKit's inspection announcement is dated **March 20, 2023**. No application browsing or tests were performed. Engine conclusions below are conditional; actual repository architecture is another researcher's scope.

## 1. Can browser-use or Playwright attach to the exact embedded view, and how do engines differ?

### Takeaway

**If the view is Electron/Chromium, an explicitly exposed CDP endpoint is a plausible direct attachment route to the existing page; if it is macOS Tauri/WKWebView, standard browser-use/CDP attachment is not the supported route.** Playwright's ability to launch its own patched WebKit does not mean it can attach to an arbitrary live WKWebView. [Playwright CDP](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp), [Playwright WebKit](https://playwright.dev/docs/browsers#webkit), [Electron switches](https://www.electronjs.org/docs/latest/api/command-line-switches#--remote-debugging-portport).

### Cited Findings

- Playwright's `connectOverCDP` (Python `connect_over_cdp`) “attaches Playwright to an existing browser instance using the Chrome DevTools Protocol.” Its example obtains the **existing default context and an existing page** through `browser.contexts()[0]` and `defaultContext.pages()[0]`. The documentation explicitly says CDP connection is “only supported for Chromium-based browsers,” is “significantly lower fidelity” than the Playwright protocol, and can have broken functionality when the browser was launched without Playwright's expected arguments. This is an attachment capability, not a blanket guarantee for every Chromium embedder/version. [API documentation](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp).
- `browserType.connect()` is a different protocol: it attaches to a browser created with `BrowserType.launchServer`, with matching Playwright major/minor versions. A random WebKit inspector socket is not documented as a compatible endpoint. [API documentation](https://playwright.dev/docs/api/class-browsertype#browser-type-connect).
- Playwright states: “Playwright doesn't work with the branded version of Safari since it relies on patches.” Its WebKit comes from recent WebKit main-branch sources, potentially ahead of Safari; each Playwright version requires specific browser binaries. Therefore **WebKit engine family compatibility is not equivalent to arbitrary WKWebView embedding compatibility**. [Browser documentation](https://playwright.dev/docs/browsers#webkit).
- Browser-use documents `Browser(cdp_url="http://localhost:9222")` as connecting to an **existing browser instance**. Its current source imports `CDPClient` from `cdp_use` and calls Chromium CDP methods; its DOM implementation specifically uses `DOMSnapshot.captureSnapshot`, `DOM.getDocument`, and `Accessibility.getFullAXTree`. It is inaccurate to assume current browser-use is merely a generic Playwright adapter that gains WKWebView support by selecting `webkit`. [Browser configuration](https://docs.browser-use.com/customize/browser/all-parameters), [session source](https://github.com/browser-use/browser-use/blob/main/browser_use/browser/session.py), [DOM source](https://github.com/browser-use/browser-use/blob/main/browser_use/dom/service.py).
- Safari Web Inspector **can inspect a particular live WKWebView**: Apple/WebKit introduced per-instance `isInspectable` opt-in (default `false`) with macOS 13.3/iOS 16.4; an enabled view appears in Safari's Develop menu. This provides live debugging, not a documented Chromium CDP server. [WebKit announcement, March 20, 2023](https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/).
- WebKit maintains its own inspector protocol schema. For example, its `Runtime.evaluate` uses `doNotPauseOnExceptionsAndMuteConsole` and `emulateUserGesture`, and reports `wasThrown`; protocol-domain names that resemble CDP are not evidence of wire compatibility. Combined with Playwright's explicit Chromium-only CDP restriction, **“enable Safari inspector and pass its endpoint to `connect_over_cdp`” is not a supported solution**. [WebKit protocol source](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/inspector/protocol/Runtime.json), [Playwright restriction](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp).
- Electron supports `--remote-debugging-port=port` (“Enables remote debugging over HTTP on the specified port”). Its `webContents` API enumerates existing web contents for windows and webviews, looks them up by ID, and maps a Chromium DevTools `TargetID` back to a `WebContents`. Thus an embedding app can identify the precise guest rather than accidentally controlling the app shell or another tab. **Renderer remote debugging is distinct from Electron's Node/main-process `--inspect` endpoint.** [Switches](https://www.electronjs.org/docs/latest/api/command-line-switches), [webContents](https://www.electronjs.org/docs/latest/api/web-contents#webcontentsfromdevtoolstargetidtargetid).

### Inferences

- For Electron, prefer a host-maintained mapping between app tab/webview ID and CDP `targetId`, select the existing target, and prevent unwanted new-page creation or browser shutdown. Merely connecting to a browser endpoint and selecting the first page is insufficient evidence that the AI shares the user's intended view. This design follows the documented existing-page and target-ID mechanisms. [Playwright existing-page example](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp), [Electron target lookup](https://www.electronjs.org/docs/latest/api/web-contents#webcontentsfromdevtoolstargetidtargetid).
- For WKWebView, keep the current engine if an app-owned native automation bridge meets requirements; switching to Chromium may simplify compatibility with existing CDP agents, but it is not logically necessary for sharing the same live session. Native scripting/snapshot facilities in section 2 support the latter inference. [Apple WKWebView](https://developer.apple.com/documentation/webkit/wkwebview).

### Gaps

- No claim is made that a specific Electron app exposes all targets browser-use expects, or that its exact Electron/Chromium version works with the chosen Playwright/browser-use release. That requires a separately authorized integration check.
- No official Apple-supported generic Safari-inspector-to-CDP compatibility layer was established. This is **not** a claim that a custom protocol translator is impossible.

## 2. What local control paths exist for Tauri/WKWebView, including screenshots and input?

### Takeaway

**WKWebView can support AI control of the same object through native JavaScript evaluation, native snapshots, and an explicit input layer.** Importantly, current Tauri docs now recommend an embedded WebdriverIO server that supports macOS: saying “Tauri automation has no macOS support” is obsolete, although upstream `tauri-driver` itself still lacks macOS support. [Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/), [Apple evaluation](https://developer.apple.com/documentation/webkit/wkwebview/evaluatejavascript(_:in:in:completionhandler:)), [Apple snapshot](https://developer.apple.com/documentation/webkit/wkwebview/takesnapshot(with:completionhandler:)).

### Cited Findings

- Tauri's WebDriver page, updated **June 29, 2026**, distinguishes three routes: (1) WebdriverIO with the **in-app embedded WebDriver server**, supported on Windows/Linux/macOS; (2) upstream `tauri-driver`, Windows/Linux only because “macOS has no WKWebView driver tool available”; (3) CrabNebula's cross-platform fork, requiring a paid key for macOS. The embedded route uses `tauri-plugin-wdio-webdriver`; the separate `tauri-plugin-wdio` enables richer backend access/mocking/logs. [Official Tauri docs](https://v2.tauri.app/develop/tests/webdriver/), [WebdriverIO Tauri docs](https://webdriver.io/docs/desktop-testing/tauri/).
- The embedded route is **WebDriver**, not CDP. Its macOS executor owns a `WebviewWindow<R>`, obtains the existing native `WKWebView` through `with_webview`, evaluates JavaScript, and calls `takeSnapshotWithConfiguration_completionHandler` to return a native snapshot. This is useful source evidence for same-object scripting and real image capture, rather than a DOM-to-canvas imitation. [macOS implementation](https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-plugin-webdriver/src/platform/macos.rs), [screenshot handler](https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-plugin-webdriver/src/server/handlers/screenshot.rs).
- **Do not confuse this embedded server's coordinate actions with native trusted mouse input.** The platform executor's default pointer implementation evaluates `pointer_event_script`; that script uses `document.elementFromPoint(x,y)` and `dispatchEvent(new PointerEvent(...))` / `new MouseEvent(...)`. The checked macOS executor does not replace that path with an OS-event implementation. Scroll actions likewise dispatch a JavaScript wheel event and call `window.scrollBy`. The server offers coordinate-shaped APIs, but this source path is DOM-synthetic input. [Default executor](https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-plugin-webdriver/src/platform/executor.rs), [pointer script](https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-plugin-webdriver/src/platform/pointer_input.rs), [macOS executor](https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-plugin-webdriver/src/platform/macos.rs).
- Apple provides `evaluateJavaScript(_:in:in:completionHandler:)`, explicitly evaluating in a specified `WKFrameInfo` and `WKContentWorld`; `nil` frame means the main frame. The native completion returns evaluation result/error on the app's main thread. `callAsyncJavaScript` is also available for asynchronous functions. These APIs can implement DOM extraction, element queries, controlled script actions, and result delivery on the actual live view. [Apple evaluation API](https://developer.apple.com/documentation/webkit/wkwebview/evaluatejavascript(_:in:in:completionhandler:)), [WKWebView methods](https://developer.apple.com/documentation/webkit/wkwebview).
- Apple documents `takeSnapshot(with:completionHandler:)` as “Generates a platform-native image from the web view’s contents asynchronously”; configuration selects the captured portion. It captures webview content, not a promise to capture all native app chrome, permission sheets, every GPU/media surface, or arbitrary hidden/offscreen state. [Apple snapshot API](https://developer.apple.com/documentation/webkit/wkwebview/takesnapshot(with:completionhandler:)).
- Tauri's source exposes `Webview::with_webview`, macOS `PlatformWebview::inner()` returning the WKWebView handle, `eval`, and `eval_with_callback` (JSON-serialized evaluation result). An app-owned bridge need not depend on an externally exposed Safari inspector. [Tauri webview source](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/webview/mod.rs).
- macOS offers an alternative **accessibility + desktop input** path: `AXUIElementCreateApplication(pid)` targets an application's accessibility object, `AXUIElementCopyAttributeValue` reads supported attributes, and `AXUIElementPerformAction` requests supported actions. Apple explicitly documents unsupported-action/not-implemented errors; an accessibility tree is not a guaranteed complete DOM. Accessibility-client trust can be checked/requested with `AXIsProcessTrustedWithOptions`. [Application object](https://developer.apple.com/documentation/applicationservices/1459374-axuielementcreateapplication), [attributes](https://developer.apple.com/documentation/applicationservices/1462085-axuielementcopyattributevalue), [actions](https://developer.apple.com/documentation/applicationservices/1462091-axuielementperformaction), [trust](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions).
- Quartz `CGEvent.post(tap:)` posts an event into the OS event stream. This is a separate implementation route from page JavaScript and can underpin local computer-use mouse/keyboard control. ScreenCaptureKit provides selected screen/window capture and documents asking the person for screen-recording permission. Native webview snapshots and OS screen capture are distinct capture paths, with distinct scope and permissions. [Quartz event posting](https://developer.apple.com/documentation/coregraphics/cgevent/post(tap:)), [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit).
- Electron additionally exposes same-`webContents` `executeJavaScript`, `capturePage`, and `sendInputEvent` for mouse/wheel/keyboard events; documentation says the containing `BrowserWindow` must be focused for `sendInputEvent`. These provide a host-native bridge even without a remote CDP server. `executeJavaScript`'s optional `userGesture` flag is not the same API as input-event dispatch. [Electron webContents](https://www.electronjs.org/docs/latest/api/web-contents), [source documentation](https://github.com/electron/electron/blob/main/docs/api/web-contents.md).

### Inferences

- A reasonable WKWebView architecture is **semantic observation/actions first, native snapshot second, accessibility/OS input fallback when necessary**, all keyed to the same app-owned view. Export a deliberately small, authenticated local tool interface, rather than exposing unrestricted native access to arbitrary web content. This combines the documented native APIs; it is a design recommendation, not a pre-existing drop-in browser-use backend. [Tauri native handle](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/webview/mod.rs), [Apple scripting](https://developer.apple.com/documentation/webkit/wkwebview/evaluatejavascript(_:in:in:completionhandler:)), [Apple accessibility](https://developer.apple.com/documentation/applicationservices/1462091-axuielementperformaction).
- Consider reusing the embedded WebDriver implementation before building every DOM command from scratch, **but audit its synthetic input, target selection, frame behavior, build gating, and lifecycle**. The default WDIO service documentation describes discovering/launching an app; attaching to an already-running production app without restart is a separate integration requirement, not proven by a successful test-launch recipe. [Tauri guide](https://v2.tauri.app/develop/tests/webdriver/), [WebdriverIO service](https://webdriver.io/docs/desktop-testing/tauri/), [executor](https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-plugin-webdriver/src/platform/executor.rs).
- For true desktop-coordinate fallback, translate screenshot pixels to view/screen coordinates deliberately (scale, zoom, window origin, scrolling), focus the intended view, and serialize human/agent control. OS event posting and accessibility act on the live app rather than requiring cookie transfer, but do not by themselves provide DOM-level semantics. [Quartz](https://developer.apple.com/documentation/coregraphics/cgevent/post(tap:)), [AX application targeting](https://developer.apple.com/documentation/applicationservices/1459374-axuielementcreateapplication).

### Gaps

- No runtime validation of trusted-event behavior, media capture, file chooser handling, IME, permissions, background/minimized capture, or WebDriver conformance was performed.
- The checked embedded macOS executor is typed around `WebviewWindow<R>`; support for an application's particular **child webviews/multiple tabs** must be verified, not inferred from the framework's general macOS support.
- Accessibility trust and screen recording permissions are documented; exact Quartz event-injection permissions, sandbox/distribution constraints, and `isTrusted` behavior for a chosen native-event technique still require implementation-specific checking. Do not promise universal native trusted input merely because an API accepts coordinates.

## 3. What does “same session” require, and what are the iframe, trust, and locality boundaries?

### Takeaway

**The same login/profile is weaker than the same live page.** Preserve the actual view/page identity and transient state, and distinguish DOM-synthetic actions from native/browser input; neither cross-origin frames nor local execution should be assumed to work transparently. [Playwright attachment](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp), [authentication reuse](https://playwright.dev/docs/auth#session-storage), [DOM standard](https://dom.spec.whatwg.org/#dom-event-istrusted).

### Cited Findings

- Playwright's persistent-context API stores browser session data such as cookies/local storage in a user data directory, but **launches a browser**. It warns that browsers cannot run multiple instances against the same user data directory. Its saved-authentication-state workflow bootstraps new contexts; it separately documents a workaround for sessionStorage because there is no API to persist it through ordinary storage-state reuse. Thus storage/profile reuse is not documented as transporting a live document, JavaScript heap, open connection, unsaved in-page state, or existing tab identity. [Persistent context](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context), [authentication](https://playwright.dev/docs/auth#session-storage). Note: the auth page's broad wording about sessionStorage not persisting across page loads should **not** be repeated as a web-platform rule; the relevant reliable claim here is its API limitation/workaround.
- Browser-use lists `cdp_url`, `user_data_dir`, and `storage_state` as **separate options**. `Browser.from_system_chrome()` configures a Chrome executable/profile and notes that Chrome may need to be fully closed first. That method should not be sold as attaching to an already-visible WKWebView or preserving an existing live tab. [Browser-use parameters](https://docs.browser-use.com/customize/browser/all-parameters).
- The DOM standard says `isTrusted` indicates user-agent dispatch rather than `dispatchEvent`; script-created events start false, and `HTMLElement.click()` is explicitly a legacy untrusted exception. Consequently setting `.value`, calling `.click()`, or dispatching mouse/keyboard events through evaluation is not equivalent to native input and does not reliably satisfy transient-user-activation requirements. [Normative DOM standard](https://dom.spec.whatwg.org/#dom-event-istrusted), [standards source inspected](https://github.com/whatwg/dom/blob/main/dom.bs). `isTrusted`, user activation, accessibility-client trust, and OS permissions are different concepts; none should be used as a synonym for the others.
- Playwright frame automation explicitly targets a `Frame`/`frameLocator`, while page-level actions assume the main frame. Browser-use exposes `cross_origin_iframes` (documented default **false**) and its current source has dedicated cross-origin frame processing. General “supports DOM automation” is therefore not a sufficient cross-origin-iframe guarantee. [Playwright frames](https://playwright.dev/docs/frames), [browser-use options](https://docs.browser-use.com/customize/browser/all-parameters), [browser-use DOM implementation](https://github.com/browser-use/browser-use/blob/main/browser_use/dom/service.py).
- Apple supports user scripts injected into **all frames** (`forMainFrameOnly=false`), and its native evaluation API accepts an explicit `WKFrameInfo`. A `WKContentWorld` isolates JavaScript variables, **not the underlying DOM**: Apple says DOM changes remain visible to all scripts regardless of world. These are useful building blocks for a frame-aware bridge, not a blanket same-origin-policy bypass from a top-frame script. [All-frame script API](https://developer.apple.com/documentation/webkit/wkuserscript/init(source:injectiontime:formainframeonly:)), [frame-targeted evaluation](https://developer.apple.com/documentation/webkit/wkwebview/evaluatejavascript(_:in:in:completionhandler:)), [content worlds](https://developer.apple.com/documentation/webkit/wkcontentworld).
- The embedded WDIO executor's frame wrapper navigates `frame.contentWindow` / `frame.contentDocument` and executes `ctx.eval(...)` from its wrapper, rather than demonstrating native per-frame dispatch. **Inference from implementation:** this path remains subject to cross-origin access restrictions; do not advertise arbitrary cross-origin iframe support without further evidence. [Executor/frame wrapper source](https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-plugin-webdriver/src/platform/executor.rs), [HTML iframe definition](https://html.spec.whatwg.org/multipage/iframe-embed-object.html#dom-iframe-contentdocument).
- Browser-use's Python API configures the browser and LLM separately, with remote provider options and a documented `ChatOllama` local-model option. Its telemetry docs provide `ANONYMIZED_TELEMETRY=false`. A **local browser and local control bridge do not imply local inference**; remote LLM calls can transmit the page text/screenshots/context sent to that provider. All-local operation requires selecting local inference and auditing telemetry/tracing/other outbound services, rather than choosing a cloud-browser product. [Model documentation](https://docs.browser-use.com/open-source/supported-models.md), [browser/LLM configuration example](https://docs.browser-use.com/customize/browser/remote), [telemetry opt-out](https://docs.browser-use.com/open-source/development/monitoring/telemetry.md).

### Inferences

- Define acceptance as **same live native view or CDP target**, not just same URL/login: preserve existing transient document state and show agent actions in that exact view. Cookie export/import and profile relaunch are fallback state-reuse approaches, not fulfillment of this acceptance criterion. [Existing-page attachment](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp), [profile launch semantics](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context).
- For WKWebView cross-origin automation, design per-frame script installation and frame-identified message/result channels, with explicit origin authorization. Merely recursively querying `iframe.contentDocument` from the top frame is not equivalent. The Apple APIs supply building blocks; frame enumeration/lifecycle and authorization still need engineering. [Apple all-frame injection](https://developer.apple.com/documentation/webkit/wkuserscript/init(source:injectiontime:formainframeonly:)), [native frame evaluation](https://developer.apple.com/documentation/webkit/wkwebview/evaluatejavascript(_:in:in:completionhandler:)).
- A useful product boundary is: **semantic DOM automation** for robust named elements and extraction; **native/browser input** for interactions requiring real event routing; **computer use** for visible surfaces or native UI the DOM layer cannot describe. The methods can share one live view without being interchangeable or promising equal reliability. [Apple scripting](https://developer.apple.com/documentation/webkit/wkwebview/evaluatejavascript(_:in:in:completionhandler:)), [AX actions](https://developer.apple.com/documentation/applicationservices/1462091-axuielementperformaction), [Quartz](https://developer.apple.com/documentation/coregraphics/cgevent/post(tap:)), [Electron input](https://www.electronjs.org/docs/latest/api/web-contents).

### Gaps

- The actual application's engine, view construction, current bridge, IPC permissions, frame/origin setup, target selection, and model endpoint have intentionally not been inferred.
- No quantitative reliability/performance comparison was established, and no claim is made that an all-local small model has the same task success as a hosted model.
- Source discovery searches returned HTTP 402; findings rely on directly retrieved official documentation and upstream source. Mutable branches/latest docs can change; pin dependency versions before implementation.
