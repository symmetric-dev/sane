# Linear clients, public SDK, and a minimal SANE cache

Research retrieved **2026-10-05**. Scope: official Linear client synchronization versus public integration capabilities and a narrow SANE architecture recommendation. Sources are living documentation and SDK `master`, not a pinned dependency version. No code edits, tests, browser verification, credentials, or live Linear mutations were performed. Only this notes file was written.

## 1. Does the public Linear client provide the official application's local/offline sync engine?

### Takeaway

**Linear's own applications really do maintain local databases and synchronize changes, including offline mutation retries. Public `@linear/sdk` is a typed GraphQL API client, not that replication engine.** SANE can show and edit Linear issues directly through supported queries/mutations, but durable local caching and any offline-write protocol would be SANE-owned work. [Official engine](https://linear.app/blog/rebuilding-delta-sync-read-path); [App offline behavior](https://linear.app/docs/get-the-app); [SDK](https://linear.app/developers/sdk).

### Cited Findings

- Linear's August 18, 2026 engineering article explicitly calls Linear local-first: each client maintains a local database. A returning client supplies a checkpoint containing the last applied change ID; delta sync retrieves subsequent changes. An immutable ordered per-workspace action log covers updates, deletion, and archiving, filtered by access and subscriptions. This is materially stronger than fetching issues with a timestamp filter. — [Rebuilding Linear's delta sync read path](https://linear.app/blog/rebuilding-delta-sync-read-path).
- Official application docs say unsent changes are stored locally, retried when connectivity returns, and survive application restarts. A “Syncing” indicator shows the number waiting. They also explicitly call offline mode a **failsafe, not a full-fledged feature**, warn they do not check each change's creation date before applying it, and identify overwriting teammates' description/status changes as a risk. Nearly all desktop functionality, including offline mode, exists in most supported browsers. — [Download Linear → Real time sync and offline](https://linear.app/docs/get-the-app).
- The earlier 2023 engineering talk concerns the sync engine **in the Linear application**. It is not a public SDK installation or replication API contract. The 2026 article now provides stronger written evidence of the client database and checkpoint/log architecture. — [Scaling the Linear Sync Engine](https://linear.app/blog/scaling-the-linear-sync-engine); [2026 article](https://linear.app/blog/rebuilding-delta-sync-read-path).
- Public SDK documentation describes `@linear/sdk` as exposing the GraphQL schema through strongly typed models and operations. Source `LinearClient` constructs `LinearGraphQLClient`, defaults to `https://api.linear.app/graphql`, and forwards generated operations to `.request()`. That transport serializes `{query, variables}`, makes an HTTP POST with `fetch`, and processes GraphQL data/errors. These inspected entry/transport files implement no persistent database, replication checkpoint replay, or durable offline mutation queue. — [SDK guide](https://linear.app/developers/sdk); [SDK repository](https://github.com/linear/linear/tree/master/packages/sdk); [client.ts](https://github.com/linear/linear/blob/master/packages/sdk/src/client.ts); [graphql-client.ts](https://github.com/linear/linear/blob/master/packages/sdk/src/graphql-client.ts).
- The GraphQL guide calls the public API the same API used internally, but documents queries/mutations, pagination/filtering, and webhooks for external updates. This wording **does not establish that all internal sync services/protocols are available or supported for third-party replication**. — [GraphQL guide](https://linear.app/developers/graphql).
- The public schema includes `IssuePayload.lastSyncId`, described as the last sync operation identifier. That field's presence is not a documented bootstrap/delta subscription endpoint, SDK database, or offline queue. The same schema exposes some explicitly `[Internal]` fields, which must not be treated as supported integration contracts solely because introspection can reveal them. — [Published SDK schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql).
- Official Linear MCP is centrally hosted and managed, using remote Streamable HTTP, with tools to find/create/update Linear objects. A local `mcp-remote` compatibility process is a transport bridge, not a local Linear replica. — [Linear MCP documentation](https://linear.app/docs/mcp).
- Supported API examples fetch issue details and `workflowStates`, and update an issue's `stateId` through `issueUpdate`, returning `success` and the resulting issue/state. Title/Markdown description creation and editing are documented too. — [GraphQL query/mutation examples](https://linear.app/developers/graphql).

### Inferences

- Distinguish three promises: **cached read** = previously fetched data available offline; **online edit** = SANE sends a mutation to authoritative Linear and confirms its outcome; **offline write sync** = durable operations, reconnect delivery, uncertain-outcome handling, conflict policy, permission changes and reconciliation. Only the first two belong in the smallest integration. The SDK is useful for API typing/access, not a full sync library. — Basis: [SDK](https://linear.app/developers/sdk), [transport](https://github.com/linear/linear/blob/master/packages/sdk/src/graphql-client.ts), [official offline warning](https://linear.app/docs/get-the-app).
- Viewing status and changing it directly in SANE is feasible without opening Linear; it requires native SANE UI/backend wiring, credentials and appropriate permissions, not embedding or extracting the official client's local database. Use the selected team's actual workflow state IDs/names rather than assuming one universal open/closed vocabulary. — Basis: [API workflow/state examples](https://linear.app/developers/graphql), [Issue schema/team/state fields](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql).

### Gaps

- No supported public package/contract for reusing the official application's database, ordered delta replay or offline operation queue was found in the reviewed docs/repository. This is a bounded finding, not proof no private/internal interface exists. No storage implementation such as IndexedDB is claimed here: the current written primary source establishes a local database, without needing to identify its implementation.
- SDK installed version, production authentication, state mutation permissions and end-to-end behavior were not tested. The official engine's performance and internal CDC idempotence do not confer idempotence on public issue mutations.

## 2. Can SANE keep a useful local cache through polling or webhooks, including missing/archived data?

### Takeaway

**A best-effort scoped persisted cache is practical; a complete replica is not supplied by the API client.** For a desktop/loopback app, fetch-on-open and bounded visible-only polling avoid webhook hosting, although Linear prefers webhooks for sustained realtime integrations. Timestamp queries need pagination and reconciliation; they are not deletion-aware ordered delta sync. [Update guidance](https://linear.app/developers/graphql); [Rate guidance](https://linear.app/developers/rate-limiting); [Webhooks](https://linear.app/developers/webhooks).

### Cited Findings

- Linear list queries use Relay cursors (`first`/`after`, `last`/`before`), default to the first 50 results, and expose `pageInfo.hasNextPage/endCursor`. Default order is `createdAt`; `orderBy: updatedAt` retrieves most recently updated resources. A single page is not an exhaustive synchronized scope. — [Pagination](https://linear.app/developers/pagination).
- Filters support dates with `gt/gte/lt/lte`, relation filters and logical operators. The published `IssueFilter` explicitly contains `updatedAt: DateComparator`, `archivedAt`, team, project and state filters. — [Filtering](https://linear.app/developers/filtering); [IssueFilter schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql).
- Archived resources are excluded from paginated responses by default; `includeArchived: true` includes them. The issue schema also exposes `archivedAt` and `trashed`; their existence does **not** document a universal deleted-record/tombstone stream or make `includeArchived` equivalent to “include deleted.” — [Archived resources](https://linear.app/developers/graphql); [Issue schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql).
- The API guide recommends webhook updates; if polling is necessary it says to fetch recently updated issues first, filter server-side, and **not poll every issue separately**. Rate-limit docs more strongly discourage polling, recommend webhooks and narrow custom queries, and expose request/complexity remaining/reset headers. Limits are subject to evolution; handle GraphQL `RATELIMITED` errors rather than assuming a fixed request budget. — [Fetching Updates](https://linear.app/developers/graphql); [Rate limiting](https://linear.app/developers/rate-limiting).
- Webhook consumers **must** have a publicly accessible HTTPS **non-localhost** URL and return HTTP 200. A failed/non-200 delivery or response taking longer than five seconds is retried up to three times: after one minute, one hour, then six hours. Persistently unavailable hooks may be disabled and require manual re-enablement. — [Webhook requirements/retries](https://linear.app/developers/webhooks).
- Verify `Linear-Signature` as HMAC-SHA256 of the **raw** request body using the signing secret, with safe comparison; Linear recommends verifying `webhookTimestamp` is within one minute to limit replay. `Linear-Delivery` uniquely identifies a payload. Data-change actions include `create/update/remove`; updates include previous changed values in `updatedFrom`. Only workspace admins or OAuth apps with `admin` can create/read webhooks. — [Webhook payload/security/admin requirements](https://linear.app/developers/webhooks).
- SANE configuration defaults to `127.0.0.1:8787` and package-local `.data`. This was directly reread for this follow-up; the prior audit describes authenticated bridge routes and owner-scoped, not per-user RBAC. — [app-config.ts](/Users/beto/sane/packages/sane-app/src/app-config.ts#L101-L108); [Prior audit](../SANE%20issue%20tracking%20integration%20options/codebase.md).

### Inferences

- **Recommendation, not Linear's preferred general realtime architecture:** one scoped backend fetch on panel open/focus/manual refresh; optional conservative bounded polling only while that pane is visible. Combine list updates in one filtered request rather than N per-issue pollers; deduplicate across tabs/workspaces sharing the same binding, pause when hidden/offline, avoid overlapping requests and back off on errors/rate limits. Fetch a detail when explicitly opened and refresh after an acknowledged mutation. This consciously trades freshness for local simplicity and should not be marketed as realtime sync. — Basis: [Update guidance](https://linear.app/developers/graphql), [Rate limits](https://linear.app/developers/rate-limiting), [Local defaults](/Users/beto/sane/packages/sane-app/src/app-config.ts#L101-L108).
- For an optional incremental optimization, request updates since an overlapping `updatedAt` watermark, order by `updatedAt`, upsert by immutable issue ID and exhaust required pages before advancing the watermark. Keep progress/continuation if a configured page/time budget stops the scan; do not label a truncated run complete. Timestamp overlap/deduplication reduces boundary misses but cannot make a mutable paginated query an immutable change log. For a small pane, refetching its bounded scope may be simpler than incremental bookkeeping. — Basis: [Pagination](https://linear.app/developers/pagination), [Filters/schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql), contrasted with [Official log](https://linear.app/blog/rebuilding-delta-sync-read-path).
- Archived issues can disappear from the default list; an issue moved out of the selected team/project/status filter also disappears. A permanently deleted or newly inaccessible issue cannot be relied on to appear in an `updatedAt` issues query. Rebuild periodically from a **complete successful scoped** listing to evict no-longer-visible members; do not evict based on a partial page or network/auth error. Selected missing IDs may need a user-triggered check, with “unavailable/no longer in this view” rather than confidently “deleted.” A bounded page cache should advertise its limits, not pretend to replicate the whole workspace. — Basis: [Archived defaults and filtered updates](https://linear.app/developers/graphql), [Filtering](https://linear.app/developers/filtering), [Remove events](https://linear.app/developers/webhooks).
- Loopback/NAT cannot receive Linear's direct server-to-server webhook pushes. A public relay or tunnel would add infrastructure, secrets/signature checks, durable ingestion, duplicate handling, reconnect replay and deployment availability; **do not expose the existing privileged SANE bridge** simply to get callbacks. A localhost OAuth callback is a different mechanism: Linear documents localhost redirect examples, but rejects localhost webhook endpoints. — Basis: [Webhooks](https://linear.app/developers/webhooks), [OAuth callback examples](https://linear.app/developers/oauth-2-0-authentication), [SANE listener](/Users/beto/sane/packages/sane-app/src/app-config.ts#L105).
- If a hosted backend is later justified for shared always-on freshness, acknowledge verified webhooks promptly after durable acceptance, deduplicate deliveries, invalidate/refetch affected data, and retain reconciliation as recovery after missed deliveries/disabled hooks. Finite retries are not an indefinitely replayable guaranteed change stream. — Basis: [Webhook retry/payload documentation](https://linear.app/developers/webhooks).

### Gaps

- Reviewed sources provide no public timestamp-query completeness guarantee, stable snapshot across pages, global deletion cursor, unlimited webhook retention/replay, or exactly-once/in-order webhook delivery guarantee. Specific trash-query behavior, archive timestamp propagation and permission-loss responses should be verified against the chosen schema/account before implementation.
- No exact polling interval or measured SANE workload was established. “Visible-only bounded polling” is an MVP tradeoff, not a vendor endorsement or promise to stay within limits regardless of other integrations.

## 3. What is the simplest safe SANE design, and what should users see when writes conflict or are uncertain?

### Takeaway

Keep **Linear authoritative, online writes only, a disposable scoped local cache, explicit stale/last-fetched indicators, and at most a small unsent draft**. Never silently overwrite an old description, claim a timed-out mutation failed, or convert a local draft into an automatic reconnect queue. [Mutation/error semantics](https://linear.app/developers/graphql); [Offline overwrite warning](https://linear.app/docs/get-the-app).

### Cited Findings

- API calls can return HTTP 200 with partial data and GraphQL errors. The official guide says to inspect `errors`, validate required fields, and handle server/rate-limit failures; examples additionally return mutation `success` and entity data. — [GraphQL error handling/mutations](https://linear.app/developers/graphql).
- `IssueUpdateInput` states that only provided fields are updated and supported nulls clear values; it contains title, description, `stateId` and other fields. The reviewed full input contains no expected revision/`updatedAt` compare-and-swap field. Issue `descriptionState` is labeled internal, so its YJS representation is not evidence that replacing public Markdown automatically merges edits. — [Published IssueUpdateInput and Issue schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql).
- Both `IssueCreateInput` and `CommentCreateInput` accept an optional client-supplied UUID v4 `id`. This is useful for follow-up identity checks, but the schema description alone does **not** promise a repeated create succeeds idempotently or returns the previous result. — [Creation input schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql).
- OAuth `read` is default, `write` permits account writes, and `comments:create`/`issues:create` are narrower creation scopes. `actor=user` is default and resources are created as the authorizing user; `actor=app` creates as the application. PKCE is supported, including token exchange without a mandatory client secret. — [OAuth authentication/scopes/actor](https://linear.app/developers/oauth-2-0-authentication).
- SANE's current initializer treats a nonempty `.sane` without its domain database as incomplete initialization and refuses ordinary init/adoption. Thus adding a cache there first can block later `sane init`. The prior audit also documents strict domain schema checks and ignored App data; this follow-up directly reread the initializer. — [repository.ts](/Users/beto/sane/packages/sane-core/src/repository.ts#L312-L342); [Prior storage audit](../SANE%20issue%20tracking%20integration%20options/codebase.md#2-what-should-own-issue-identity-and-data-without-committing-issues-or-coupling-them-to-workstreams); [App data default](/Users/beto/sane/packages/sane-app/src/app-config.ts#L103).

### Inferences

1. **Small integration:** a native list/detail/status editor calls the authenticated SANE backend; backend uses the public SDK or explicit narrow GraphQL queries. Store an explicit catalog-workspace → Linear organization/team/optional project binding plus credential reference. Display remote workspace/team and acting account before writes. Preserve issue UUID identity, with human identifier/URL for presentation; no automatic SANE workstream/phase changes. — Basis: [API](https://linear.app/developers/graphql), [Issue identity/team schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql), [Prior SANE audit](../SANE%20issue%20tracking%20integration%20options/codebase.md).
2. **Persistence location:** use separate external app-local runtime data, e.g. a small versioned cache/SQLite file under the configured App data directory or an OS application-data directory outside the code checkout. Do not commit copies of remote issues in `.sane`, create `.sane` as a tracker prerequisite, or add tables to `.sane/sane.db`. Package-local `.data` is ignored in this repository according to the prior audit, but is still physically inside a checkout: an outside-checkout app-data directory is stronger protection against accidental Git inclusion. If any in-checkout location is used, verify ignored **and not already tracked**, including WAL/SHM/backups. — Basis: [Initializer](/Users/beto/sane/packages/sane-core/src/repository.ts#L312-L342), [App configuration](/Users/beto/sane/packages/sane-app/src/app-config.ts#L103), [Prior storage/ignore audit](../SANE%20issue%20tracking%20integration%20options/codebase.md).
3. **Cache scope/privacy:** store only needed remote DTO fields with `updatedAt`, per-resource fetch time, scan scope/completeness and last successful refresh. Partition by organization and credential/actor identity, not merely team/project. Keep secrets backend-only in secure credential storage, sanitize logs, provide cache clear/retention, invalidate on disconnect/account/permission changes, and do not treat project filters as authorization. Cached reads cannot detect fresh revocation while offline; document/limit retained sensitive data. The present owner-scoped bridge is not a multi-user permission boundary. — Basis: [OAuth scopes/actors](https://linear.app/developers/oauth-2-0-authentication), [Permission-aware official engine](https://linear.app/blog/rebuilding-delta-sync-read-path), [Prior App auth audit](../SANE%20issue%20tracking%20integration%20options/codebase.md).
4. **Honest read UI:** “Cached · last refreshed 2 minutes ago,” offline/error banner, explicit Refresh/Open in Linear; label partial lists. Use last **successful** fetch, not the last attempted one. Offline previously loaded reads can remain available under the chosen retention policy, but unavailable pages/details must not look like empty current results. — Basis: [Pagination](https://linear.app/developers/pagination), [GraphQL errors](https://linear.app/developers/graphql).
5. **Write lifecycle:** distinguish `draft/unsent`, `sending`, `confirmed`, `failed with a definite validation/auth error`, and `outcome unknown—checking Linear`. UI may optimistically preview a change only with a visible pending badge; promote cache state to confirmed after validated response/refetch. Disable duplicate submit while in flight. On timeout/disconnection after dispatch, the server may have committed the operation before the response was lost: reconcile first, do not blindly retry create/comment/update or mark “not saved.” A bounded local operation-status record is not permission to replay on reconnect. — Basis: [SDK HTTP transport](https://github.com/linear/linear/blob/master/packages/sdk/src/graphql-client.ts), [Mutation success/errors](https://linear.app/developers/graphql).
6. **Uncertain create outcome:** where appropriate generate/persist the supported create UUID before sending and check that identity afterward; for updates compare current remote field values; comments may need identity/content/activity review. Seeing the desired value does not prove this attempt caused it or confer exactly-once attribution. User-confirmed retry is a last resort after explaining uncertainty. Local request IDs can prevent duplicate SANE clicks, not guarantee provider-level idempotence. — Basis: [Create inputs](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql), [Request implementation](https://github.com/linear/linear/blob/master/packages/sdk/src/graphql-client.ts).
7. **Conflicts, especially description replacement:** keep edit-base values and timestamp; refresh before committing and compare relevant fields. If changed remotely, show the new version/diff and offer reload, manual merge, or explicit overwrite. Submit only changed fields; a stale form must not resend the whole cached issue. Description overwrite can destroy another user's work; state-only edits can also replace newer decisions. This check narrows but cannot eliminate the read/write race without a supported atomic precondition; never claim automatic merge or CAS protection. If rich editing complexity is not worth it, start with status/comment actions and open full description editing in Linear. — Basis: [Update input/schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql), [Official offline conflict warning](https://linear.app/docs/get-the-app).
8. **No offline writes:** allow a small explicitly unsent local draft only if useful; show “Draft—will not be sent automatically,” bind it to account/organization/issue and edit-base metadata, and re-fetch/reconfirm before sending online. Draft persistence requires retention/discard UI but not a general operation queue. — Basis: [Official offline overwrite warning](https://linear.app/docs/get-the-app), [Public SDK scope](https://linear.app/developers/sdk).
9. **Attribution and remote reality:** human actions should normally use that human's OAuth user authorization; if shared app credentials are selected, say who/what will appear remotely and do not impersonate the local viewer. Keep read-only controls for insufficient scopes and recheck permissions at write time; scope names alone are not a per-issue authorization guarantee. Refetch after mutations and visible refresh so edits from teammates/Linear/MCP appear; no assumption SANE is the only writer. — Basis: [OAuth actor/scopes](https://linear.app/developers/oauth-2-0-authentication), [Remote MCP writes](https://linear.app/docs/mcp), [Official collaboration warning](https://linear.app/docs/get-the-app).

### Gaps

- No general issue/comment mutation idempotency guarantee, atomic expected-version contract or rich-description conflict-merge guarantee was established. Some unrelated schema operations explicitly document idempotency keys; that must not be generalized to issue writes. Server behavior for duplicate client-supplied issue/comment IDs needs dedicated confirmation before relying on it.
- No offline cache revocation guarantee is possible from the reviewed public contracts. Retention, device protection, app-data lifetime, shared-bridge users and per-user credential ownership are implementation/product decisions.
- OAuth was not configured, no live permissions/attribution were observed, and no UI integration was implemented. Native viewing/editing feasibility is grounded in public API operations and the prior repository audit, not an assertion that SANE already has a Linear panel.
