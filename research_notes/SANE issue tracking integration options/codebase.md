# SANE issue tracking: repository integration audit

## 1. Where can a tracker plug into the App UI, backend, and process lifecycle?

### Takeaway

The current App is a React 19 SPA served by a Bun bridge, with a persisted workspace/worktree navigation catalog and hand-written authenticated HTTP routing. A workspace-scoped Issues feature can be added without involving SANE skills, phase acceptance, or workstream initialization; the smallest coherent extension is a new Issues view plus an issue service behind the existing browser authentication boundary. [Dependencies](../../packages/sane-app/package.json#L11-L40), [navigation contract](../../packages/sane-app/src/catalog-contract.ts#L24-L35), [routing boundary](../../packages/sane-app/src/bridge.ts#L1298-L1320).

### Inferences

- **Minimal native UI seam (proposed):** add `issues` to the navigation contract/backend whitelist; update navigation destination/grouping, `ReadyWorkspace` sidebar, `ShellHeader`, and `ShellContent`; add feature-owned `issues-client.ts`, store/provider, list/detail UI, and stylesheet. Reuse current selected catalog workspace, not active conversation or workstream. A native list/detail screen is likely simpler than vendoring a whole tracker frontend. This follows the explicit shell and contract seams cited above.
- **External tracker UI choices (proposed):** lowest integration cost is an Issues panel with project link/open-in-new-tab; medium is an App-owned list/detail UI calling a backend adapter; iframe embedding is conditional on the tracker allowing framing, compatible cookies/login, absolute asset paths, and navigation behavior. React on both sides does not imply a supported drop-in component library. Do not promise iframe/SSO or mount a full third-party SPA under `/assets` without checking its distribution/auth model.
- **API shape (proposed):** workspace-scoped list/create/get/update/comment routes, typed DTOs, bounded pagination, issue revisions/ETags, idempotent create request IDs, explicit error mapping, and validated provider-specific project binding. Query every issue by both issue ID and workspace ID to prevent cross-workspace access. Use existing browser boundary unchanged; keep remote provider tokens backend-only.
- **Lifecycle (proposed):** initially let the operator manage an external tracker independently, just as the current OpenCode adapter only discovers/connects. Hosting Docker/database/server processes under App supervision is a separate operational feature, not an implied part of adding an issue adapter. A local issue service can open after ownership acquisition, refuse mutations during closing, flush/close before locks release, and isolate tracker failure from assistant admission where possible.

### Gaps

- No runtime/UI/browser verification was requested or performed. Third-party frame headers, cookies, login flows, and actual embedding feasibility remain unverified.
- No ready-made embeddable issue-tracker library or vendor API compatibility is established by this repository audit; the other researchers must substantiate external candidates, licenses, deployment cost, and maintenance status.
- Current App setup depends on native-source store configuration even though an issue feature need not depend on either harness; this audit does not establish a standalone tracker-only App launch mode. [Startup validation](/Users/beto/sane/packages/sane-app/src/bridge.ts#L149-L172).

## 2. What should own issue identity and data, without committing issues or coupling them to workstreams?

### Takeaway

Use catalog workspace identity for the initial feature, with issues shared across a repository's worktrees and supported for plain-directory workspaces. The safest initial local storage is a separate issue database under the App's existing ignored data directory, not new tables in `.sane/sane.db`; merely putting issue files in an otherwise uninitialized `.sane` would currently block future SANE initialization. [Catalog identity](/Users/beto/sane/packages/sane-app/src/catalog.ts#L91-L109), [App storage](/Users/beto/sane/packages/sane-app/src/app-config.ts#L101-L109), [schema strictness](/Users/beto/sane/packages/sane-core/src/schema-upgrade.ts#L21-L28), [initialization guard](/Users/beto/sane/packages/sane-core/src/repository.ts#L312-L342).

### Cited Findings

- **Workspace versus worktree:** catalog has stable UUID workspace IDs, `repository` or `directory` kind, common Git directory, and per-worktree UUID/root/gitDir/bindingRevision. Git workspaces are grouped by canonical commonDir; directory workspaces by directory root. Each discovered tree receives a distinct ID and revision; registration also discovers Git worktrees. This is not a repository URL or branch-name identity. [Types](/Users/beto/sane/packages/sane-app/src/catalog-contract.ts#L24-L35), [discovery/grouping](/Users/beto/sane/packages/sane-app/src/catalog.ts#L78-L133).
- **Filesystem identities are pinned:** catalog refuses changed repository/worktree device/inode identities during add and revalidates root/gitDir/commonDir identities for binding access. A moved/replaced checkout is not silently adopted. [Add](/Users/beto/sane/packages/sane-app/src/catalog.ts#L102-L108), [bindings](/Users/beto/sane/packages/sane-app/src/catalog.ts#L146-L158).
- **Browsing and execution are intentionally separate:** navigation can select one workspace/worktree while a conversation retains another immutable execution association. The UI explains the mismatch and offers browse-execution-worktree; follow-ups retain original cwd/harness. Agent issue operations cannot safely infer target workspace from what the human is browsing. [Contract](/Users/beto/sane/packages/sane-app/src/catalog-contract.ts#L13-L21), [UI](/Users/beto/sane/packages/sane-app/frontend/app.tsx#L206-L218), [fixed execution explanation](/Users/beto/sane/packages/sane-app/frontend/app.tsx#L253-L261), [immutable association](/Users/beto/sane/packages/sane-app/src/catalog.ts#L194-L207).
- **Catalog IDs are App-store local:** `catalog.json` and `navigation.json` live in selected `dataDir`, initially empty; App manifest has its own `storeId` UUID. Newly initialized App data creates fresh IDs and no workspaces. Separately, admission records distinguish `app-only` bindings from repository-domain bindings. [Store records](/Users/beto/sane/packages/sane-app/src/app-store.ts#L9-L20), [initial records](/Users/beto/sane/packages/sane-app/src/app-store.ts#L235-L252).
- **App data is JSON plus journals:** required manifest/sources/admissions/metadata/catalog/navigation JSON files are validated on startup; run events are persisted as per-run JSONL; optional worker and agent state use versioned JSON records. Atomic JSON publication uses exclusive 0600 temp files, fsync, rename, and directory fsync. [Validation/publication](/Users/beto/sane/packages/sane-app/src/app-store.ts#L189-L233), [run journal](/Users/beto/sane/packages/sane-app/src/bridge.ts#L522-L553), [optional store](/Users/beto/sane/packages/sane-app/src/worker-store.ts#L8-L16), [optional agents](/Users/beto/sane/packages/sane-app/src/app-store.ts#L172-L187).
- **Project `.sane` is not global:** repository discovery resolves the primary checkout from Git worktree/common-directory evidence and sets `stateRoot = <primaryCheckout>/.sane`, `databasePath = .sane/sane.db`. Linked worktrees resolve the primary's state, not separate per-branch issue ledgers. Repository domain has its own generated UUID, different from catalog workspace ID. [Discovery](/Users/beto/sane/packages/sane-core/src/repository.ts#L32-L55), [domain UUID/init](/Users/beto/sane/packages/sane-core/src/repository.ts#L330-L353), [context type](/Users/beto/sane/packages/sane-core/src/contracts.ts#L26).
- **Storage namespaces are distinct:** default App store is `<packageDir>/.data`, configurable by dataDir; native CC profile defaults to `~/.claude`, OC registration to XDG state `opencode/service.json`; context-package installation uses home `.config/opencode`, `.agents/skills`, and `.claude/skills`. The inspected implementation does not establish a home-level `~/.sane` issue-store convention. [App/native defaults](/Users/beto/sane/packages/sane-app/src/app-config.ts#L101-L109), [home installation](/Users/beto/sane/packages/sane-cli/src/install-sane-agent-context-packages.ts#L154-L208).
- **`.sane/sane.db` is a capability-checked domain database:** Bun SQLite, WAL/foreign keys/recursive triggers, strict schema object and definition matching. Adding arbitrary issue tables would cause `CORRUPT_STORE`; it requires an explicit domain schema feature/migration if pursued. Do not casually extend this DB for generic tracker data. [SQLite setup](/Users/beto/sane/packages/sane-core/src/repository.ts#L343-L350), [exact schema validation](/Users/beto/sane/packages/sane-core/src/schema-upgrade.ts#L9-L28), [explicit upgrades](/Users/beto/sane/packages/sane-core/src/repository.ts#L312-L323).
- **Critical `.sane` coexistence risk:** nonempty `.sane` without `sane.db` is treated as incomplete initialization; initializer permits only its own initializing marker before creating DB. Therefore creating `.sane/issues.db` or `.sane/issues/` first will block ordinary later `sane init` under the current contract. Reusing the directory is possible only after domain initialization or with an intentional namespace/init-contract change. [Inspection](/Users/beto/sane/packages/sane-core/src/repository.ts#L312-L328), [exclusive init](/Users/beto/sane/packages/sane-core/src/repository.ts#L330-L342).
- **Issue data can be untracked here:** root `.gitignore` excludes `/.sane/`, `/.sane-app-daily/`, `/.sane-app-dev/`, and `.data-fresh`; package `.gitignore` excludes `.data`, `.config.json`, `.runtime`, locks, and assets. Read-only `git check-ignore -v` confirmed hypothetical `.sane/issues.db`, `.sane/issues.db-wal`, and `packages/sane-app/.data/issues.db` match those rules; `git ls-files` returned no tracked files for `.sane`, App `.data`, `.config.json`, or research_notes. Ignore is convention, not a security barrier against forced add or other repositories lacking rules. [Root ignore](/Users/beto/sane/.gitignore#L1-L12), [package ignore](/Users/beto/sane/packages/sane-app/.gitignore#L1-L10).
- **Ordinary filesystem APIs cannot expose `.sane` or App data:** workspace root/path validation excludes `.git`/`.sane`, protected Git paths, and canonical App-data subtree. Native Issues APIs must read through a dedicated service, not the file editor route. [Protection](/Users/beto/sane/packages/sane-app/src/workspace.ts#L78-L101), [catalog protection](/Users/beto/sane/packages/sane-app/src/catalog.ts#L78-L100).
- **Workstream APIs are an unsuitable initial dependency:** `RepositoryRouter` rejects plain directories, inspects initialized domain stores, enforces expected repository UUID, and returns null for `app-only` admissions. A generic tracker should not require `router.forWorkspace` or call `router.initialize`. [Domain router](/Users/beto/sane/packages/sane-app/src/workstreams.ts#L83-L119), [app-only execution](/Users/beto/sane/packages/sane-app/src/workstreams.ts#L139-L159), [explicit workstream init route](/Users/beto/sane/packages/sane-app/src/bridge.ts#L1399-L1405).

### Inferences

- **Recommended initial tenancy (proposed):** one App-owned issue database at `<dataDir>/issues.db`, with workspaceId on every issue, comment, label/project-setting record, plus globally unique issue ID and per-workspace display number. Catalog workspace UUID is sufficient inside one App store; include storeId in external mapping/export provenance when data may be merged or transferred. WorktreeId is optional context/link metadata, not the issue's tenant key. Do not reset issue lists when only worktree selection changes.
- **Read availability (proposed):** issue metadata stored in App data can remain readable even if every checkout disappears. Validate that workspace is registered with `catalog.registered`, which is explicitly metadata-only, rather than demanding a filesystem binding for every list/read. Require an available validated binding only for file/checkouts/actions that actually touch a workspace. [Metadata-only lookup](/Users/beto/sane/packages/sane-app/src/catalog.ts#L179-L192).
- **Cross-install/machine data (proposed):** App catalog IDs are not portable repository identity. If sharing issues across multiple App installs is required, prefer an external server project ID or a separate durable issue-space UUID with an explicit binding registry. Never derive tenant identity solely from repo basename, selected branch, arbitrary remote URL, or worktree path. RepositoryId can be an optional verified linkage when `.sane` exists, but must not gate creating issues for an uninitialized Git repo or plain directory.
- **JSON alternative (proposed):** versioned `issues.json` with serialized, revision-checked writes through the atomic publication helper is consistent for a very small prototype. SQLite is preferable once comments, search/filtering, activity history, concurrent edits, or pagination exist. Use a separate schema/version lifecycle; App ownership permits one writer but browser callers still need optimistic concurrency and atomic update semantics.
- **If `.sane` reuse is desired (proposed):** keep tracker data in a separate database, e.g. `.sane/issues.db`, never add arbitrary tables to `sane.db`. For initialized repos this reduces App-store coupling, but different Apps/CLI writers then require proper shared-database coordination. For uninitialized repos revise namespace initialization carefully first; do not auto-initialize SANE to obtain a folder. A separate OS application-data root is a safer option when issue state must survive App reinstall without altering repository domain behavior.
- **No-commit guarantee (proposed):** external server/GitHub persistence or OS application-data storage avoids repository files entirely. App `.data` or `.sane` is runtime state physically inside a checkout but excluded from Git here; if used elsewhere, verify ignored AND not already tracked before creating data, cover SQLite WAL/SHM/backups/attachments, and avoid repository export files by default. No ignore rule alone prevents `git add -f`.
- **Future linkage (proposed):** independent `issue_links` records can carry optional `{repositoryId, workstreamId}`, `{storeId, appSessionId}`, qualified `{harness, authorityId, nativeId}`, optional worktree/file, or external provider references. Issue status and comments remain independent. Explicit user action may later start a workstream from an issue or attach a conversation; deleting/closing/linking an issue must not implicitly approve phases, complete jobs, or change acceptance.

### Gaps

- Whether issues should follow a single App installation, local repository across Apps, or team/server project across machines is a product decision; these have materially different identity and backup designs.
- No generalized issue-space mapping, credential vault, multi-user RBAC, or tracker DB migration mechanism was found in the audited App surfaces. Proposed names/files/schema are extension designs, not existing functionality.
- Runtime `.data`, `.sane`, and config contents were deliberately not read for credentials or live issue data. No secrets are included here.

## 3. Which architectures fit the three effort tiers, optional harness tools, and GitHub Issues?

### Takeaway

External-server adapters and native local storage can share one small App-owned issue contract; harness tools are an optional access layer over either, not a reason to bind issues to SANE workflows. Existing OC plugin and CC MCP/hook infrastructure provides patterns, but its current caller/domain machinery assumes initialized Git repositories and often enrollment, so it must not be reused unchanged for general workspace issue operations. [OC plugin](/Users/beto/sane/opencode/plugins/sane/index.ts#L23-L59), [CC MCP](/Users/beto/sane/packages/sane-cli/src/native-claude-mcp.ts#L10-L30), [domain requirement](/Users/beto/sane/packages/sane-cli/src/native-caller.ts#L18-L48).

### Cited Findings

- **Native harness integration already exists independently of rendering:** OC `Plugin.define` registers tools through `ctx.tool.transform`, context hooks, and execute hooks. It reads each actual session ID when applying session-bound SANE context, rather than blindly applying plugin location context to children. [Plugin setup](/Users/beto/sane/opencode/plugins/sane/index.ts#L9-L32), [tools](/Users/beto/sane/opencode/plugins/sane/index.ts#L34-L59), [shell hook](/Users/beto/sane/opencode/plugins/sane/index.ts#L60-L72). Official V2 plugin docs likewise expose tools/transforms/hooks and caution that plugin location is not every session's location. [OpenCode V2 plugin guide](https://opencode.ai/v2/docs/build/plugins).
- **OC caller qualification is strong but Git-coupled:** verifies callback session/message/tool IDs, managed registration source, service process identity/loopback endpoint, local and remote session directory and parent agreement; then calls `discoverRepository(cwd)` and gathers repository-local ancestors. Plain directories therefore cannot pass this exact qualifier. [Qualifier](/Users/beto/sane/packages/sane-cli/src/native-opencode.ts#L27-L55).
- **CC tools use stdio MCP plus hook-injected invocation tokens:** MCP lists workers, handoff/status, link/context, and consumes a bound invocation. `native-configuration.ts` generates plugin settings, MCP stdio settings, and PreToolUse matcher. Token issuance binds tool name, canonical input, caller identity, and expiration; consumption is one-use. Adding native issue names to this mechanism requires updating its hard-coded tool list, matcher, dispatch, schemas, and install closure as needed. [MCP](/Users/beto/sane/packages/sane-cli/src/native-claude-mcp.ts#L10-L30), [configuration](/Users/beto/sane/packages/sane-cli/src/native-configuration.ts#L3-L14), [tokens](/Users/beto/sane/packages/sane-cli/src/native-claude.ts#L7-L59), [distributed source closure](/Users/beto/sane/packages/sane-cli/src/install-sane-agent-context-packages.ts#L62-L64).
- **CC native qualification is not itself workstream qualification:** hook validation obtains actual session/cwd/tool identity from a selected profile and rejects child agent identity as not a qualified resumable conversation. Repository discovery/enrollment happens downstream in `openNativeCaller`, where ready domain and enrollment are required. Thus identity qualification and workflow authorization can be separated deliberately. [Hook caller](/Users/beto/sane/packages/sane-cli/src/native-claude.ts#L27-L33), [domain open/enrollment](/Users/beto/sane/packages/sane-cli/src/native-caller.ts#L18-L48).
- **Two different hook purposes must not be conflated:** App run forwarding sends lifecycle events to loopback using run ID and per-run secret, is observational/fail-open, and always exits zero. Native MCP PreToolUse is used to qualify/inject invocation identity. Hooks alone are not an existing generic issue CRUD API, nor should an observed Stop/tool completion automatically close an issue. [App forwarding](/Users/beto/sane/packages/sane-app/hooks/forward.ts#L1-L19), [App hook event set](/Users/beto/sane/packages/sane-app/src/claude-run-service.ts#L13-L23), [native matcher](/Users/beto/sane/packages/sane-cli/src/native-configuration.ts#L3-L14).
- **Existing native App boundary is separate from cookies:** ephemeral loopback listener has `/native/handoffs`, `/native/workers`, and hooks; handoff/worker HTTP checks POST, no browser Origin, and bearer token. `native-handoff.json` is published privately in dataDir. The browser auth class expressly excludes native bearer/hook boundaries. New native issue routes require their own deliberate authorization, not browser cookies or relaxed Origin checks. [Token boundary](/Users/beto/sane/packages/sane-app/src/bridge.ts#L363-L365), [worker boundary](/Users/beto/sane/packages/sane-app/src/bridge.ts#L934-L955), [listener/connection file](/Users/beto/sane/packages/sane-app/src/bridge.ts#L2290-L2296), [boundary contract](/Users/beto/sane/packages/sane-app/src/bridge-auth.ts#L19-L20).
- **Handoff transport offers a connection-file pattern, not drop-in issue semantics:** it checks an absolute same-user 0600 regular file, pinned loopback URL/path/token/pid, and sends bounded bearer-auth JSON. But before that it opens the repository domain/enrolls for kickoff; ordinary handoff/status needs existing enrollment. Copy its transport security pattern, not `handoffNativeCaller` as issue authorization. [Client](/Users/beto/sane/packages/sane-cli/src/native-handoff.ts#L44-L64).
- **SANE workflow context is optional and distinct:** App only creates framework/session context for allowlisted SANE identities; `saneSessionText` returns null if no stored SANE context. Router execution returns null workstream/artifact roots for app-only admissions. Therefore an issue access feature can be offered to a base/non-SANE assistant without adding skills, phase claims, or acceptance gates. - **Existing adapter safety precedent:** OC endpoint and credentials are kept together; outbound requests reject redirects, have timeouts, invalidate bad connections, and never automatically replay mutations. This is a useful external-tracker adapter pattern, but no generalized tracker credential manager is present in these files. ### Inferences

#### Tier A — external tracker server plus App adapter/UI (proposed)

- Deploy whichever independently verified open-source tracker meets the parent research criteria as a separate service, outside repo versioned content; operator owns its database, backups, upgrades, and authentication. Start with a workspace-to-provider-project mapping and an Issues navigation entry with project link. Add native App list/detail/create/edit UI only if needed; never assume a complete tracker is an embeddable npm UI library.
- Add an App-local `IssueProvider`/adapter interface covering list/get/create/update/comment (status/labels only initially), provider capabilities, stable opaque IDs, project binding, and pagination. Keep provider-native fields separate from portable fields; do not homogenize every Jira/Linear concept up front. Backend holds credentials and validates configured service URL/allowed destination to avoid SSRF, rejects redirects, times out, and does not blind-retry uncertain writes. Bind an immutable remote project ID, not just a URL/slug.
- This has lower domain-code burden but potentially higher deployment burden. Iframe may reduce UI implementation only when vendor framing/auth is verified; a backend adapter plus small SANE UI avoids cross-origin credentials but introduces synchronization/permission expectations. Shared App bearer credentials mean all App users can act as that credential unless a new per-user authorization layer is added.
- Minimal extension points: shell/navigation locations in section 1; issue route/service/provider files under `packages/sane-app/src`; private mapping under dataDir. Configuration is strictly key-validated, so a new saved `issueProviders` field requires deliberate AppConfig/parser/version compatibility work or a separately versioned optional integration record. [Strict config](/Users/beto/sane/packages/sane-app/src/app-config.ts#L9-L22), [top-level whitelist](/Users/beto/sane/packages/sane-app/src/app-config.ts#L60-L61).

#### Tier B — library/native embedded UI and storage (proposed; recommended for simple local tracking)

- Implement narrow native React issue list/detail/edit UI and App-owned separate SQLite store in dataDir. Leverage existing Markdown rendering and app styling. Use reusable OSS UI primitives where suitable, but pick a full tracker library only if its maintained package exposes a genuine supported component/storage API; none is evidenced here.
- Initial data: UUID issue ID, workspaceId, local display number, title, Markdown description, status (`open`, `in_progress`, `closed`), optional priority/labels, timestamps, revision; separate comments/activity and optional relation records. No sprints, epics, acceptance documents, skills, workstream creation, or harness dependencies initially. One workspace across worktrees; no mandatory Git domain. A JSON-only prototype is an alternate shorter implementation with later migration cost.
- Preserve backup/export/import and workspace/store identity from the beginning. Local-only storage is simplest when ownership is one App; cross-App use needs a shared authoritative issue-space identity and concurrent-writer design. Merely adding a DB path under `.sane` does not solve this, and causes the initializer conflict documented in section 2.
- Minimal extension points: same UI/routes as Tier A, plus separate `issue-store.ts`/contract and close/drain hooks; use current App ownership and private-file conventions. Keep `sane-core` workstream schema untouched. A provider-shaped contract can later allow external/GitHub alternatives without requiring a multi-provider platform at first launch.

#### Tier C — optional OC/CC/MCP/hooks access layer (proposed; additive to A or B)

- Expose explicit tools such as `issue_list`, `issue_get`, `issue_create`, `issue_update`, and `issue_comment` over the exact same issue service. Keep reads/writes distinct, bound output/context size, and honor harness permissions. Tools are useful without SANE skills or workstream acceptance. Tool implementation should not invoke `sane_link` or initialize `.sane` as a hidden prerequisite.
- Simplest portable route: a standalone issue MCP server with an explicitly selected workspace/issue-space binding and App connection, usable by both harnesses. Stronger automatic scope route: OC plugin resolves the caller's actual session directory; CC PreToolUse token pattern supplies actual cwd/session. Build a generic workspace qualifier that maps validated session execution location to catalog identity but does not call `openNativeCaller` or Git-only `qualifyOpenCodeCaller` unchanged. Never trust model-supplied cwd/workspaceId by itself.
- A dedicated `/native/issues` endpoint on the private listener can reuse the connection-file/bearer pattern, with separately scoped credentials/caller checks. Don't reinterpret handoff/worker authority or expose a raw entire App token to untrusted plugins unnecessarily. External tracker MCP can be used directly for agent access, but project scope must match App mapping and agent permissions; it does not automatically create an integrated App issue panel.
- Hooks can optionally refresh linked-issue summaries or append explicit activity events, but should not infer done/closed from assistant text, Stop, or tool exit. Native harness tool access is an execution capability; SANE issue-to-workstream linkage is a later product semantic feature. No skill/context changes are required for initial tracking.

#### GitHub Issues alternative (proposed)

- Treat GitHub as another external provider rather than implementing sync with a second local source of truth. Add explicit workspace → GitHub repository binding, backend list/get/create/edit/comment adapter and browser project/deep links. Issues themselves remain on GitHub, not in Git commits; local mapping/cache/credentials remain private runtime state.
- Do not automatically choose the first Git remote: this App supports directory workspaces, multiple worktrees, immutable filesystem pins, and nested repositories; repository ownership/visibility/access must be explicit. IDs should include provider host and stable repository/issue identity, with issue number only a display key. Repo-private/team authorization, app/PAT or `gh` credential handling, rate limits, pull-request exclusion, and project-board behavior require separate external verification.
- Direct `gh` or GitHub MCP may suffice for optional harness operations with little SANE code, while a workspace-linked App panel is additional adapter/UI work. Generic tracker tools should remain usable by base/non-SANE agents. This audit does not verify `gh` presence/auth or existing GitHub MCP configuration, and ran no native-service probes.

### Gaps

- Effort order is architectural, not a measured estimate. External deployment simplicity depends on selected product; a link-out-only integration can be smallest, while a full native CRUD UI can be smaller overall than running a large tracker stack for one person.
- Candidate API licensing/embedding rights, full server versus library packaging, official MCP coverage, GitHub auth/rate-limit contracts, and current vendor maintenance must come from other research sources. No external product recommendation is inferred from local dependency names.
- Native integration scopes do not currently demonstrate plain-directory issue qualification. Supporting these safely is new work, not a built-in capability of the existing SANE native tools.
