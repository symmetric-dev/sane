# Lightweight and embedded issue tracking for SANE

Research snapshot: 2026-10-05. Scope is a simple, independently usable workspace issue tracker inside sane-app, with project data outside Git (an ignored `.sane/` is acceptable), no mandatory workstream/skill acceptance, and only optional future SANE links. This is source/document inspection, not installation, execution, tests, or browser verification. Recommendations below are architectural judgments, not measured integration costs.

## 1. What can genuinely be embedded as a library, rather than mistaken for a tracker SDK?

### Takeaway

The strongest practical embedded approach is a **custom thin issue domain backed by SQLite plus an open-source React board/drag-and-drop library**. No mature, permissively licensed npm package providing the complete local issue domain, storage, board, project isolation, and agent tools was verified; the real reusable issue-domain libraries found are Rust crates with significant caveats.

### Cited Findings

**React UI building blocks — genuinely embeddable, not full trackers**

- **`@caldwell619/react-kanban`** is an actual npm React/TypeScript board library, MIT licensed, latest registry version `0.0.12`. It exports `ControlledBoard`, `UncontrolledBoard`, board/card types, and state helpers including `moveCard`. Custom cards can extend its `Card` interface. Controlled mode leaves state ownership to the host application, making it suitable for persisting mutations through SANE's own backend. It does **not** document an issue database, ticket service, tenancy, comments service, or MCP surface. — [README and usage](https://github.com/christopher-caldwell/react-kanban); [package metadata](https://registry.npmjs.org/@caldwell619/react-kanban/latest)
- Its peers are React and React DOM `>=16`, and `@hello-pangea/dnd >=16`; these must be installed by the host. Upstream `asseinfo/react-kanban` was forked because it appeared unmaintained; the fork's own repository was last pushed 2025-02-03, had 62 stars, and was not archived at this snapshot. Prefer this over assuming the original is maintained, but maintenance confidence remains modest. React-version compatibility is declared, not verified here. — [README](https://github.com/christopher-caldwell/react-kanban); [repository metadata](https://api.github.com/repos/christopher-caldwell/react-kanban)
- **dnd-kit** is an MIT React drag-and-drop toolkit, not a ready-to-use issue tracker or finished Kanban product. It offers draggable/droppable hooks, `DndContext`, a sortable preset, keyboard/pointer/touch sensors, and customizable accessibility behavior. The repository dates to 2020, had 17,694 stars, and was pushed 2026-09-12; this is a substantially stronger maturity signal than the small tracker prototypes. — [README](https://github.com/clauderic/dnd-kit); [license](https://github.com/clauderic/dnd-kit/blob/master/LICENSE); [repository metadata](https://api.github.com/repos/clauderic/dnd-kit)
- The classic `@dnd-kit/core` registry package is version `6.3.1`, MIT, with React/React DOM peers `>=16.8.0` and dependencies on `tslib`, `@dnd-kit/utilities`, and `@dnd-kit/accessibility`. Use deliberate package-family/version selection; repository activity does not by itself prove the classic package is the latest architectural direction. — [npm metadata](https://registry.npmjs.org/@dnd-kit/core/latest)
- **`@libxai/board` is not an uncomplicated open-source alternative.** It is a genuine importable React component package (`KanbanBoard`, `GanttBoard`, ESM/CJS/types/style exports), but current npm metadata says `BUSL-1.1`, version `1.9.45`. Its dependency list is large: dnd-kit, Framer Motion, Recharts, jsPDF, html2canvas, xlsx, Markdown packages, AI-provider SDKs, and `@libxai/core`, plus React 18 and `ai ^4` peers. This is not the lightweight, permissive board choice it may appear to be from search descriptions. — [README](https://github.com/libxai/libxai-suite); [npm metadata](https://registry.npmjs.org/@libxai/board/latest)
- LibXAI's repository license expressly says Business Source License is **not an Open Source license** and grants non-production use, with an Apache-2.0 change date of 2027-10-12. The file still describes ASAKAA v0.4.0 while the package is LibXAI v1.9.45: resolve version-specific licensing with the maintainer rather than extrapolating the change date to all versions. Repository default branch is unusually `feature/time-tracking`, and metadata showed one star. — [actual license](https://github.com/libxai/libxai-suite/blob/feature/time-tracking/LICENSE); [repository metadata](https://api.github.com/repos/libxai/libxai-suite)

**Storage library — truly reusable, but no issue features**

- **`better-sqlite3`** is an MIT npm SQLite binding for Node.js with explicit file-path construction, transactions, prepared statements, WAL configuration, worker-thread support, and an online backup API in its documentation. It is not an issue tracker or synchronizer. The latest registry package at this snapshot was `13.0.3`, requiring Node `>=22` and depending on `node-addon-api`; native/prebuilt binary packaging must be considered, especially if the host is Electron or another embedded runtime. — [README](https://github.com/WiseLibs/better-sqlite3); [npm metadata](https://registry.npmjs.org/better-sqlite3/latest); [API docs](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)
- SQLite concurrency is bounded: the README recommends appropriate indexes and WAL, and warns against very high concurrent write volumes. That is compatible with the proposed single-workspace/local-use scope, but not evidence of distributed synchronization. — [README concurrency guidance](https://github.com/WiseLibs/better-sqlite3)

**Actual Rust issue-domain interfaces — not npm SDKs**

- **`beads_rust`** genuinely publishes a library surface: `model` contains Issue/Dependency/Comment/Event, `storage` is the SQLite layer, and `sync`, `config`, `policy`, etc. are public. However its exported `run()` is currently a no-op returning `Ok(())`; embedding requires using specific domain/storage APIs, not assuming calling `run()` embeds the tracker. There is no verified JavaScript binding or Node SDK. — [library source](https://github.com/Dicklesworthstone/beads_rust/blob/main/src/lib.rs); [crate docs](https://docs.rs/beads_rust/latest/beads_rust/)
- This crate is currently `0.7.4` and uses the pure-Rust **FrankenSQLite (`fsqlite 0.4.7`)**, Asupersync, Rich Rust, TOON, and optional FastMCP/self-update components. Do not describe current main as a thin wrapper over standard `rusqlite`; its storage engine and dependency family have evolved. The README recommends a pinned nightly for installation despite `rust-version = 1.89` in its manifest. Most importantly, its restrictive license rider is a blocking concern; see question 2. — [Cargo.toml](https://github.com/Dicklesworthstone/beads_rust/blob/main/Cargo.toml); [README](https://github.com/Dicklesworthstone/beads_rust); [LICENSE](https://github.com/Dicklesworthstone/beads_rust/blob/main/LICENSE)
- **LineAgent** genuinely has an explicit Rust library target. `src/lib.rs` states downstream users can reuse domain services without spawning the process, exposing `core`, `storage`, `auth`, `api`, `mcp`, `config`, etc.; the architectural layers place ticket/comment/label/status/search below transports. That is a real headless issue-domain candidate, not merely a CLI with an npm install command. — [library source](https://github.com/deepfounder-ai/LineAgent/blob/main/src/lib.rs); [Cargo.toml](https://github.com/deepfounder-ai/LineAgent/blob/main/Cargo.toml)
- LineAgent is only `0.1.0`, created 2026-06-11, with two stars and last push 2026-06-18. It uses Tokio/Axum, SQLx SQLite, authentication libraries, and Reqwest, and lacks a human-oriented UI by its own description. Its manifest says Apache-2.0, but GitHub reports `NOASSERTION`, and the LICENSE includes the anomalous sentence “For avoidance of doubt, no patent license is granted by this License” despite the earlier patent grant. **Clarify the actual license before reuse rather than calling it clean standard Apache-2.0.** — [README](https://github.com/deepfounder-ai/LineAgent); [metadata](https://api.github.com/repos/deepfounder-ai/LineAgent); [manifest](https://github.com/deepfounder-ai/LineAgent/blob/main/Cargo.toml); [license text](https://github.com/deepfounder-ai/LineAgent/blob/main/LICENSE)

### Inferences

- Best embedded shortlist: **(1) SANE-owned issue model + SQLite + dnd-kit**, for maximal control and established primitives; **(2) the same backend + `@caldwell619/react-kanban`**, if an existing board component is worth its maintenance risk. Neither is “reuse a finished tracker”; both are explicitly custom builds. — Basis: [dnd-kit](https://github.com/clauderic/dnd-kit); [controlled board API](https://github.com/christopher-caldwell/react-kanban); [SQLite API](https://github.com/WiseLibs/better-sqlite3)
- Treat LineAgent as a **research/prototype Rust domain reuse option**, not the default: real library interface, but very young and licensing needs clarification. Do not select beads_rust as the clean OSS library answer merely because its badge begins with MIT. — Basis: [LineAgent library](https://github.com/deepfounder-ai/LineAgent/blob/main/src/lib.rs); [LineAgent license](https://github.com/deepfounder-ai/LineAgent/blob/main/LICENSE); [beads_rust license](https://github.com/Dicklesworthstone/beads_rust/blob/main/LICENSE)

### Gaps

- No production-ready headless npm issue-domain package meeting all requirements was verified in this bounded search. This is not proof that none exists.
- SANE's runtime and existing database choices were not inspected; `better-sqlite3` is a conditional Node-backend suggestion, not a verified dependency choice for sane-app.
- No bundle measurements, dependency audits, accessibility tests, peer-compatibility tests, or native packaging verification were performed.

## 2. Can local CLI trackers operate without committing project artifacts or installing workflow requirements?

### Takeaway

**Yes, current Beads documents supported Git-free isolation**, and beads_rust supports disabling automatic JSONL import/export while redirecting storage. However current Beads is Dolt-based and workflow-oriented, while current beads_rust carries a discriminatory license rider; neither should be presented as a minimal, permissively licensed SQLite npm tracker.

### Cited Findings

**Beads (`bd`, Go) — supported isolation, but substantial domain/engine**

- Current README calls Beads a distributed graph issue tracker powered by Dolt. Embedded Dolt is now the default, data in `.beads/embeddeddolt/`, **single writer**. Server mode uses a separate `dolt sql-server` for multiple concurrent writers. SQLite is legacy, not the current default. `.beads/issues.jsonl` is an interchange/viewer export, explicitly not the source of truth or a backup. — [README storage modes](https://github.com/gastownhall/beads#-storage-modes); [Dolt architecture](https://github.com/gastownhall/beads/blob/main/docs/architecture/dolt.md)
- Cross-machine synchronization ordinarily uses `bd dolt push`/`pull`, targeting `refs/dolt/data` on the Git remote. These are not ordinary tracked working-tree issue files, but still constitute **repository-associated issue data**, undesirable as the default here. Dolt's internal commits and branches are database history, not necessarily source-repository commits; distinguish the two. — [README storage modes](https://github.com/gastownhall/beads#-storage-modes); [architecture](https://github.com/gastownhall/beads/blob/main/docs/architecture/dolt.md)
- **Supported Git-free mode:** set `BEADS_DIR` to an explicit database directory and run `bd init --quiet --stealth`. The README says `BEADS_DIR` bypasses Git repository discovery and stealth sets `no-git-ops: true`, disabling Git operations and hook installation. It says core create/ready/update/prime/close commands work with zero Git calls. This is stronger evidence than simply telling users “don't commit the files.” — [Git-Free Usage](https://github.com/gastownhall/beads#-git-free-usage)
- Normal `bd init` creates/updates `AGENTS.md` and installs project Claude/Codex integrations by default, unless `--skip-agents` or `--stealth` is passed. Never use default initialization inside a SANE workspace for this requirement. Also avoid `bd setup`, which intentionally installs agent guidance/hooks. — [README initialization notes](https://github.com/gastownhall/beads#-quick-start)
- Beads has JSON CLI commands, dependency-aware ready work, claim/close operations, relationship graphs, and ecosystem tools; README links a Python `beads-mcp` distribution. `@beads/bd` is an **npm-distributed executable installer/launcher**, not a reusable JS issue-domain package: registry metadata lists `bin: {bd: "bin/bd.js"}`, `main: "bin/bd.js"`, and a binary-install `postinstall` script. — [README](https://github.com/gastownhall/beads); [npm package metadata](https://registry.npmjs.org/@beads/bd/latest)
- Beads metadata identifies MIT, 27,647 stars, creation 2025-10-12, and a 2026-10-05 push. Current npm distribution was `1.3.1`. Embedded mode includes Dolt in the `bd` binary; no separate Dolt installation is required until server mode. Large adoption is not evidence that its architecture is minimal. — [repository metadata](https://api.github.com/repos/gastownhall/beads); [npm metadata](https://registry.npmjs.org/@beads/bd/latest); [Dolt deployment modes](https://github.com/gastownhall/beads/blob/main/docs/architecture/dolt.md)

**beads_rust (`br`) — repository-friendly defaults can be disabled, license cannot be ignored**

- The default architecture remains SQLite + `.beads/issues.jsonl`. Successful mutations auto-flush JSONL, and normal commands auto-import changed local JSONL before running. The documented defaults are `sync.auto_flush: true`, `sync.auto_import: true`, `sync.history_enabled: true`, with bounded JSONL history under `.beads/.br_history`. Documentation encourages manually staging/committing `.beads/`; therefore “local-first” does not imply “issues stay out of Git by default.” — [README storage and configuration](https://github.com/Dicklesworthstone/beads_rust)
- **Supported opt-outs:** `--no-auto-flush` / `--no-auto-import`, or persistent `sync.auto_flush: false` / `sync.auto_import: false`; `history_enabled` is configurable. `BEADS_DIR` selects the data directory; `--db`, `BD_DB`/`BD_DATABASE`/`BEADS_DB` override database path. These allow a private `.sane/issues/` or external workspace-data directory rather than tracked `.beads/`. Do not use `--no-db`: that is JSONL-only, the opposite of the desired database-first design. — [README global flags, configuration, environment variables](https://github.com/Dicklesworthstone/beads_rust)
- Normal issue/sync workflows do not auto-commit, push, pull, install hooks, or run a daemon. Still, the README qualifies “non-invasive”: `br init` can update the project's `.gitignore`; config commands edit config, and some reporting commands inspect Git. SANE should own explicit storage location/init choices rather than trusting the blanket non-invasive slogan. — [README Non-Invasive Design](https://github.com/Dicklesworthstone/beads_rust)
- An optional build feature `mcp` adds stdio MCP (`br serve`), sharing SQLite, JSONL, locks, audit events, and sync controls with the CLI. It does not listen on a network port or run Git, and exposes issue tools/resources. JSON/TOON CLI is also available. — [README MCP support](https://github.com/Dicklesworthstone/beads_rust); [manifest feature flags](https://github.com/Dicklesworthstone/beads_rust/blob/main/Cargo.toml)
- **Critical licensing:** LICENSE is “MIT License (with OpenAI/Anthropic Rider).” It denies rights to OpenAI/Anthropic and affiliates/parties acting for them; prohibits providing access to restricted parties; applies to derivatives; and explicitly includes executing, testing, analyzing, indexing, and ML-pipeline incorporation within its use definition. GitHub identifies the license as `NOASSERTION`, not MIT. This is **not ordinary permissive MIT**, and unsuitable for an unqualified “open-source MIT dependency” recommendation. Seek explicit permission/legal clarification before adoption, especially in agent-integrated products. — [LICENSE](https://github.com/Dicklesworthstone/beads_rust/blob/main/LICENSE); [metadata](https://api.github.com/repos/Dicklesworthstone/beads_rust)
- Project metadata: created 2026-01-18, 1,114 stars, pushed 2026-10-05; its advertised classic architecture has not prevented dependency/storage-engine changes. — [metadata](https://api.github.com/repos/Dicklesworthstone/beads_rust); [current manifest](https://github.com/Dicklesworthstone/beads_rust/blob/main/Cargo.toml)

### Inferences

- **Conditional Beads configuration:** choose `BEADS_DIR=<workspace>/.sane/issues/beads`, initialize with `--stealth`, ensure the enclosing `.sane/` is excluded from Git, and never configure Dolt remotes or run push/pull. This uses documented isolation mechanisms, but embedding still needs a supervised CLI adapter, issue UI, mapping, concurrency handling, and upgrade/backup policy. It does not require users to accept a SANE workstream. — Basis: [Git-free mode](https://github.com/gastownhall/beads#-git-free-usage); [Dolt single-writer mode](https://github.com/gastownhall/beads/blob/main/docs/architecture/dolt.md)
- **Technical, not licensing-approved, br configuration:** redirect `BEADS_DIR`, disable auto-import/auto-flush and unwanted JSONL history, do not call export/sync automatically, and keep all storage ignored/external. It meets no-committed-artifact storage behavior in principle, but removing sync also removes the collaboration story; backup and multi-machine sharing become SANE responsibilities. The license currently prevents recommending this as the clean OSS choice. — Basis: [configuration](https://github.com/Dicklesworthstone/beads_rust); [license](https://github.com/Dicklesworthstone/beads_rust/blob/main/LICENSE)
- For a small human-facing Linear-like board, Beads's graph/memory/orchestration orientation is probably more machinery than a minimal native issue service. Reuse makes most sense if dependency-aware agent task queues are central, not merely because an npm installer exists. — Basis: [Beads purpose/features](https://github.com/gastownhall/beads)

### Gaps

- These configuration recipes were source/document verified only, not executed. No claim of a proven zero-side-effect initialization is made.
- No published JS SDK, stable external Rust ABI, or supported embedded Go integration contract for current Beads was verified.
- License interpretation is not legal advice. Restrictive or anomalous text is reported rather than presumed harmless.

## 3. Which lightweight standalone apps are realistic reuse candidates, and what must SANE build itself?

### Takeaway

**Lific is the strongest verified lightweight full-tracker sidecar candidate**, with real SQLite storage, a built-in board UI, REST/CLI/MCP, and no Git-based issue store. It is a standalone Rust/Svelte app—not a React npm SDK. BugBytes is a poor local-first fit; smaller reference apps can supply ideas but do not eliminate custom integration work.

### Cited Findings

**Lific — best full-app/sidecar shortlist**

- Lific describes one binary (~25–32 MB depending on platform), embedded SQLite, embedded web UI, and a content-addressed attachments directory beside the database. It provides status/priority/labels/modules/relations/comments, list/board views, search, pages, activity/audit history, and optional plans. It explicitly says it is a database/API rather than markdown-in-Git. — [README](https://github.com/VoidNullable/lific)
- Library/package classification: Rust CLI app, `2.10.0`, Apache-2.0, Axum/Tokio + bundled `rusqlite`, embedded assets, and RMCP; its web package is `private: true`, Svelte 5/Vite, with `svelte-dnd-action`. The inspected `src/lib.rs` URL was absent. No advertised npm domain SDK or reusable React tracker component was found; consume REST/MCP or host its UI rather than promising an import. — [Cargo manifest](https://github.com/VoidNullable/lific/blob/master/Cargo.toml); [web manifest](https://github.com/VoidNullable/lific/blob/master/web/package.json); [license](https://github.com/VoidNullable/lific/blob/master/LICENSE); [repository](https://github.com/VoidNullable/lific)
- Storage is naturally outside the source repository: default init uses OS-standard user config/data locations. `--config <path>` overrides discovery; relative database paths resolve relative to the config file, and `--db` overrides database path. A per-workspace config/db/attachments/backup directory under ignored `.sane/` is supported by those knobs. No issue Git sync is required; multi-machine access is to one server/database, not replicas merging. — [configuration and wrong-tool guidance](https://github.com/VoidNullable/lific)
- **Avoid default onboarding side effects:** `lific init` installs and starts an OS background service; `--no-service` skips that and `lific start` runs foreground. `lific connect` writes agent client MCP configs, and `lific agents-md` writes repo instructions; neither is required to create/update ordinary issues. SANE should manage its own sidecar lifecycle and registrations. — [README setup and agent onboarding](https://github.com/VoidNullable/lific)
- REST, direct SQL CLI, and stdio/Streamable HTTP MCP are provided. There are 31 advertised MCP tools across issues/comments/plans/pages/attachments/search/history/structure/export. Direct CLI and stdio can work without a server; the human UI requires the server. — [README tool table and transports](https://github.com/VoidNullable/lific)
- Login-free private mode sets `[auth] required=false` and `server.host=127.0.0.1`, with guardrails against non-loopback exposure. Project membership is default-deny on fresh v2+ installs; operator/unbound keys and admins deliberately bypass it, and old upgraded installs retain disabled enforcement until opted in. For workspace isolation, separate DB instances are the clearest boundary; shared-server project roles are a different, logical boundary. — [authorization and configuration](https://github.com/VoidNullable/lific)
- Backups include the DB **and attachments**, using consistent snapshots and single archives; automatic interval backups have retention. Restores require stopping the server. No distributed multi-writer synchronization, enterprise SSO/SAML, or full sprint-estimate-Gantt layer is claimed. — [backup/restore and wrong-tool guidance](https://github.com/VoidNullable/lific)
- Maturity remains emerging: created 2026-04-03, 66 stars, pushed 2026-10-02. The version number and rich feature list are not proof of long production history. — [repository metadata](https://api.github.com/repos/VoidNullable/lific)

**BugBytes — full app with cloud-auth/relational backend requirements, not a local SDK**

- Located the relevant project as **`mishhtachio/BugBytes`**, not the unrelated BugBytes tutorial channel. Its README describes React 18/Vite UI, Express backend, **Clerk authentication**, PostgreSQL (Supabase or local) through Prisma, workspace/project isolation, issues/list/Kanban, member roles, activity, and optional Git commit/PR webhook transitions. Storage is a database, not tracked issue files, but its documented setup is not SQLite/offline local-first. — [README](https://github.com/mishhtachio/BugBytes)
- The package is a **private full-app package**, named `@figma/my-make-file`, with Vite/server/build scripts and numerous frontend/backend dependencies. There is no documented importable tracker SDK, embeddable domain package, CLI or MCP surface in the examined sources. Auth removal or adaptation would be actual development work, not a toggle verified here. Local PostgreSQL is supported by the documented connection URL; that does not remove the documented Clerk prerequisite. — [package.json](https://github.com/mishhtachio/BugBytes/blob/main/package.json); [README setup](https://github.com/mishhtachio/BugBytes)
- README claims MIT and links `LICENSE`, but that linked file returned 404, and GitHub metadata supplied no license classification. **Licensing is unverified, not “confirmed MIT.”** Repository created 2026-06-05, one star, pushed 2026-10-02. — [README license claim](https://github.com/mishhtachio/BugBytes#-license); [linked LICENSE](https://github.com/mishhtachio/BugBytes/blob/main/LICENSE); [metadata](https://api.github.com/repos/mishhtachio/BugBytes)
- Git webhook integration is issue-to-code automation, **not** evidence that issue artifacts must be committed into Git. Keeping issue data off-repo does not cure its auth/backend/SDK/licensing mismatch. — [webhook and database documentation](https://github.com/mishhtachio/BugBytes)

**Other lightweight reference implementations**

- **`btholt/mcp-issue-tracker`** is a full-stack React 18/Vite + Fastify/SQLite/BetterAuth example app (repository description says “An example app for the ...”). It offers CRUD, tags, assignees, filters, and REST endpoints. A configurable `DATABASE_PATH` allows external storage. Apache-2.0 is documented and detected by GitHub; created July 2025, 122 stars, last pushed 2025-07-26. It is a useful code/reference starting point, not a verified maintained drop-in SDK. — [README](https://github.com/btholt/mcp-issue-tracker); [metadata](https://api.github.com/repos/btholt/mcp-issue-tracker)
- Its backend package has Fastify, BetterAuth, bcrypt, `better-sqlite3`, and `sqlite3` dependencies, with app launch/build/migration scripts rather than a supported host-embedding interface. README setup still contains template URLs; its documented feature list does not establish workspace/project isolation, Kanban, or MCP capability merely because the repository name includes MCP. — [backend manifest](https://github.com/btholt/mcp-issue-tracker/blob/main/backend/package.json); [README](https://github.com/btholt/mcp-issue-tracker)
- **LineAgent as a sidecar** stores SQLite in `LINEAGENT_DATA_DIR` (default `/data`), exposes REST, CLI and stdio MCP (19 advertised tools), supports projects, tickets, parents/cycles/relations/comments, full-text search, audit, and user tenancy. It explicitly says it lacks a pretty human UI. Bind host defaults to `0.0.0.0`, so a local SANE deployment should choose loopback explicitly; a separate data directory/database per workspace gives stronger isolation than relying only on project filters. Its youth and license anomaly remain the major warnings. — [README variables, features, MCP](https://github.com/deepfounder-ai/LineAgent); [LICENSE](https://github.com/deepfounder-ai/LineAgent/blob/main/LICENSE)

### Inferences

**Recommended decision order**

1. **Native thin issue service + SQLite + dnd-kit (preferred for actual in-app embedding).** Full control over workspace ownership, look/feel, and not requiring SANE workflow onboarding. This is a custom build, not a discovered complete npm tracker. Use an existing board only to save board implementation, never to imply persistence/domain features are solved. — Basis: [dnd-kit scope](https://github.com/clauderic/dnd-kit); [SQLite binding API](https://github.com/WiseLibs/better-sqlite3)
2. **Lific sidecar (preferred for reusing a finished lightweight tracker).** Launch with an explicit per-workspace config/data path, no OS-service/client-config installation; use its API from SANE or link/embed its whole UI. An iframe/webview would embed a full application, not transform it into a React library. This saves issue-domain/agent/backup features at the cost of a second runtime and integration/lifecycle/auth/UI work. — Basis: [Lific interfaces and configuration](https://github.com/VoidNullable/lific); [private Svelte frontend](https://github.com/VoidNullable/lific/blob/master/web/package.json)
3. **Beads Git-free CLI adapter (conditional).** Sensible if agent dependency graphs matter more than a simple human tracker; pin a version and isolate with explicit `BEADS_DIR` + stealth. Dolt, domain complexity, single-writer embedded storage, and UI adapter cost make it a weaker default for this user need. — Basis: [Beads Git-free mode](https://github.com/gastownhall/beads#-git-free-usage); [Dolt modes](https://github.com/gastownhall/beads/blob/main/docs/architecture/dolt.md)
4. **LineAgent experimental domain/sidecar** only after license clarification and a maturity assessment. **Do not shortlist beads_rust or LibXAI as clean OSS defaults under current licenses; do not shortlist BugBytes as local-first/drop-in.** — Basis: [LineAgent metadata](https://api.github.com/repos/deepfounder-ai/LineAgent); [LineAgent license](https://github.com/deepfounder-ai/LineAgent/blob/main/LICENSE); [br license](https://github.com/Dicklesworthstone/beads_rust/blob/main/LICENSE); [LibXAI license](https://github.com/libxai/libxai-suite/blob/feature/time-tracking/LICENSE); [BugBytes architecture](https://github.com/mishhtachio/BugBytes)

**What the native option explicitly needs built**

This is a proposed minimal scope, inferred from the requirements and the libraries' limited responsibilities, not a claim that a supplied package already provides it. — Basis: [controlled board state responsibilities](https://github.com/christopher-caldwell/react-kanban); [SQLite low-level API](https://github.com/WiseLibs/better-sqlite3)

- Issue schema/service: stable IDs, title, Markdown description, status, priority, labels, created/updated times; optional assignee, parent, project, and relation tables only as needed.
- Storage ownership: database, WAL/SHM, attachments, backups/exports/config under a fully ignored `.sane/issues/` directory or OS application data keyed by stable workspace ID. Repo paths should not be the only identity if workspaces can move; define whether linked worktrees share issues or get separate stores.
- UI: board and list, create/edit/detail panel, search/filter/sort, Markdown rendering/sanitization, empty/error/loading states, keyboard controls, and persistent rank/order when cards move. dnd-kit does not supply these product features; a board component supplies only a subset.
- Persistence/API: validated CRUD, transactional status/order changes, migrations, indexes, pagination, concurrent edit conflict policy, archive/delete semantics, and notifications/refresh after agent writes.
