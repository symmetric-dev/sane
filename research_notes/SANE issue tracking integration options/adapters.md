# Lowest-effort hosted issues and optional workspace-aware harness adapters

Research verified by fetching primary sources in this session on **2026-10-05** (session date). This is a retrieval date, not a claimed publication or release date. Most sources are living documentation or `main`/`trunk` files; no immutable source snapshot or installed harness version was verified. Scope is general integration research, not an inspection of SANE implementation. Recommendations below are explicitly inferences, not claims about existing SANE capabilities. No code, tests, browser verification, harness configuration, skills, or issue records were changed.

## 1. Is “just use GitHub Issues” the lowest-effort option, and what is actually open source?

### Takeaway

For someone already using GitHub, the lowest-effort starting point is an explicitly selected issue repository plus links to its issue list/new-issue form; `gh` adds structured access without building another tracker. **GitHub.com Issues is a proprietary hosted service, not an OSS issue-tracker backend**: OSS `gh` and GitHub MCP are access layers; Forgejo/Gitea are the narrowly relevant OSS provider alternatives.

### Cited Findings

- GitHub provides hosted free/paid plans, including unlimited private repositories with limited feature sets on Free for individuals and organizations. Enterprise Cloud is hosted by GitHub; Enterprise Server is a separate self-hosted offering, not evidence that GitHub's issue service is OSS. Keep the hosted-service choice separate from client/server OSS licensing. — [GitHub plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)
- GitHub CLI explicitly calls itself an open-source tool, and its source license is MIT. Its issue commands include create/list/view/edit/comment/close/reopen and accept explicit `-R [HOST/]OWNER/REPO`. — [Creating an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/creating-an-issue); [gh issue](https://cli.github.com/manual/gh_issue); [gh MIT license](https://raw.githubusercontent.com/cli/cli/trunk/LICENSE)
- `gh issue list` supports JSON fields, state/label/assignee/search filters, and a default maximum of 30 fetched issues. `gh issue create` accepts title/body and `--body-file -` for stdin, or `--web` to open the creation form. These make a small UI wrapper feasible, but do not create local-workspace semantics. — [gh issue list](https://cli.github.com/manual/gh_issue_list); [gh issue create](https://cli.github.com/manual/gh_issue_create)
- GitHub supports new-issue form URLs with title/body/labels parameters. They open a form for human submission; invalid parameters/permissions can yield 404 and excessively long URLs can yield 414. — [Creating an issue from a URL query](https://docs.github.com/en/issues/tracking-your-work-with-issues/creating-an-issue#creating-an-issue-from-a-url-query)
- GitHub's official MCP server is MIT-licensed and offers issue-management tools. A local binary can be built/run without Docker; the container is another option. The remote endpoint `https://api.githubcopilot.com/mcp/` is hosted by GitHub. Its documentation says the remote service binds this OSS library into GitHub infrastructure using an **internal repository**, and has some remote-only tools. OSS local MCP server != fully open-source hosted GitHub service. — [GitHub MCP README](https://github.com/github/github-mcp-server); [Remote server documentation](https://raw.githubusercontent.com/github/github-mcp-server/main/docs/remote-server.md)
- GitHub MCP supports issue-only toolsets and read-only mode: local `--toolsets issues --read-only`, or remote `https://api.githubcopilot.com/mcp/x/issues/readonly`. Defaults otherwise include context, repos, issues, pull requests, and users. Lockdown mode is explicitly a best-effort public-content filter, **not an authorization boundary**. — [GitHub MCP README](https://github.com/github/github-mcp-server); [Remote toolsets/headers](https://raw.githubusercontent.com/github/github-mcp-server/main/docs/remote-server.md)
- Forgejo versions v9+ use GPL-3.0-or-later; versions through v8 used MIT. Gitea documents its OSS core as MIT and self-hosted, with issue tracking. Do not confuse the Forgejo documentation's Apache license with the software's GPL license, or Gitea's commercial Cloud/Enterprise offerings with its OSS core. — [Forgejo FAQ/license](https://forgejo.org/faq/#is-forgejo-licensed-under-the-gpl); [What is Gitea?](https://docs.gitea.com/)
- Both Forgejo and Gitea document repository issue creation at `/api/v1/repos/{owner}/{repo}/issues`, API tokens, pagination, and instance-specific Swagger/OpenAPI at `/api/swagger` and `/swagger.v1.json`. Forgejo guarantees API compatibility within a major version, but warns of breaking changes across majors. — [Forgejo API usage](https://forgejo.org/docs/latest/user/api/usage/); [Gitea API usage](https://docs.gitea.com/development/api-usage)
- Forgejo supports `read:issue`/`write:issue` scopes and tokens restricted to specific repositories. Gitea documents `read`/`write` scope groups including `issue`; write includes read. These are distinct API/auth contracts, not a promise that GitHub CLI or GitHub MCP works against either forge merely by changing its hostname. — [Forgejo token scopes](https://forgejo.org/docs/latest/user/authentication/token-scope/); [Gitea API usage](https://docs.gitea.com/development/api-usage)

### Inferences

- **Effort ladder:** (1) SANE workspace setting + “Open issues”/“New issue” links; (2) list/detail pane backed by `gh --json`, with optional user-confirmed create/comment/close; (3) direct REST adapter if credential control, packaging, pagination, or dependency-free distribution warrants it; (4) optional harness tools. None needs a new issue database, issue Markdown files in Git, Projects, or SANE phase acceptance.
- `gh` is especially economical if already installed/authenticated; it adds an executable dependency and process/error handling if SANE ships it as an integration. Spawn argv directly, always supply explicit `-R`, pass bodies via stdin, and parse JSON rather than terminal tables. Do not invoke a shell with user-generated issue text.
- Keep issue creation bodies out of URL query strings when sensitive or large: URL prefill is simple, but leaks content to browser history/logging and has length limits. A plain new-issue URL or API/CLI preview-and-submit is safer.
- If an **OSS backend** is a hard requirement, prefer the Forgejo/Gitea instance the user already operates. Deploying an entire forge only for SANE issues adds hosting/upgrades/backups and is not the lowest-effort GitHub path. Implement one such adapter only when actually selected; do not broaden this into a tracker marketplace.

### Gaps

- No packaged deployment, installed `gh` version, Forgejo/Gitea instance, or third-party forge MCP implementation was inspected or exercised. Current unversioned docs displayed Forgejo v16 and Gitea v28; that is observed documentation, not confirmation of a deployed version.
- No cost model beyond the cited plan features was established; organizational policy, residency, or account restrictions can invalidate an otherwise simple hosted choice.

## 2. How should local workspaces map to remote issues, with private storage, auth, and rate limits?

### Takeaway

GitHub issues belong to **repositories**, not local directories or SANE workspaces; organizations aggregate repository issues and own Projects, rather than replacing repository issue identity. Use a user-confirmed mapping from a stable local workspace ID to provider/host/repository, keeping authoritative issue data remote and only disposable config/cache locally.

### Cited Findings

- GitHub REST issue list/create/get/update endpoints are repository-addressed: `/repos/{owner}/{repo}/issues[/number]`. `/issues` and `/orgs/{org}/issues` are broader authenticated-user views; the org endpoint defaults to assigned issues, not an independent org-wide issue store. REST list/get can return pull requests too; distinguish them by `pull_request`. Lists paginate with default 30 and maximum 100 per page, and support `since`, labels, and state filters. — [Issues REST reference](https://docs.github.com/en/rest/issues/issues)
- API issue creation requires repository pull access and issues enabled; disabled issues return 410. Creation triggers notifications. Labels/assignees/milestones can be silently dropped without adequate repository access. Updates are allowed for issue owners or users with push/Triage access. Transfers can produce 301 redirects; inaccessible transferred issues can appear as 404. — [Issues REST reference](https://docs.github.com/en/rest/issues/issues)
- `gh auth login` defaults to a web flow and system credential store, but can **fall back to plaintext** if secure storage is unavailable. Its documented classic-token minimum scopes for `--with-token` are `repo`, `read:org`, `gist`; it recommends `GH_TOKEN` for fine-grained-token usage because `--with-token` can be confusing with resource-limited tokens. These are CLI login requirements, not minimal issue-only REST permissions. — [gh auth login](https://cli.github.com/manual/gh_auth_login)
- Fine-grained PATs can select one resource owner and specific repositories and permissions. Organizations can require approval; pending tokens read only public resources. Tokens cannot exceed the user's own privileges. Current docs also list limitations for outside collaborators, multiple organizations, and user-owned Projects. GitHub recommends a GitHub App for organizational or long-lived integrations. — [Managing PATs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
- The permission table lists repository **Issues read** for list/get and **Issues write** for create; update/comment endpoints list Issues write as an accepted permission, with additional/alternative-permission details to check per endpoint. Scope only the chosen issue repositories; do not request Contents/Actions/Projects permissions merely to create issues. — [Fine-grained PAT endpoint permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens#repository-permissions-for-issues)
- GitHub MCP supports PATs and OAuth; the local README currently documents first-use OAuth on github.com as well as PAT env auth. The remote README warns that host OAuth support requires the host's GitHub App/OAuth App setup; generic MCP OAuth capability alone does not establish that a particular host works with GitHub OAuth. — [GitHub MCP authentication/setup](https://github.com/github/github-mcp-server)
- Projects are owned by users/organizations and layer project items/fields over issues/PRs, also supporting draft issues. The GraphQL guide requires project/item/field/option node IDs; adding an issue item and updating its field are separate calls. CLI/classic-token examples need `read:project` or `project`. A project can contain redacted inaccessible content. The current REST permission table also lists organization ProjectsV2 endpoints, so claiming “Projects is GraphQL-only” would be inaccurate. — [Projects API guide](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects); [Projects REST permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens#organization-permissions-for-projects)
- GitHub REST primary limits normally are 60 requests/hour unauthenticated or 5,000/hour authenticated user, with specific higher/lower auth cases. Search has stricter limits; GraphQL has its own primary budget. Secondary limits include 100 concurrent requests across REST/GraphQL and generally 80 content-generating requests/minute and 500/hour, subject to change and tighter endpoint limits. Handle 403/429, `retry-after`, reset headers, and exponential backoff; response headers are authoritative. — [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

### Inferences

#### Mapping and edge cases

- Store an explicit **issue target**, separate from the code remote: `{workspaceId, provider, host, repositoryId, owner, repo, optionalFilter, credentialRef}`. Repository ID and provider issue ID protect identity across renames/transfers; owner/repo/number and URL remain useful display/routing locators. Resolve redirects and update bindings deliberately.
- A Git remote is a discovery **suggestion**, not the authority. Ask the human to confirm owner/repo, privacy, and account before the first write. Multiple remotes/forks/SSH aliases should not silently choose the issue target. Defaulting every request to `origin` or shell cwd risks cross-workspace mistakes.
- **Local repository without a remote:** choose an existing private issue-only repository or let the user create one through the provider UI. No code push, remote addition, or local issue commit is necessary. A repository has issues independently of whether that local code is pushed (inferred from explicit `-R`/repository REST addressing).
- **Multiple local workspaces sharing one remote:** default to a shared repository backlog if that is the human's intent. If separate views are needed, use an explicit label/filter or separate issue repositories. Labels/views are organization aids, **not access-control boundaries**. If privacy or membership differs, use a separate private repository.
- **Worktrees/checkouts:** define whether they inherit one logical workspace binding or have independent IDs; do not automatically duplicate issue stores per temporary worktree. A directory path can move; keep it as a locator, not the sole identity. Sharing a remote does not prove two workspaces are identical.
- **Private issues about public code:** point the workspace at a separate private issue repository and keep code references optional. Its membership controls visibility. A private Project layered over public issues is not a substitute for private issue storage; project view privacy cannot make the underlying public issue private.

#### Minimal storage/auth/adapter proposal

- Authoritative title/body/comments/state/labels remain at the provider. Store binding, credential references, cursors/ETags, last-fetch time and disposable snapshots only in **ignored `.sane` config/cache or app-local state**. No committed issue data, skill edits, workstream acceptance state, or lifecycle mirroring. Confirm ignore policy during implementation rather than assuming every `.sane` file is untracked.
- Do not put PATs in `.sane`, committed harness configs, logs, or model-visible tool arguments. Reuse a securely stored `gh` login for the lowest-effort personal case, but surface plaintext fallback; or use an OS credential store with narrow PAT permissions. Reauthorize/recheck permissions on account changes. Use an App only when distribution/team auth justifies its setup cost.
- Tiny provider interface: `connectionStatus`, `resolveTarget`, `listIssues(filters,cursor)`, `getIssue(ref)`, `createIssue(draft)`, `addComment(ref,body)`, `setState(ref,open|closed)`, optionally `updateIssue(title/body/labels)`. Return stable ref + number + URL + provider state + timestamps; normalize auth/rate-limit/offline/target-disabled errors. Leave delete/transfer/assign-agent/Projects/subissues/automation outside MVP.
- Partition private cache by provider host/repository **and credential identity**, not just workspace; purge/revalidate when access changes. Indicate stale/offline views, support cache clearing, and never claim an offline draft was submitted. Avoid an offline mutation queue initially: unknown create outcomes/retries need deduplication and user reconciliation, not blind repeated POSTs.
- Fetch on open/manual refresh with modest optional polling, shared fetch deduplication for workspaces pointing at one repository, bounded pagination, and backoff. No webhook hosting or Projects schema synchronization is needed for a personal issue pane.

### Gaps

- No SANE workspace identity model, credential storage, or ignore policy was reviewed. The proposed fields/paths are general requirements, not existing APIs or final schemas.
- Provider authorization and organization SSO/approval behavior must be checked for the selected account. Narrow scopes and labels alone do not guarantee workspace isolation.
- No exact Projects/search/GraphQL budget or provider-specific forge throttling was measured; consult the chosen endpoint/instance if those features are later required.

## 3. What optional harness extensions are verified, and should tools go direct or through SANE?

### Takeaway

Both OpenCode and Claude Code support MCP, but their plugin/hook contracts are **different**, and neither provider MCP nor a lifecycle hook establishes SANE workspace authorization. Direct `gh`/GitHub MCP is cheapest for personal chat use; route optional tools through a SANE workspace-aware backend when the app must enforce the same target, account, privacy, and confirmation behavior across harnesses.

### Cited Findings

- **OpenCode V2 MCP:** configure under `mcp.servers` with local `command: [...]`, `cwd`, `environment`, or remote `url`, `headers`, `oauth`; remote servers use OAuth by default. Credentials are outside project config. Project server objects replace same-name lower-precedence objects in full. Names are normalized `<server>_<tool>`; permission rules match those names. Tools use Code Mode by default. — [OpenCode V2 MCP](https://opencode.ai/v2/docs/mcp-servers)
- OpenCode sends `_meta["ai.opencode/sessionID"]` on session tool calls, including Code Mode. It is optional for non-session calls, identifies an OpenCode session rather than an MCP transport session, and docs explicitly prohibit using it alone for authentication/authorization. — [OpenCode V2 MCP context](https://opencode.ai/v2/docs/mcp-servers#context)
- **OpenCode V2 plugins:** `Plugin.define({id, setup(ctx)})` from `@opencode/plugin`; local `.opencode/plugins/` or configured packages/paths. Custom tools use `ctx.tool.transform(editor => editor.add(...))`, JSON Schema input, and executors with cancellation signals. Context includes `ctx.location.directory`, optional workspace ID and project metadata, but docs warn that this is the plugin instance's location, **not every session/event's location**. — [OpenCode V2 plugins](https://opencode.ai/v2/docs/build/plugins)
- Verified V2 runtime hooks include `ctx.session.hook("prompt"|"context", ...)`, `ctx.tool.hook("execute.before"|"execute.after", ...)`, `ctx.permission.hook("evaluate", ...)`, and `ctx.shell.hook("create.before", ...)`. Tool hooks inspect/replace inputs/results; permission hooks can change allow/ask to allow/ask/deny, but configured deny is final. Prompt hooks are **not exactly-once side-effect boundaries**, can run multiple times under concurrent admission, and do not expose a typed rejection API. V1 hook-object syntax is a separate contract, not translated automatically to V2. — [OpenCode V2 plugin hooks](https://opencode.ai/v2/docs/build/plugins#hooks)
- **Claude Code MCP:** local stdio or remote HTTP, with local scope (default, per-project in `~/.claude.json`), project scope (`.mcp.json`), and user scope (`~/.claude.json`). MCP can be bundled in a Claude plugin. Normal tool names are `mcp__<server>__<tool>`; plugin-bundled names include the plugin scope, unlike OpenCode's names. — [Claude Code MCP](https://code.claude.com/docs/en/mcp)
- Claude's local stdio server gets `CLAUDE_PROJECT_DIR`, a stable launch project root; it does not change with extra working directories. `roots/list` returns granted directories and can change. For hooks, `cwd` follows the current/worktree directory whereas `CLAUDE_PROJECT_DIR` stays at launch root. These are location hints, not remote repository mappings. — [Claude Code MCP stdio](https://code.claude.com/docs/en/mcp#option-3-add-a-local-stdio-server); [Claude hooks path variables](https://code.claude.com/docs/en/hooks#reference-scripts-by-path)
- **Claude Code hooks:** settings/plugin JSON events such as `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, and `Stop`; command handlers receive JSON stdin and return stdout/exit decisions, while HTTP hooks receive POST JSON. `PreToolUse` can block; `PostToolUse` is after success, not a pre-write guard. Config can be personal/project/local or plugin `hooks/hooks.json`. Current docs additionally describe MCP-tool/prompt/agent handler types; do not assume those are available in an unverified installed version. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- Current Claude docs warn that command hooks can run from fallback directories if cwd disappears. MCP-tool hooks on initial `SessionStart`/`Setup` are skipped because MCP client context is unavailable, and hooks do not start OAuth flows. These constraints matter if trying to attach tracker context on launch. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- Both harness docs provide local/remote MCP integration, but GitHub's own README qualifies remote OAuth by host-specific support. Adding a URL is not proof that sign-in or provider writes work. — [OpenCode MCP OAuth](https://opencode.ai/v2/docs/mcp-servers#oauth); [Claude MCP](https://code.claude.com/docs/en/mcp); [GitHub MCP README](https://github.com/github/github-mcp-server)

### Inferences

| Optional route | Effort/value | Workspace limitation / guardrail |
| --- | --- | --- |
| Harness shell calls `gh` directly | Almost no integration if installed and authenticated | Always use confirmed `-R`; shell cwd/agent inference is not workspace isolation. SANE cannot centrally govern bypassing direct provider calls. |
| Harness connects official GitHub MCP | Ready-made issue operations; local OSS or hosted endpoint | Issue toolset narrows capability, not repository access. Use narrow credentials, read-only start, and human permission prompts; verify host OAuth compatibility. |
| Harness calls a small SANE issue MCP/backend facade | More initial work; one app/harness target/auth policy | Backend resolves verified session/workspace bindings, allowlists repository and operations, and enforces approval independently of model assertions. |
| OpenCode-specific plugin / Claude-specific hook | Useful optional context, reminders, local notifications | Maintain two contracts. Never treat lifecycle completion, a filesystem edit, or test success as authorization to submit/close an issue. |

- **Recommended sequencing:** standalone workspace links/list first; direct harness access optional and user-managed; add a thin SANE facade only if consistent workspace policy across the app and harnesses is valuable. MCP is the common transport; an OpenCode plugin can register facade tools without making Claude implement the same plugin API.
- Facade tool names can be provider-neutral (`issues_list/get/create/comment/set_state`) and omit arbitrary remote URLs/owner/repo from mutation schemas. Resolve the issue target on the server. For multiple workspaces use a server-validated binding/capability, not a model-chosen absolute path. OpenCode session metadata and Claude cwd/root may help correlate an already authenticated local session, but are not credentials.
- On local HTTP, bind loopback and authenticate requests with an app-minted capability; validate incoming host/URLs and workspace ownership. On stdio, derive authority from the app-launched process/session binding. An issue reference must also be verified against the selected repository. Do not forward provider secrets to the model or assume “localhost” makes requests trustworthy.
- Enforce confirmation **in the backend**, or through trusted user UI with a single-use approval token bound to workspace, target, operation, draft and expiry. A model-provided `confirmed: true` is not human confirmation. Show provider/host/repo/privacy and account alongside the draft and resulting URL. A permission prompt authorizes a call, not necessarily that inferred remote target is correct.
- Hooks can add a terse selected-target reminder, annotate a session with an explicitly selected issue, invalidate cache after an approved mutation, or notify the app that a tool completed. Prefer request/result metadata over harvesting transcripts. Do not automatically create issues from every failure, comment every turn, close on Stop, assign Copilot, start workstreams, or couple tracking to SANE skills/acceptance.
- Treat remote issue bodies/comments as untrusted content: display/render safely, do not execute embedded instructions, and keep human-selected operations distinct from fetched text. Official MCP lockdown may reduce exposure but does not replace credential/backend authorization.

### Gaps

- This research verifies **documentation contracts**, not actual installed OpenCode/Claude versions or SANE's current integration layer. Any implementation must recheck the target harness release and the existing app/session identity boundary.
- No end-to-end OAuth, hook, MCP, provider write, private-repository, or cross-workspace behavior was tested. No automatic issue mutation or tracker setup is authorized by these notes.
